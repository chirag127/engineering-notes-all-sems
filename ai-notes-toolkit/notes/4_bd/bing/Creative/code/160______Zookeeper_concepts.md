#### Zookeeper concepts

Zookeeper is a distributed coordination service that provides common services for distributed applications, such as naming, configuration management, synchronization, and group services. Zookeeper is based on a simple client-server model, where clients are nodes (machines) that use the services and servers are nodes that provide the services. Zookeeper stores data in a shared hierarchical namespace that is organized like a standard filesystem. Each node in the namespace is called a znode and can have data associated with it as well as children. Zookeeper maintains a consistent view of the data across all the servers and clients, and guarantees that changes are atomic and ordered. Zookeeper also provides mechanisms for clients to watch for changes in the data, to create ephemeral nodes that disappear when the client disconnects, and to implement distributed locks and barriers. Some of the main concepts of Zookeeper are:

- Znodes: Zookeeper stores data in a shared hierarchical namespace that is organized like a standard filesystem. Each node in the namespace is called a znode and can have data associated with it as well as children. Znodes can be either persistent or ephemeral. Persistent znodes remain in the namespace until explicitly deleted by a client. Ephemeral znodes are automatically removed when the client that created them disconnects. Znodes can also have sequential names, which means that Zookeeper appends a monotonically increasing number to the name of the znode. This can be useful for implementing queues or leader election.

- Node name: Every node in Zookeeper's namespace is identified by a path, which is a sequence of strings separated by slashes. For example, /app/config is a path that identifies a znode named config that is a child of a znode named app, which is a child of the root znode. Paths are absolute and case-sensitive.

- Client/Server: Clients connect to a single Zookeeper server, which is also called a quorum server. The server handles the client requests and sends back responses. The server also maintains a copy of the data in the namespace and participates in the leader election and synchronization protocols with other servers. A Zookeeper ensemble is a set of servers that work together to provide the Zookeeper service. Typically, an ensemble has an odd number of servers (such as 3 or 5) to avoid split-brain scenarios. One of the servers in the ensemble is elected as the leader, which coordinates the updates to the data and the communication with the followers. The followers are the other servers in the ensemble, which replicate the data from the leader and serve read requests from the clients. The clients can connect to any server in the ensemble, but they will be redirected to the leader if they want to write data.

- Configuration data: Each node in a Zookeeper namespace can have data associated with it as well as children. The data is a byte array that can store any kind of information, such as configuration parameters, status flags, or metadata. The data is limited to 1 MB in size and is stored in memory by the servers. The data can be read or written by the clients using the get and set methods. The data can also be watched by the clients, which means that the clients will be notified by the server if the data changes.

- Watches: Zookeeper provides a mechanism for clients to watch for changes in the data or the children of a znode. A watch is a one-time trigger that is set by the client when it performs a read operation, such as get or getChildren. The server will send a notification to the client if the watched znode changes, either in its data or its children. The client can then perform another read operation to get the updated information and set another watch if needed. Watches are useful for implementing dynamic configuration, service discovery, or distributed coordination.

- Sessions: Zookeeper maintains a session for each client that connects to a server. A session is identified by a unique session ID and has a timeout period. The client and the server exchange periodic heartbeats to keep the session alive. If the client fails to send a heartbeat within the timeout period, the server will expire the session and delete any ephemeral znodes created by the client. The client can also explicitly close the session by calling the close method. The client can reconnect to the same or a different server in the ensemble and resume the session if it has the same session ID and the session has not expired.
