### Unit 4 - Data Base Design & Normalization

- Database design is the process of creating a logical and physical structure for the data in a database system. It involves identifying the entities, attributes, relationships, and constraints that represent the real-world problem domain and organizing them in a way that facilitates efficient data storage, retrieval, and manipulation.
- Normalization is a technique of database design that helps in improving the quality and performance of the database. It involves applying a set of rules or principles to reduce data redundancy, eliminate data anomalies, and ensure data integrity and consistency.
- The main benefits of normalization are:
  - It reduces the amount of space required to store the data, as duplicate or unnecessary data is eliminated.
  - It simplifies the queries and operations on the data, as the data is organized in a logical and consistent way.
  - It prevents data inconsistencies and errors, as the data is stored in only one place and updated accordingly.
  - It makes the database more flexible and adaptable to changing business requirements, as new entities and attributes can be added or modified without affecting the existing data and relationships.
- The main drawbacks of normalization are:
  - It may increase the number of tables and joins in the database, which can affect the performance and complexity of the queries and operations.
  - It may require more processing power and memory to access and manipulate the data, as the data is distributed across multiple tables and relationships.
  - It may not be suitable for some types of applications or data, such as data warehousing, analytical processing, or hierarchical data, where denormalization or partial normalization may be preferred for better performance and usability.
- The process of normalization involves applying different levels or forms of normalization to the data, starting from the lowest to the highest. The most common forms of normalization are:
  - First Normal Form (1NF): It ensures that each attribute in a table has a single, atomic value and that there are no repeating groups or arrays of values within a table. For example, a table that stores customer orders should not have multiple columns for order items, but rather a separate table that stores each order item as a row.
  - Second Normal Form (2NF): It ensures that each attribute in a table depends on the whole primary key of the table and not on a subset of it. For example, a table that stores customer orders should not have attributes that depend only on the customer ID, but rather a separate table that stores customer details as a row.
  - Third Normal Form (3NF): It ensures that each attribute in a table depends only on the primary key of the table and not on any other attribute or non-key attribute. For example, a table that stores customer orders should not have attributes that depend on the order date, but rather a separate table that stores order dates as a row.
  - Boyce-Codd Normal Form (BCNF): It is a stronger version of 3NF that ensures that each attribute in a table depends only on a candidate key of the table and not on any other attribute or non-key attribute. A candidate key is a minimal set of attributes that can uniquely identify a row in a table. For example, a table that stores customer orders should not have attributes that depend on the order number, but rather a separate table that stores order numbers as a row.
  - Fourth Normal Form (4NF): It ensures that each attribute in a table depends only on a candidate key of the table and not on any other attribute or non-key attribute, and that there are no multi-valued dependencies in the table. A multi-valued dependency occurs when an attribute can have more than one value for a given combination of key attributes. For example, a table that stores customer orders should not have attributes that store multiple values for the same order, such as payment methods or delivery options, but rather separate tables that store each value as a row.
  - Fifth Normal Form (5NF): It ensures that each attribute in a table depends only on a candidate key of the table and not on any other attribute or non-key attribute, and that there are no join dependencies in the table. A join dependency occurs when a table can be decomposed into two or more tables and then reconstructed by joining them on their common attributes. For example, a table that stores customer orders should not have attributes that can be derived from joining other tables, such as order total or order status, but rather separate tables that store each attribute as a row.
