# Deadlock Handling

- A deadlock is an unwanted situation in which two or more transactions are waiting indefinitely for each other to release locks on shared resources   .
- A deadlock can cause the whole system to halt and waste CPU and memory resources.
- Deadlock handling is the process of preventing, avoiding, detecting or resolving deadlocks in a database system  .
- There are three classical approaches for deadlock handling, namely :
  - Deadlock prevention: This approach ensures that at least one of the necessary conditions for deadlock (mutual exclusion, hold and wait, no preemption, circular wait) is never satisfied . For example, a transaction can be forced to request all the locks it needs before starting, or to release all the locks it holds before requesting a new one . This approach can avoid deadlocks, but it may also reduce concurrency and cause unnecessary blocking .
  - Deadlock avoidance: This approach allows the system to grant a lock request only if it is safe, i.e., it does not lead to a potential deadlock situation . For example, the system can use a wait-for graph or a resource allocation graph to keep track of the dependencies among transactions and detect cycles . This approach can also avoid deadlocks, but it requires additional information and computation from the system and the transactions .
  - Deadlock detection and removal: This approach allows the system to detect a deadlock after it has occurred and take some actions to resolve it . For example, the system can periodically run a deadlock detection algorithm, such as the banker's algorithm or the wound-wait scheme, and abort or roll back one or more transactions involved in the deadlock . This approach can tolerate deadlocks, but it may also incur high overhead and performance degradation .
- In a distributed database system, deadlock handling is more complex and challenging than in a centralized system, because of the following issues :
  - Transaction location: The system needs to know the location of each transaction and the resources it requests or holds, which may be distributed across different sites . This requires a global view of the system state and a communication mechanism among the sites .
  - Transaction control: The system needs to coordinate the locking and unlocking of resources among different transactions, which may have different concurrency control protocols and deadlock handling policies . This requires a consistent and efficient decision making process and a conflict resolution mechanism among the sites .
- There are two main strategies for deadlock handling in a distributed database system, namely :
  - Centralized deadlock handling: This strategy assigns a single site as the deadlock coordinator, which is responsible for collecting the information about the transactions and the resources, running the deadlock detection algorithm, and initiating the deadlock resolution actions . This strategy can simplify the deadlock handling process and reduce the communication overhead, but it may also introduce a single point of failure and a performance bottleneck .
  - Distributed deadlock handling: This strategy distributes the deadlock handling tasks among the sites, which cooperate with each other to exchange the information about the transactions and the resources, detect the deadlock cycles, and resolve the deadlocks . This strategy can improve the reliability and scalability of the system, but it may also increase the complexity and communication overhead of the deadlock handling process .
