# Unit 2 - Software Requirement Specifications (SRS)

- Software Requirement Specifications (SRS) is a document that describes the features, functions, and constraints of a software system.
- SRS is also known as Software Requirements Document (SRD), Software Requirements Specification (SRS), or Functional Specification (FS).
- SRS is a communication tool between the stakeholders and the developers of the software system.
- SRS helps to ensure that the software system meets the needs and expectations of the stakeholders and the users.
- SRS also serves as a basis for software design, testing, validation, verification, and maintenance.

## Characteristics of a Good SRS

- A good SRS should be clear, concise, consistent, complete, correct, traceable, verifiable, modifiable, and unambiguous.
- A clear SRS uses simple and precise language, avoids jargon and technical terms, and defines all the terms and acronyms used.
- A concise SRS includes only the essential and relevant information, avoids repetition and redundancy, and uses tables, diagrams, and charts to present the information effectively.
- A consistent SRS does not have any conflicts or contradictions within or across the sections, and follows a uniform format and style throughout the document.
- A complete SRS covers all the requirements and constraints of the software system, and does not leave any gaps or ambiguities for interpretation.
- A correct SRS reflects the actual needs and expectations of the stakeholders and the users, and does not contain any errors or mistakes.
- A traceable SRS links each requirement to its source, such as a stakeholder, a user, a use case, or a business rule, and to its destination, such as a design component, a test case, or a validation criterion.
- A verifiable SRS specifies each requirement in a way that it can be checked and confirmed by using a test, a demonstration, an inspection, or an analysis.
- A modifiable SRS is organized and structured in a way that it can be easily updated and changed without affecting the quality and consistency of the document.
- An unambiguous SRS expresses each requirement in a way that it has only one possible meaning and interpretation, and does not leave any room for confusion or misunderstanding.

## Components of a SRS

- A typical SRS consists of the following components:

  - Introduction: This section provides an overview of the software system, its purpose, scope, objectives, and context. It also identifies the stakeholders and the users of the system, and defines the terms and acronyms used in the document.
  - System Overview: This section describes the general characteristics and features of the software system, such as its functions, interfaces, performance, quality, security, and reliability. It also provides a high-level view of the system architecture and design.
  - System Requirements: This section specifies the functional and non-functional requirements of the software system, such as the inputs, outputs, processes, data, constraints, and assumptions. It also defines the use cases and scenarios that illustrate how the system will be used by the users and interact with other systems.
  - System Models: This section presents the graphical and textual models that represent the software system, such as the data flow diagrams, entity-relationship diagrams, state transition diagrams, class diagrams, sequence diagrams, and activity diagrams. These models help to visualize and understand the structure, behavior, and dynamics of the system.
  - System Validation: This section defines the criteria and methods that will be used to validate and verify that the software system meets the requirements and expectations of the stakeholders and the users. It also specifies the test cases and test procedures that will be used to check and confirm the functionality and quality of the system.
  - Appendices: This section includes any additional or supplementary information that supports or complements the SRS, such as the references, glossary, bibliography, and index.
