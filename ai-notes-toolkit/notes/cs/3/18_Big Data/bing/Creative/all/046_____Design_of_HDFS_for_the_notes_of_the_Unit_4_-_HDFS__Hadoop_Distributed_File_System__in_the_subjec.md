# Design of HDFS

HDFS stands for Hadoop Distributed File System. It is a distributed file system that is designed to store very large files with streaming data access patterns, running on clusters of commodity hardware . HDFS is based on the Google File System and is a member of the Hadoop Ecosystem. HDFS is suitable for applications that have large data sets and require high throughput access to file system data.

Some of the key design features of HDFS are:

- **Blocks**: HDFS divides the files into fixed-size blocks (typically 128 MB or 256 MB) and stores them across the nodes in the cluster  . This reduces the metadata overhead and allows for parallel processing of the data.
- **Replication**: HDFS replicates each block across multiple nodes (usually three) to ensure fault tolerance and availability  . The replication factor can be configured per file or per cluster. HDFS also performs periodic checksum checks to detect and repair corrupted blocks .
- **NameNode and DataNodes**: HDFS has a master-slave architecture, where the NameNode is the master node that manages the namespace and the metadata of the file system, and the DataNodes are the slave nodes that store the actual data blocks    . The NameNode communicates with the DataNodes through heartbeats and block reports, and maintains the mapping of files to blocks and blocks to DataNodes  .
- **Client**: The client is the application that accesses the HDFS file system. The client interacts with the NameNode to locate the blocks of a file, and then directly reads or writes data from or to the DataNodes    . The client also performs some of the file system operations, such as creating, deleting, renaming, or appending files .
- **Rack Awareness**: HDFS is aware of the network topology of the cluster, and tries to place the replicas of a block on different racks to improve the data reliability and the network bandwidth utilization   . HDFS uses a rack-aware replica placement policy that prefers local nodes, nodes on the same rack, and nodes on a different rack, in that order.
- **High Availability**: HDFS supports high availability of the NameNode through the use of a secondary NameNode, a standby NameNode, or a quorum of JournalNodes. The secondary NameNode periodically merges the edits log with the fsimage file to prevent the edits log from growing too large . The standby NameNode keeps its state synchronized with the active NameNode through a shared storage or a quorum of JournalNodes, and can take over the role of the active NameNode in case of a failure. The JournalNodes are a group of nodes that store the edits log and allow the standby NameNode to read the edits log from the active NameNode.
- **Federation**: HDFS supports federation, which allows multiple NameNodes to coexist in the same cluster and manage different namespaces. This increases the scalability and the isolation of the file system. Each NameNode is paired with a corresponding ResourceManager that manages the resources and the scheduling of the applications that access the namespace. The DataNodes register with and send block reports to all the NameNodes in the cluster. The clients can access any namespace by specifying the NameNode address in the URI.
- **Erasure Coding**: HDFS supports erasure coding, which is a technique that encodes the data blocks into a number of data chunks and parity chunks, and stores them across different nodes. This reduces the storage overhead and improves the data durability compared to replication. Erasure coding is suitable for cold or archival data that is rarely accessed. HDFS uses Reed-Solomon codes or XOR codes as the erasure coding schemes. HDFS allows the users to specify the erasure coding policy per file or per directory.
