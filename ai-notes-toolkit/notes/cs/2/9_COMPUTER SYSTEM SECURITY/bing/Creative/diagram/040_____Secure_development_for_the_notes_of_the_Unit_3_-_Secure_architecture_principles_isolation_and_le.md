### Secure development for the notes of the Unit 3 - Secure architecture principles: isolation and least privilege

Secure development is the process of creating software systems that are resilient to security threats and vulnerabilities. Secure development requires following a set of principles, practices, and tools that help identify and prevent security flaws during early stages of software development, when it is most cost effective to do so.

Some of the key secure development principles are  :

- **Minimize attack surface area**: This principle states that every feature or functionality added to a software system increases the risk of a security vulnerability. Therefore, developers should only implement the essential features and functionalities that are required by the system, and avoid unnecessary or unused code, services, or interfaces that could expose the system to attacks.
- **Establish secure defaults**: This principle states that the default configuration of a software system should be secure and not require any additional actions by the users or administrators to enable security. For example, the default settings of a system should enforce strong passwords, encryption, and access control policies, and disable any insecure or unnecessary features or services.
- **The principle of least privilege**: This principle states that every component or user of a software system should only have the minimum level of access or permissions that are necessary to perform their tasks, and no more. This principle reduces the impact of a security breach, as an attacker would have limited access to the system or data, and also limits the potential damage that a malicious or compromised component or user could cause to the system or other components or users.
- **The principle of defense in depth**: This principle states that a software system should have multiple layers of security controls and mechanisms that protect it from different types of attacks and threats. This principle increases the difficulty and cost of an attack, as an attacker would have to bypass or compromise multiple security barriers to reach the target system or data, and also provides redundancy and resilience in case one layer of security fails or is compromised.
- **Fail securely**: This principle states that a software system should handle errors and exceptions in a secure manner, and not expose any sensitive information or functionality to the attacker or the user. For example, a system should not display detailed error messages that could reveal the system's configuration, architecture, or vulnerabilities, and should not allow any unauthorized access or actions when an error occurs.
- **Don't trust services**: This principle states that a software system should not blindly trust any external or internal services, components, or data sources that it interacts with, and should always validate and verify their inputs, outputs, and behaviors. This principle prevents the system from being exploited by malicious or compromised services, components, or data sources that could inject malicious code, data, or commands, or manipulate the system's logic or functionality.
- **Separation of duties**: This principle states that a software system should separate the roles and responsibilities of different components or users, and enforce checks and balances to ensure that no single component or user can perform sensitive or critical actions without the approval or oversight of another component or user. This principle prevents the system from being compromised by a malicious or corrupted component or user, and also provides accountability and auditability for the system's actions and transactions.
- **Avoid security by obscurity**: This principle states that a software system should not rely on hiding or obscuring its security mechanisms, algorithms, or keys, and should assume that the attacker knows or can discover them. This principle encourages the use of well-known and proven security standards and practices, and avoids the use of proprietary or custom security solutions that could have unknown or untested weaknesses or vulnerabilities.

These principles can be applied to different aspects of software development, such as design, coding, testing, deployment, and maintenance, and can help improve the security and quality of software systems.
