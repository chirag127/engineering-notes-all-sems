### Defense against Control Hijacking - Run-time Defenses

Control hijacking is a type of attack that exploits a vulnerability in a program to alter its execution flow and execute malicious code. Control hijacking can be performed by overwriting code pointers, such as return addresses, function pointers, or exception handlers, with the address of the attacker's payload. To prevent or mitigate control hijacking attacks, several run-time defenses have been proposed, such as:

- **Stack canaries**: A stack canary is a random value that is placed on the stack before a return address. The canary is checked before returning from a function to detect if it has been overwritten by a buffer overflow. If the canary is corrupted, the program aborts and prevents the execution of the attacker's payload. Stack canaries are effective against simple buffer overflows, but they can be bypassed by more advanced attacks, such as return-oriented programming (ROP) or format string attacks.
- **Non-executable memory**: Non-executable memory is a mechanism that marks certain memory regions, such as the stack or the heap, as non-executable, meaning that the processor will not execute any instructions from those regions. This prevents the attacker from injecting and executing arbitrary code on the target system. However, non-executable memory does not prevent the attacker from reusing existing code segments, such as libraries or system calls, to construct a malicious payload, as in ROP or jump-oriented programming (JOP) attacks.
- **Address space layout randomization (ASLR)**: ASLR is a technique that randomizes the base address of the executable, the libraries, the stack, and the heap, making it harder for the attacker to predict the location of the code pointers or the payload. ASLR increases the entropy of the address space, forcing the attacker to guess or leak the addresses before launching a control hijacking attack. However, ASLR can be defeated by brute-force attacks, information leaks, or memory disclosure vulnerabilities.
- **Code pointer integrity (CPI)**: CPI is a technique that ensures that only valid code pointers are used during the execution of a program. CPI separates the code pointers from the rest of the data and protects them with a cryptographic hash or a signature. CPI checks the integrity of the code pointers before using them, and aborts the program if they are corrupted. CPI can prevent arbitrary control hijacking attacks, but it may incur a high performance overhead and memory consumption.
- **Control flow integrity (CFI)**: CFI is a technique that enforces that the control flow of a program follows a predefined control flow graph (CFG), which is derived from the program's source code or binary. CFI inserts run-time checks at each indirect control transfer, such as a function call or a return, to verify that the target address is one of the valid successors in the CFG. CFI can prevent the attacker from diverting the control flow to arbitrary locations, but it may not prevent the attacker from executing a subset of the CFG that is still malicious, as in control flow bending attacks.
