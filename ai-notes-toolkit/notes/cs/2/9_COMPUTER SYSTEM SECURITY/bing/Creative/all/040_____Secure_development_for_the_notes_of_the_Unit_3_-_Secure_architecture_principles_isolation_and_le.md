# Secure development for the notes of the Unit 3 - Secure architecture principles isolation and least privilege in the subject of COMPUTER SYSTEM SECURITY

Secure development refers to the set of tools, practices, and approaches that the SEI has created to identify and prevent security flaws during early development of software systems, when it is most cost effective to do so. Some of the secure development principles are:

- **Minimize attack surface area**: Every time a programmer adds a feature to their application, they are increasing the risk of a security vulnerability. Therefore, it is important to keep the application as simple and modular as possible, and to limit the exposure of sensitive data and functionality to the minimum necessary.
- **Establish secure defaults**: The application should be configured with the most secure settings by default, and the user should be able to change them only if they have a valid reason and understand the implications. For example, the application should use encryption, authentication, and logging by default, and the user should be able to opt out only if they have a legitimate need and consent.
- **The principle of least privilege**: The application should ensure that people and processes only have enough access that they need to do their job, and no more. For instance, if the application holds sensitive customer financial information, it should limit who can access that information, and for what purpose. The application should also use the principle of least privilege internally, by separating different components and layers, and granting them the minimum permissions required to function .
- **The principle of defense in depth**: The application should not rely on a single security mechanism or layer, but rather use multiple and diverse security controls to protect the data and functionality. For example, the application should use encryption, firewalls, antivirus, intrusion detection, and backup systems to provide redundancy and resilience in case one of them fails or is compromised.
- **Fail securely**: The application should handle errors and exceptions gracefully, without exposing sensitive information or functionality to the attacker. For example, the application should not display detailed error messages that reveal the internal structure or configuration of the system, but rather log them and display generic messages to the user. The application should also not assume a default state of trust or access when an error occurs, but rather deny or restrict it until the error is resolved.
- **Don't trust services**: The application should not blindly trust the data or functionality provided by external services or components, but rather validate and verify them before using them. For example, the application should not assume that the input from the user, the network, or the database is safe or accurate, but rather sanitize and check it for malicious or erroneous content. The application should also not assume that the output from the application, the network, or the database is secure or reliable, but rather encrypt and sign it to prevent tampering or interception.
- **Separation of duties**: The application should enforce the separation of roles and responsibilities among different people and processes, to prevent conflicts of interest or abuse of power. For example, the application should not allow the same person to create, approve, and execute a transaction, but rather require different people or processes to perform these tasks. The application should also audit and monitor the actions and activities of different people and processes, to ensure accountability and traceability.
- **Avoid security by obscurity**: The application should not rely on hiding or obscuring the data or functionality to protect them, but rather use well-known and proven security mechanisms and standards. For example, the application should not use proprietary or custom encryption algorithms or protocols, but rather use widely accepted and tested ones. The application should also not assume that the attacker does not know or cannot access the data or functionality, but rather protect them regardless of their visibility or accessibility.
