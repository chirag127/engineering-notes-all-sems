# Bringing Microbatch and One-Record-at-a-Time Closer Together

- Spark's distributed processing model is based on the concept of **resilient distributed datasets (RDDs)**, which are immutable collections of data that can be processed in parallel across a cluster of nodes.
- Spark supports two types of operations on RDDs: **transformations** and **actions**. Transformations create new RDDs from existing ones, while actions trigger the computation and return the results to the driver program or write them to external storage.
- Spark also provides a high-level abstraction for streaming data processing called **structured streaming**, which allows users to write queries using SQL or DataFrame APIs on streaming data sources and sinks.
- Structured streaming is based on the idea of **incremental execution**, which means that the query is executed as a series of **micro-batches** of data that arrive over time. Each micro-batch is treated as a new input for the query, and the results are updated incrementally.
- Micro-batch processing has some advantages over one-record-at-a-time processing, such as better fault tolerance, higher throughput, and lower latency. However, it also has some limitations, such as the need to tune the batch size and the difficulty of handling late or out-of-order data.
- To overcome these limitations, Spark has introduced two features that bring micro-batch and one-record-at-a-time processing closer together: **continuous processing** and **watermarking**.
- Continuous processing is a new execution mode for structured streaming that allows users to specify a very low latency requirement (e.g., 1 ms) for their queries. In this mode, Spark runs the query as a single long-running task that processes each record as soon as it arrives, without waiting for micro-batches to form. This mode can achieve sub-millisecond end-to-end latency, but it sacrifices some fault tolerance and throughput compared to micro-batch processing.
- Watermarking is a technique that allows users to specify a threshold of how late they are willing to accept data for their queries. For example, if the watermark is set to 10 minutes, then any data that arrives more than 10 minutes late will be discarded. This way, users can handle late or out-of-order data in a principled way, without affecting the correctness of their results. Watermarking can be used in both micro-batch and continuous processing modes.
