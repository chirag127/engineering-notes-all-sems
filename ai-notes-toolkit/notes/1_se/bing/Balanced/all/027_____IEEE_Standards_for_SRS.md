### IEEE Standards for SRS

- A software requirements specification (SRS) is a description of a software system to be developed. It specifies the functional and nonfunctional requirements of the system, as well as the constraints, assumptions, dependencies, and quality attributes. 
- The IEEE Standards Association (IEEE-SA) provides several standards and guidelines for developing and documenting SRS. The most widely used one is IEEE 830-1998, which has been replaced by ISO/IEC/IEEE 29148:2011 (with an update in 2018). 
- The IEEE 830-1998 standard recommends the following structure for an SRS document:

  1. Introduction
     - Purpose
     - Scope
     - Definitions, acronyms, and abbreviations
     - References
     - Overview
  2. Overall description
     - Product perspective
     - Product functions
     - User characteristics
     - General constraints
     - Assumptions and dependencies
  3. Specific requirements
     - External interface requirements
     - Functional requirements
     - Performance requirements
     - Design constraints
     - Software system attributes
     - Other requirements
  4. Appendices
  5. Index

- The IEEE 29148:2011 standard provides a similar structure, but with some additional sections and subsections, such as:

  - Stakeholder requirements definition
  - System requirements specification
  - System requirements validation
  - Rationale and design information
  - Requirements traceability information
  - Requirements measurement information
  - Requirements analysis models
  - Requirements specification database

- The IEEE standards also provide several suggestions of how to organize functional requirements, such as by mode, user class, object, feature, stimulus, functional hierarchy, or combinations of these criteria. 
- The IEEE standards also provide several guidelines for writing good SRS, such as:

  - Use clear and consistent terminology
  - Avoid ambiguity and vagueness
  - Use natural language, diagrams, tables, and mathematical notation as appropriate
  - Specify requirements at an appropriate level of detail
  - Avoid specifying design or implementation details
  - Use shall, should, and may to indicate the level of obligation
  - Use must and must not to indicate absolute requirements
  - Use will and will not to indicate factual statements
  - Use active voice and present tense
  - Use bullet lists, numbering, and indentation for readability
  - Use cross-references and traceability links
  - Use a standard format and layout
  - Review and verify the SRS for completeness, consistency, correctness, and testability
