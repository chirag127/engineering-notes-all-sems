

# Software Engineering

Software engineering is the application of engineering principles and practices to the design, development, testing, and maintenance of software systems. Software engineering aims to produce high-quality software that meets the needs and expectations of the users, clients, and stakeholders, while also being cost-effective, reliable, secure, and maintainable.

Some of the main topics in software engineering are:

- Software development life cycle (SDLC): The process of planning, creating, testing, and deploying software. There are different models of SDLC, such as waterfall, agile, iterative, and spiral, each with its own advantages and disadvantages.
- Software requirements engineering: The process of eliciting, analyzing, specifying, validating, and managing the requirements of a software system. Requirements can be functional, non-functional, or quality attributes, and they can be expressed in natural language, diagrams, or formal methods.
- Software design: The process of defining the architecture, components, interfaces, and data structures of a software system. Software design can be done at different levels of abstraction, such as conceptual, logical, and physical. Software design can also follow different paradigms, such as object-oriented, structured, or functional.
- Software testing: The process of verifying and validating that a software system meets the specified requirements and performs as expected. Software testing can be done at different levels, such as unit, integration, system, and acceptance testing, and can use different techniques, such as black-box, white-box, or gray-box testing.
- Software maintenance: The process of modifying and improving a software system after its deployment. Software maintenance can be done for different reasons, such as correcting errors, enhancing functionality, adapting to changes, or improving performance. Software maintenance can be classified into corrective, adaptive, perfective, or preventive maintenance.
- Software quality: The degree to which a software system satisfies the requirements and expectations of the users, clients, and stakeholders. Software quality can be measured by different criteria, such as functionality, reliability, usability, efficiency, maintainability, and portability. Software quality can also be ensured by applying different standards, methods, and tools, such as ISO 9001, CMMI, or Six Sigma.

### Software Components

- Software components are reusable units of software that can be integrated into larger systems.
- Software components have well-defined interfaces that specify their inputs, outputs, and behaviors.
- Software components can be developed independently and deployed in different contexts and configurations.
- Software components can be composed to form complex software systems using component-based software engineering (CBSE) principles and techniques.
- Software components can be classified into different types, such as:
  - Functional components: provide specific functionalities or services, such as sorting, encryption, or authentication.
  - Data components: store, manipulate, or access data, such as databases, files, or caches.
  - User interface components: present information or interact with users, such as buttons, menus, or dialogs.
  - Middleware components: facilitate communication or coordination between other components, such as message brokers, web servers, or application servers.
  - Infrastructure components: support the execution or management of other components, such as operating systems, libraries, or frameworks.
- Software components can have different properties, such as:
  - Granularity: the size or complexity of a component, which can range from fine-grained (e.g., a single function) to coarse-grained (e.g., a subsystem).
  - Coupling: the degree of dependency or interaction between components, which can be low (e.g., loose coupling) or high (e.g., tight coupling).
  - Cohesion: the degree of relatedness or consistency within a component, which can be high (e.g., high cohesion) or low (e.g., low cohesion).
  - Reusability: the potential or ease of using a component in different contexts or systems, which can be high (e.g., generic components) or low (e.g., specific components).
  - Adaptability: the ability or flexibility of a component to adjust to different requirements or environments, which can be high (e.g., configurable components) or low (e.g., fixed components).
- Software components can have different benefits, such as:
  - Modularity: the separation of concerns or responsibilities into distinct units, which can improve the readability, maintainability, and testability of software.
  - Composability: the combination or integration of components to form larger systems, which can enable the reuse, customization, and evolution of software.
  - Interoperability: the compatibility or communication between components, which can facilitate the exchange, collaboration, and distribution of software.
  - Quality: the satisfaction or fulfillment of functional and non-functional requirements, such as correctness, reliability, performance, or security, which can be enhanced by using well-tested, verified, or certified components.
  - Productivity: the efficiency or effectiveness of software development, which can be increased by reducing the time, cost, or effort of creating, modifying, or deploying software.



### Software Characteristics

Software characteristics are the attributes or properties that describe the quality of a software product. They are also known as software quality factors or software quality attributes. They can be classified into two categories: internal and external.

- Internal characteristics are those that can be measured or evaluated by the software developers or testers, such as complexity, modularity, cohesion, coupling, etc. They affect the maintainability, testability, and reliability of the software.
- External characteristics are those that can be perceived or experienced by the software users or customers, such as functionality, usability, efficiency, portability, etc. They affect the satisfaction, productivity, and performance of the software.

Some of the common software characteristics are:

- Functionality: The degree to which the software meets the specified requirements and provides the desired functions. It includes aspects such as correctness, completeness, security, interoperability, etc.
- Reliability: The degree to which the software performs consistently and accurately under normal and abnormal conditions. It includes aspects such as fault tolerance, recoverability, availability, etc.
- Usability: The degree to which the software is easy to learn, use, and understand by the intended users. It includes aspects such as user interface, documentation, feedback, etc.
- Efficiency: The degree to which the software uses the available resources (such as memory, CPU, disk, network, etc.) optimally and effectively. It includes aspects such as response time, throughput, resource utilization, etc.
- Maintainability: The degree to which the software can be modified or corrected easily and cost-effectively. It includes aspects such as modularity, readability, complexity, cohesion, coupling, etc.
- Portability: The degree to which the software can be transferred or adapted to different environments (such as hardware, operating system, platform, etc.) without significant changes. It includes aspects such as compatibility, adaptability, installability, etc.

A mnemonic to remember these six characteristics is **FURPS**:

- Functionality
- Usability
- Reliability
- Performance
- Supportability

Supportability is a broader term that covers maintainability and portability. Performance is a synonym for efficiency.

### Software Development Life Cycle (SDLC) Models

Software Development Life Cycle (SDLC) Models are frameworks that describe the activities performed at each stage of a software development project. SDLC models help developers plan, design, implement, test, and maintain software systems.

There are different types of SDLC models, each with its own advantages, disadvantages, and suitability for different projects. Some of the most common SDLC models are:

- **Waterfall Model**: This is the oldest and simplest model, where the software development process is divided into sequential phases, such as requirements, design, implementation, testing, and deployment. Each phase must be completed before moving to the next one, and there is no going back to a previous phase. This model is easy to follow and manage, but it does not allow for changes or feedback during the development process, and it assumes that the requirements are clear and fixed from the start.
- **V-Shaped Model**: This is an extension of the waterfall model, where each phase is associated with a corresponding testing phase. For example, after the requirements phase, there is a validation phase, where the requirements are verified. Similarly, after the design phase, there is a verification phase, where the design is tested. This model ensures that the quality of the software is checked at each stage, but it still does not allow for changes or feedback during the development process, and it requires a lot of upfront planning and documentation.
- **Prototype Model**: This is a model where a prototype or a mock-up of the software is developed before the actual software. The prototype is used to demonstrate the functionality and features of the software to the stakeholders and get their feedback. Based on the feedback, the prototype is refined or discarded, and the process is repeated until a satisfactory prototype is achieved. Then, the actual software is developed based on the prototype. This model allows for changes and feedback during the development process, and it helps to reduce the risk of delivering a software that does not meet the expectations of the stakeholders. However, this model can be time-consuming and costly, and it may lead to confusion or inconsistency between the prototype and the final software.
- **Spiral Model**: This is a model that combines the iterative and prototype approaches. The software development process is divided into four quadrants: planning, risk analysis, engineering, and evaluation. Each quadrant represents one iteration or cycle of the development process, where a prototype or a part of the software is developed and tested. The process is repeated with increasing levels of detail and complexity until the final software is completed. This model allows for changes and feedback during the development process, and it helps to identify and mitigate the risks involved in the project. However, this model can be complex and difficult to manage, and it requires a lot of expertise and experience to apply it effectively.
- **Iterative Incremental Model**: This is a model where the software is developed and delivered in small and frequent increments or versions. Each increment adds some functionality or features to the software, and it is tested and reviewed before moving to the next one. This model allows for changes and feedback during the development process, and it helps to deliver a working software faster and more frequently. However, this model can be challenging to coordinate and integrate the different increments, and it may require more resources and testing than other models.

There are other SDLC models, such as agile, scrum, extreme programming, etc., that are based on the iterative incremental model, but with more emphasis on collaboration, communication, and flexibility.

Some mnemonics and learning tricks for the SDLC models are:

- To remember the phases of the waterfall model, use the acronym **DRIFT**: Design, Requirements, Implementation, Testing, and Deployment.
- To remember the phases of the V-shaped model, use the acronym **VIRV**: Validation, Implementation, Requirements, Verification, and add Design, Testing, and Deployment in between.
- To remember the quadrants of the spiral model, use the acronym **PREP**: Planning, Risk analysis, Engineering, and Evaluation.
- To remember the difference between prototype and spiral models, use the phrase **"Prototype before, spiral after"**: Prototype model develops a prototype before the actual software, while spiral model develops a prototype after each iteration.

### Prototype Model in SDLC

- The prototype model is a software development life cycle (SDLC) model in which a prototype is built, tested, and then reworked as necessary until an acceptable prototype is finally achieved from which the complete system or product can be developed.
- A prototype is a working model of a software or system that has some limited functionality or features, but enough to demonstrate the idea and get feedback from the customer.
- The prototype model is used when the customer is not clear about the requirements or expectations from the software or system, or when the requirements are complex or changing frequently.
- The prototype model has the following phases:
  - **Requirement Gathering and Analysis**: The customer and the developer discuss the objectives and scope of the software or system, and the developer gathers the basic requirements from the customer.
  - **Quick Design**: The developer creates a quick design of the software or system based on the requirements, and decides which features or functions to include in the prototype.
  - **Build Prototype**: The developer builds a prototype of the software or system using tools and techniques that are suitable for rapid prototyping, such as mockups, wireframes, or scripting languages.
  - **Customer Evaluation**: The customer evaluates the prototype and provides feedback to the developer, such as suggestions, changes, additions, or deletions of features or functions.
  - **Refining Prototype**: The developer modifies the prototype according to the customer feedback, and repeats the process of building, evaluating, and refining the prototype until the customer is satisfied with the prototype.
  - **Engineer Product**: The developer uses the final prototype as a basis for developing the complete software or system, using more robust and efficient tools and techniques, and following the standard SDLC phases of design, coding, testing, installation, and maintenance.

- The prototype model has the following advantages :
  - It reduces the risk of failure by involving the customer in the development process and ensuring that the software or system meets the customer needs and expectations.
  - It improves the quality of the software or system by allowing the developer to discover and fix errors or bugs in the early stages of development.
  - It enhances the communication and collaboration between the customer and the developer by providing a common platform for discussion and feedback.
  - It facilitates the incorporation of changes or new requirements by allowing the developer to modify the prototype easily and quickly.
  - It increases the customer satisfaction and confidence by delivering a working model of the software or system before the final product.

- The prototype model has the following disadvantages :
  - It may increase the cost and time of development by requiring the developer to build and refine multiple prototypes before the final product.
  - It may compromise the quality of the software or system by focusing more on the appearance and functionality of the prototype than on the performance and reliability of the final product.
  - It may create confusion or misunderstanding between the customer and the developer by blurring the distinction between the prototype and the final product, or by setting unrealistic expectations for the final product.
  - It may lead to incomplete or inadequate documentation of the software or system by neglecting the design and coding details of the prototype.

- A mnemonic to remember the phases of the prototype model is **Q-B-C-R-E-E**, which stands for **Q**uick Design, **B**uild Prototype, **C**ustomer Evaluation, **R**efining Prototype, **E**ngineer Product, and **E**xit Criteria. The exit criteria is the condition or standard that determines when the prototype is acceptable and ready for engineering the final product.
- An example of a software or system that can be developed using the prototype model is a mobile app that allows users to order food from different restaurants. The developer can build a prototype of the app that has some basic features, such as browsing menus, selecting items, and making payments, and get feedback from the potential users on the user interface, functionality, and usability of the app. The developer can then refine the prototype based on the feedback, and add more features, such as ratings, reviews, recommendations, and delivery tracking, until the users are satisfied with the prototype. The developer can then use the prototype as a blueprint for developing the complete app, using more advanced tools and techniques, and following the standard SDLC phases.

### Evolutionary Development Models in SDLC

- Evolutionary development models are a type of software development life cycle (SDLC) models that aim to deliver a working software product in multiple iterations, each with increasing functionality and quality.
- Evolutionary development models are suitable for projects that have unclear or changing requirements, need frequent feedback from customers or users, or involve complex or innovative technologies.
- Evolutionary development models can be classified into two types: exploratory and incremental.
  - Exploratory models, such as prototyping and throwaway prototyping, involve building a quick and simple version of the software product to elicit feedback from customers or users, and then discarding or refining it based on the feedback.
  - Incremental models, such as agile and spiral, involve building the software product in small and manageable units, each with a subset of the required features, and then integrating them into a complete system.
- Evolutionary development models have some advantages and disadvantages compared to other SDLC models, such as waterfall or V-model.
  - Advantages include:
    - Faster delivery of a working software product to customers or users, which can increase customer satisfaction and trust.
    - Ability to cope with changing or evolving requirements, which can reduce the risk of delivering a software product that does not meet the customer's needs or expectations.
    - Opportunity to learn from feedback and improve the software product quality and functionality in each iteration, which can enhance the software product value and performance.
    - Flexibility to adapt to new technologies or techniques, which can improve the software product innovation and competitiveness.
  - Disadvantages include:
    - Difficulty in estimating the cost, time, and resources required for the software project, which can affect the project management and planning.
    - Lack of a clear and stable vision of the software product, which can lead to confusion or inconsistency among the project stakeholders and developers.
    - Potential for introducing errors or defects in the software product, which can compromise the software product reliability and security.
    - Need for frequent communication and collaboration among the project stakeholders and developers, which can increase the project complexity and overhead.



### Iterative Enhancement Models in SDLC

- Iterative Enhancement Models are a type of software development life cycle (SDLC) models that focus on delivering a working system in small increments, each of which adds some functionality to the previous one.
- Each increment is treated as a sub-project and goes through all phases of the SDLC, such as planning, analysis, design, implementation, testing, and deployment.
- The first increment is usually a simplified version of the system that meets some basic requirements and provides a proof of concept. The subsequent increments add more features and complexity to the system until it is complete and satisfies all the requirements.
- Iterative Enhancement Models are also known as Incremental Models or Iterative and Incremental Models.

Some advantages of Iterative Enhancement Models are:

- They allow early feedback from the users and stakeholders, which can improve the quality and usability of the system.
- They reduce the risk of failure by delivering a working system in each increment, which can be tested and evaluated.
- They can accommodate changing requirements and new features more easily than other models, as each increment can be modified or extended without affecting the previous ones.
- They can deliver a system faster than other models, as the first increment can be deployed sooner and provide some value to the users.

Some disadvantages of Iterative Enhancement Models are:

- They require more planning and management than other models, as each increment has to be defined, scheduled, and coordinated.
- They may result in a system that is not well integrated or consistent, as each increment may have different design and implementation choices.
- They may increase the cost and effort of testing and maintenance, as each increment has to be tested and integrated with the previous ones, and any defects or changes have to be propagated to all the increments.
- They may not be suitable for complex or large-scale systems, as the number of increments may be too high or the dependencies among them may be too complex.

A mnemonic to remember the Iterative Enhancement Models is:

**I**ncremental **E**nhancement **M**odels **S**tart **S**imple and **A**dd **F**eatures

Some examples of Iterative Enhancement Models are:

- The Spiral Model, which combines the iterative approach with risk analysis and prototyping.
- The Agile Model, which emphasizes collaboration, communication, and adaptation in the iterative process.
- The Rational Unified Process (RUP), which defines four phases (inception, elaboration, construction, and transition) and six disciplines (business modeling, requirements, analysis and design, implementation, testing, and deployment) for the iterative process.



## Unit 2 - Software Requirement Specifications (SRS)

- A software requirement specification (SRS) is a document that describes the software system to be developed, its purpose, environment, functionality, and performance  .
- The SRS is a communication tool between the stakeholders (business, users, developers, testers, etc.) and the developers, and it helps to reduce ambiguity, conflicts, and errors in the software development process .
- The SRS should be clear, concise, consistent, complete, correct, traceable, verifiable, modifiable, and prioritized.
- The SRS should follow a standard format and structure, such as the IEEE 830-1998 standard, which consists of the following sections:
  - Introduction: This section provides an overview of the SRS, its scope, objectives, definitions, acronyms, references, and assumptions.
  - Overall description: This section describes the general factors that affect the software system, such as the product perspective, product functions, user characteristics, constraints, assumptions, and dependencies.
  - Specific requirements: This section details the specific requirements of the software system, such as the functional requirements, non-functional requirements, external interface requirements, performance requirements, design constraints, quality attributes, and validation criteria.
  - Appendices: This section contains any additional information that is relevant to the SRS, such as data models, flowcharts, diagrams, tables, etc.
- The SRS should be reviewed and validated by the stakeholders and the developers to ensure that it meets the needs and expectations of the software system.
- The SRS should be updated and maintained throughout the software development life cycle to reflect any changes or modifications in the software system.

- A mnemonic to remember the characteristics of a good SRS is **C4TV MAP**:
  - **C**lear: The SRS should be unambiguous and understandable by all the stakeholders and the developers.
  - **C**oncise: The SRS should be brief and to the point, avoiding unnecessary details or repetitions.
  - **C**onsistent: The SRS should be coherent and compatible with other documents and standards, avoiding contradictions or conflicts.
  - **C**omplete: The SRS should cover all the aspects and features of the software system, leaving no gaps or questions.
  - **T**raceable: The SRS should be linked to the source of the requirements, such as the business needs, user needs, or regulations, and be able to track the changes and impacts of the requirements throughout the software development life cycle.
  - **V**erifiable: The SRS should be testable and measurable, using specific and objective criteria to determine whether the software system meets the requirements or not.
  - **M**odifiable: The SRS should be flexible and adaptable, allowing for easy and controlled changes or updates of the requirements as needed.
  - **A**ppropriate: The SRS should be relevant and suitable for the software system, addressing the real problems and needs of the stakeholders and the users.
  - **P**rioritized: The SRS should rank the requirements according to their importance, urgency, or dependency, and allocate the resources and time accordingly.

### Analysis in Requirement Engineering Process in SRS

- Software Requirements Specification (SRS) is a document that describes the intended purpose, environment, functionality, and performance of a software system.
- SRS is a part of the requirement engineering process, which is the process of eliciting, analyzing, validating, and managing the software requirements.
- Analysis is the second phase of the requirement engineering process, after elicitation. In this phase, the requirements are examined, structured, prioritized, and modeled to ensure that they are clear, consistent, complete, and feasible.
- Analysis involves the following activities:
  - **Requirement classification**: The requirements are categorized into functional and non-functional requirements, and also into user, system, and domain requirements. Functional requirements specify what the system should do, while non-functional requirements specify how the system should do it. User requirements are the needs and expectations of the end-users, system requirements are the technical specifications of the system, and domain requirements are the constraints and assumptions of the application domain.
  - **Requirement organization**: The requirements are grouped into coherent and manageable units, such as features, modules, components, or use cases. This helps to reduce complexity and redundancy, and to facilitate communication and verification. Requirement organization can be done using various techniques, such as hierarchical decomposition, partitioning, or clustering.
  - **Requirement prioritization**: The requirements are ranked according to their importance, urgency, and dependency. This helps to identify the critical and optional requirements, and to resolve conflicts and trade-offs. Requirement prioritization can be done using various techniques, such as MoSCoW, value-based, or cost-benefit analysis.
  - **Requirement modeling**: The requirements are represented using graphical or textual notations, such as diagrams, tables, or natural language. This helps to visualize, understand, and validate the requirements, and to identify gaps and inconsistencies. Requirement modeling can be done using various techniques, such as use case diagrams, data flow diagrams, entity-relationship diagrams, or state transition diagrams.

- A mnemonic to remember the four activities of analysis is **COPM** (Classification, Organization, Prioritization, Modeling).
- An example of a requirement analysis technique is the **Volere** template, which is a structured and comprehensive template for writing SRS documents. The template consists of 31 sections, covering various aspects of the software requirements, such as project drivers, stakeholders, scope, functional and non-functional requirements, data requirements, quality scenarios, etc. The template also provides guidelines, examples, and checklists for each section.

### Data Flow Diagrams in Software Requirement Specification (SRS)

- Data Flow Diagrams (DFDs) are a graphical representation of the information flows within a system. They show how data is input, processed, stored, and output by the system components.  
- DFDs are useful for capturing the functional requirements of a system, as well as for validating and verifying the system design. They can also help in identifying potential errors, inconsistencies, and redundancies in the system.  
- DFDs are composed of four basic symbols: processes, data flows, data stores, and external entities. Processes are the activities or functions that transform data from one form to another. Data flows are the arrows that show the direction and content of data movement. Data stores are the places where data is stored temporarily or permanently. External entities are the sources or destinations of data outside the system boundary. 
- DFDs can be drawn at different levels of abstraction, depending on the level of detail required. The most common levels are: 0-level DFD, 1-level DFD, and 2-level DFD. 
- 0-level DFD, also known as context diagram, shows the entire system as a single process with input and output data flows to and from external entities. It provides an overview of the system scope and boundaries. 
- 1-level DFD, also known as top-level diagram, shows the main processes and data flows within the system, as well as the external entities that interact with the system. It provides a high-level view of the system functionality and structure. 
- 2-level DFD, also known as lower-level diagram, shows the sub-processes and data flows within each main process of the system. It provides a detailed view of the system logic and data manipulation. 
- DFDs follow some basic rules and conventions, such as: each process should have at least one input and one output data flow, each data flow should have a unique name and a clear description, each data store should have a unique name and a clear description, each external entity should have a unique name and a clear description, data flows should not cross each other, processes should not have direct data flows to external entities, etc. 
- DFDs can be complemented by other diagrams and documents, such as Entity Relationship Diagrams (ERDs), which show the data structure and relationships of the system, and Software Requirement Specification (SRS), which describe the system requirements in a structured and formal way.   
- A possible mnemonic to remember the four basic symbols of DFDs is: PADDLE. P for Process, A for Arrow (Data Flow), D for Data Store, L for Line (System Boundary), and E for External Entity.

### Entity Relationship Diagrams in Software Requirement Specification (SRS)

- Entity Relationship Diagrams (ERDs) are a data modeling method used in software engineering to produce a conceptual data model of an information system.
- ERDs show the entities (objects or concepts) that are relevant to the system and the relationships (associations or dependencies) among them.
- ERDs can be used to document the data requirements of a system, such as the attributes (properties or characteristics) of each entity, the cardinality (number of occurrences) of each relationship, and the constraints (rules or restrictions) that apply to the data.
- ERDs can also be used to design the database schema (structure or format) of the system, such as the tables, columns, keys, and indexes that store the data.
- ERDs can be represented using different notations, such as Chen notation, Crow's Foot notation, or UML notation. Each notation has its own symbols and conventions for depicting the entities, relationships, attributes, and cardinalities.
- ERDs can be divided into three levels of abstraction: conceptual, logical, and physical. The conceptual level shows the high-level view of the data and its meaning, the logical level shows the detailed view of the data and its structure, and the physical level shows the implementation view of the data and its storage.
- ERDs can be used in conjunction with other diagrammatic notations, such as Data Flow Diagrams (DFDs) and SADT diagrams, to explain the lower-level relationships and dataflow for components in the system .
- ERDs can help to improve the quality and consistency of the software requirement specification (SRS) by providing a clear and precise description of the data and its semantics, facilitating the communication and validation of the requirements among the stakeholders, and enabling the verification and testing of the system .

### Decision Tables in Software Requirement Specification (SRS)

- A decision table is a tabular representation of the logic and conditions of a software system. It is used to specify the behavior and outcomes of the system based on different combinations of inputs and rules.
- A decision table consists of four parts: condition stubs, action stubs, condition entries, and action entries. Condition stubs are the names of the input variables or parameters that affect the system's behavior. Action stubs are the names of the output variables or actions that the system performs. Condition entries are the possible values or states of the condition stubs. Action entries are the possible values or states of the action stubs.
- A decision table can be represented in two formats: limited entry and extended entry. In a limited entry format, each condition entry and action entry can only have two values: Y (yes) or N (no). In an extended entry format, each condition entry and action entry can have more than two values, such as numbers, text, or symbols.
- A decision table can be used to document the functional requirements of a software system in a clear and concise way. It can also be used to verify the completeness and consistency of the requirements, as well as to identify and eliminate any conflicts or redundancies. A decision table can also be used to generate test cases and scenarios for the software system.
- A decision table can have some advantages and disadvantages compared to other methods of specifying software requirements. Some of the advantages are:

  - It can handle complex and multiple conditions and actions in a systematic and organized way.
  - It can reduce the ambiguity and misunderstanding of the requirements by using a standard and uniform notation.
  - It can facilitate the communication and collaboration among the stakeholders, such as the developers, testers, and users of the software system.
  - It can improve the quality and reliability of the software system by ensuring the accuracy and completeness of the requirements.

- Some of the disadvantages are:

  - It can become large and cumbersome if there are too many condition stubs and action stubs, or if there are too many possible combinations of condition entries and action entries.
  - It can be difficult to maintain and update if the requirements change frequently or if new requirements are added.
  - It can be challenging to convert a decision table into a natural language or a graphical representation, such as a flowchart or a state diagram.

- An example of a decision table for a software system that calculates the discount and total price of a product based on the customer type and the quantity purchased is shown below:

| Condition Stubs | Condition Entries | Action Stubs | Action Entries |
| --------------- | ----------------- | ------------ | -------------- |
| Customer Type   | Regular (R)       | Discount (%) | 0              |
|                 | Premium (P)       |              | 10             |
| Quantity        | < 10              | Total Price  | Price * Quantity * (1 - Discount/100) |
|                 | >= 10             |              | Price * Quantity * (1 - Discount/100) - 5 |

- The decision table can be read as follows:

  - If the customer type is regular and the quantity is less than 10, then the discount is 0% and the total price is the product of the price and the quantity.
  - If the customer type is regular and the quantity is greater than or equal to 10, then the discount is 0% and the total price is the product of the price and the quantity minus 5.
  - If the customer type is premium and the quantity is less than 10, then the discount is 10% and the total price is the product of the price and the quantity multiplied by 0.9.
  - If the customer type is premium and the quantity is greater than or equal to 10, then the discount is 10% and the total price is the product of the price and the quantity multiplied by 0.9 minus 5.

### Verification and Validation in SRS

- Verification and validation (V&V) are two activities that ensure the quality and correctness of the software requirements specification (SRS) document.
- Verification is the process of checking whether the SRS conforms to the standards, guidelines, and specifications that are defined for it. It answers the question: "Are we building the product right?"
- Validation is the process of checking whether the SRS meets the needs and expectations of the stakeholders. It answers the question: "Are we building the right product?"

  - Completeness checks: To ensure that the SRS covers all the functional and non-functional requirements and does not omit any essential information.

  - Validity checks: To ensure that the SRS is aligned with the actual needs and expectations of the stakeholders and the intended users of the system.
  - Realism checks: To ensure that the SRS is feasible and achievable within the given constraints and resources.
  - Ambiguity checks: To ensure that the SRS is clear and unambiguous and does not leave any room for interpretation or misunderstanding.
  - Verifiability checks: To ensure that the SRS is testable and measurable and that every requirement can be verified by some method or procedure  .

### Basic Concept of Software Design

- Software design is the process of defining the architecture, components, interfaces, and other characteristics of a software system before its implementation.
- Software design can be seen as a problem-solving activity that involves applying principles, concepts, and techniques to transform a set of requirements into a software solution.
- Software design can be divided into two levels: high-level design and low-level design.
  - High-level design focuses on the overall structure and behavior of the software system, such as the modules, subsystems, interactions, and interfaces.
  - Low-level design focuses on the detailed implementation of each module or component, such as the algorithms, data structures, and programming languages.
- Software design can be influenced by various factors, such as the requirements, the domain, the stakeholders, the quality attributes, the constraints, and the trade-offs.
- Software design can be evaluated by various criteria, such as the functionality, the reliability, the usability, the efficiency, the maintainability, the reusability, the portability, and the scalability of the software system.
- Software design can be documented by various artifacts, such as the design models, the design diagrams, the design specifications, and the design patterns.
- Software design can be improved by various practices, such as the design reviews, the design testing, the design refactoring, and the design patterns.



### Architectural Design in Software Design

- Architectural design is the process of defining the high-level structure and behavior of a software system, as well as the principles and guidelines for its development and evolution.
- Architectural design involves identifying the main components of the system, their interfaces, interactions, dependencies, and constraints, as well as the non-functional requirements and quality attributes that the system must satisfy.
- Architectural design is important for software design because it provides a blueprint for the system, facilitates communication and collaboration among stakeholders, enables reuse and integration of existing components, and guides the implementation, testing, deployment, and maintenance of the system.
- Architectural design can be performed using different methods and models, such as:
  - Architectural styles: These are general patterns or paradigms for organizing the components and connectors of a system, such as client-server, peer-to-peer, layered, pipe-and-filter, etc. Each style has its own advantages, disadvantages, and suitability for different types of systems and domains.
  - Architectural views: These are different perspectives or abstractions of the system, such as logical, physical, process, development, etc. Each view focuses on a specific set of concerns or aspects of the system, such as functionality, performance, security, modularity, etc. Different views can be represented using different notations or languages, such as UML, SysML, etc.
  - Architectural patterns: These are reusable solutions or templates for addressing common or recurring problems or challenges in architectural design, such as broker, MVC, microservices, etc. Each pattern describes the problem, the context, the solution, the consequences, and the variants of applying the pattern.
  - Architectural frameworks: These are collections or sets of predefined components, connectors, rules, and guidelines for developing a specific type of system, such as enterprise, web, mobile, etc. Each framework provides a standard or common way of structuring, configuring, and deploying the system, as well as a set of tools and libraries for supporting the development process.
  - Architectural tactics: These are specific techniques or strategies for achieving or improving a certain quality attribute or non-functional requirement of the system, such as availability, scalability, security, etc. Each tactic involves making certain design decisions or trade-offs, such as replication, caching, encryption, etc.
  - Architectural evaluation: This is the process of assessing or measuring the quality or suitability of the architectural design of a system, based on a set of criteria or metrics, such as functionality, performance, reliability, usability, etc. Architectural evaluation can be performed using different methods or techniques, such as reviews, inspections, analysis, testing, simulation, etc.

### Low Level Design in Software Design

- Low level design is an important and challenging phase of software design, as it requires a lot of technical knowledge, skills, and creativity. #### Modularization in Software Design

- Modularization is the process of dividing a software system into smaller, independent, and cohesive modules that can be developed, tested, and maintained separately.
- Modularization aims to achieve high cohesion and low coupling among modules, which means that each module should have a clear and specific purpose, and the interactions and dependencies between modules should be minimal and well-defined.
- Modularization has several benefits for software design, such as:
  - It improves readability and understandability of the code, as each module can be studied and modified in isolation.
  - It enhances reusability and maintainability of the code, as modules can be reused in different contexts and updated without affecting other modules.
  - It facilitates parallel development and testing, as modules can be developed and tested by different teams or individuals concurrently.
  - It reduces complexity and increases reliability, as modules can be verified and validated independently, and errors can be localized and isolated more easily.
- Modularization can be achieved at different levels of abstraction, such as:
  - Functional modularization, which is based on the decomposition of the system into functions or procedures that perform specific tasks or operations.
  - Data modularization, which is based on the encapsulation of data and the operations that manipulate them into data structures or objects.
  - Control modularization, which is based on the separation of the control flow and the logic of the system into modules that handle different events or scenarios.
  - Interface modularization, which is based on the definition of clear and consistent interfaces between modules that specify the inputs, outputs, and behaviors of each module.
- Modularization can be implemented using different techniques and tools, such as:
  - Programming languages, which provide syntactic and semantic features to support modularization, such as subroutines, functions, classes, modules, packages, namespaces, etc.
  - Design patterns, which provide reusable solutions to common modularization problems, such as abstraction, inheritance, polymorphism, composition, delegation, etc.
  - Software architectures, which provide high-level frameworks and guidelines to organize and structure the modules of a system, such as layered, client-server, peer-to-peer, microservices, etc.
  - Software development methodologies, which provide processes and practices to manage and coordinate the modularization of a system, such as agile, waterfall, spiral, etc.



#### Design Structure Charts in Software Design

- A design structure chart (DSC) is a diagram that shows the hierarchical decomposition of a software system into its modules and submodules.
- A DSC is used to represent the structure and organization of a software system, as well as the data flow and control flow between the modules.
- A DSC is a useful tool for structured design, which is a method of software design that follows a top-down approach, starting from the main function of the system and breaking it down into smaller and simpler subfunctions.
- A DSC consists of the following elements:
  - Modules: Rectangular boxes that represent the functions or procedures of the system. Each module has a unique name and a number that indicates its level in the hierarchy. The main module is numbered 0, and the submodules are numbered 1, 2, 3, etc. according to their depth in the tree.
  - Connectors: Lines that connect the modules and show the direction of data flow and control flow. The connectors can have different types, such as:
    - Call: A solid line with an arrowhead that indicates a module calls another module as a subroutine.
    - Jump: A dashed line with an arrowhead that indicates a module jumps to another module without returning.
    - Return: A solid line with a circle that indicates a module returns to the calling module after completing its task.
    - Data: A solid line with a diamond that indicates a module passes data to another module as a parameter or a return value.
    - Flag: A solid line with a triangle that indicates a module passes a boolean value to another module as a condition or a status.
  - Coupling: The degree of interdependence between the modules. The coupling can be measured by the number and type of connectors between the modules. The lower the coupling, the better the modularity and maintainability of the system.
  - Cohesion: The degree of relatedness of the tasks performed by a module. The cohesion can be measured by the number and type of inputs and outputs of a module. The higher the cohesion, the better the clarity and efficiency of the system.

- A DSC can be drawn using the following steps:
  - Identify the main function of the system and draw it as the root module of the DSC.
  - Identify the subfunctions of the main function and draw them as the child modules of the root module. Connect them with the appropriate connectors.
  - Repeat the process for each subfunction until the lowest level of detail is reached.
  - Check the coupling and cohesion of the modules and refine the DSC if necessary.

- A DSC can be used for the following purposes:
  - To document the design of a software system and communicate it to the developers and stakeholders.
  - To verify the completeness and correctness of the design and identify any errors or inconsistencies.
  - To facilitate the implementation and testing of the software system by providing a clear and modular structure.
  - To support the maintenance and modification of the software system by allowing easy identification and isolation of the affected modules.

#### Pseudo Codes in Software Design

- Pseudo code is a way of writing the steps of an algorithm or a program in a simplified and informal language that is close to natural language but does not follow the syntax or rules of a specific programming language.
- Pseudo code is used to design and communicate the logic and structure of a program before writing the actual code. It can also be used to document and explain an existing code.
- Pseudo code is not meant to be executed by a computer, but to be read and understood by humans. Therefore, there is no standard or fixed way of writing pseudo code, and different programmers may use different styles and conventions.
- However, some general guidelines for writing good pseudo code are:
  - Use clear and consistent names for variables, functions, and data structures.
  - Use indentation and white space to show the hierarchy and flow of control in the program.
  - Use keywords such as IF, THEN, ELSE, WHILE, FOR, REPEAT, UNTIL, etc. to indicate the conditional and looping statements.
  - Use comments to explain the purpose and functionality of the pseudo code.
  - Use mathematical symbols and operators to express arithmetic and logical operations.
  - Use pseudocode to describe the main steps of the algorithm or program, and avoid unnecessary details or implementation-specific issues.
- An example of pseudo code for finding the maximum element in an array of numbers is:

```
// Define a function to find the maximum element in an array
FUNCTION MAXIMUM(ARRAY)
  // Initialize the maximum element to the first element of the array
  MAX_ELEMENT = ARRAY[0]
  // Loop through the rest of the array elements
  FOR EACH ELEMENT IN ARRAY
    // Compare the current element with the maximum element
    IF ELEMENT > MAX_ELEMENT THEN
      // Update the maximum element if the current element is larger
      MAX_ELEMENT = ELEMENT
    END IF
  END FOR
  // Return the maximum element as the output of the function
  RETURN MAX_ELEMENT
END FUNCTION
```

#### Coupling in Software Design

- Coupling is the degree of interdependence between software modules; a measure of how closely connected two routines or modules are; the strength of the relationships between modules.
- Coupling is usually contrasted with cohesion, which is the degree of intra-dependence within a module; a measure of how well the elements of a module belong together.
- Low coupling often correlates with high cohesion, and vice versa. Low coupling means that modules are independent and changes in one module have little impact on other modules. High cohesion means that modules are focused and have a single responsibility.
- Coupling is an important factor in software design, as it affects the quality, maintainability, reusability, and modularity of the software. High coupling increases the complexity and reduces the readability of the code, making it more prone to errors and harder to debug and test.
- There are different types of coupling, depending on the nature and degree of the dependencies between modules. Some common types of coupling are:
  - Common coupling: when modules share global data or variables. This is the weakest form of coupling, as it allows modules to communicate without passing parameters. However, it also introduces the risk of data inconsistency and unintended side effects.
  - Data coupling: when modules exchange data through parameters. This is a better form of coupling than common coupling, as it reduces the dependency on global data and makes the modules more reusable. However, it still requires the modules to know the details of the data structure and format.
  - Control coupling: when modules pass control information or flags through parameters. This is a stronger form of coupling than data coupling, as it implies that the modules are dependent on the logic and flow of control of each other. This reduces the flexibility and modularity of the modules.
  - Stamp coupling: when modules pass complex data structures or objects through parameters. This is a stronger form of coupling than control coupling, as it requires the modules to know the internal representation and implementation of the data structures or objects. This increases the coupling between the modules and the data, making it harder to change or modify them.
  - Content coupling: when modules directly access or modify the data or code of other modules. This is the strongest form of coupling, as it implies that the modules are tightly intertwined and have no clear boundaries. This makes the modules highly dependent and non-reusable, and violates the principle of encapsulation.
- A mnemonic to remember the types of coupling from weakest to strongest is: **C**an **D**ogs **C**hase **S**quirrels **C**arefully?
- A simple example of coupling in software design is a calculator program that consists of two modules: a user interface module and a calculation module. The user interface module takes the input from the user and displays the output, while the calculation module performs the arithmetic operations. The coupling between these modules can be measured by the number and type of parameters they exchange, and the degree of dependency they have on each other's logic and data. Ideally, the coupling should be low, so that the modules can be easily modified, tested, and reused.



#### Cohesion Measures in Software Design

- Cohesion is a measure of how strongly related and focused the various responsibilities of a software module are.
- A software module can be a function, a class, a package, or a subsystem.
- Cohesion is an ordinal type of measurement and is usually described as “high cohesion” or “low cohesion”.
- Modules with high cohesion tend to be preferable, because high cohesion is associated with several desirable traits of software including robustness, reliability, reusability, and understandability.
- In contrast, low cohesion is associated with undesirable traits such as being difficult to maintain, test, reuse, or even understand.
- Cohesion is often contrasted with coupling, which is a measure of how interdependent two or more software modules are.
- Low coupling and high cohesion are generally considered as the main principles of good software design.

There are different types of cohesion, depending on the degree of functional relatedness of the elements within a module. They are listed below in the order of increasing cohesion:

- **Coincidental cohesion**: The elements within a module have no apparent relationship to each other. This is the lowest level of cohesion and should be avoided. For example, a module that performs file operations, mathematical calculations, and string manipulations has coincidental cohesion.
- **Logical cohesion**: The elements within a module are logically related and perform similar functions, but they are not part of a single problem domain. For example, a module that performs different types of sorting algorithms has logical cohesion.
- **Temporal cohesion**: The elements within a module are related by the fact that they are executed at the same time or in a specific sequence. For example, a module that performs initialization, input, and output operations has temporal cohesion.
- **Procedural cohesion**: The elements within a module are related by the fact that they contribute to a specific task or subtask. For example, a module that performs the steps of a login process has procedural cohesion.
- **Communicational cohesion**: The elements within a module are related by the fact that they operate on the same data or input/output. For example, a module that performs different operations on the same database table has communicational cohesion.
- **Sequential cohesion**: The elements within a module are related by the fact that the output of one element is the input of another element. For example, a module that performs encryption, compression, and transmission of data has sequential cohesion.
- **Functional cohesion**: The elements within a module are related by the fact that they all contribute to a single well-defined function or problem domain. This is the highest level of cohesion and should be aimed for. For example, a module that calculates the area of a circle has functional cohesion.

A possible mnemonic to remember the types of cohesion is: **CLoT ProCoSeFu** (Coincidental, Logical, Temporal, Procedural, Communicational, Sequential, Functional).

Some advantages of high cohesion are:

- It improves the readability and understandability of the code.
- It reduces the complexity and size of the modules.
- It increases the reusability and maintainability of the modules.
- It facilitates the testing and debugging of the modules.
- It enhances the modularity and flexibility of the software design.

Some disadvantages of low cohesion are:

- It decreases the readability and understandability of the code.
- It increases the complexity and size of the modules.
- It reduces the reusability and maintainability of the modules.
- It complicates the testing and debugging of the modules.
- It degrades the modularity and flexibility of the software design.



### Design Strategies in Software Design

- Design strategies are the approaches that are taken to design a software system that meets the requirements and specifications of the problem domain.
- Design strategies help to outline the product's architecture, interfaces, data, and modules in a systematic and coherent way.
- Design strategies also help to improve the quality, maintainability, reusability, and scalability of the software system.
- There are three major types of design strategies in software engineering: structured design, function-oriented design, and object-oriented design.

#### Structured Design
- Structured design is a design strategy that focuses on the decomposition of the software system into smaller, independent, and well-defined modules that communicate with each other through well-defined interfaces.
- Structured design follows the top-down design approach, which starts with a high-level view of the system and gradually breaks it down into lower-level components.
- Structured design is based on the principle of information hiding, which means that each module should hide its internal details and expose only the necessary information to other modules.
- Structured design is suitable for simple and linear software systems that have clear and stable requirements and specifications.
- Structured design has some limitations, such as:
  - It does not support the concepts of inheritance, polymorphism, and encapsulation, which are essential for modeling complex and dynamic software systems.
  - It does not handle the changes in the requirements and specifications well, as it requires modifying the entire system structure and interfaces.
  - It does not facilitate the reuse of existing modules, as they are tightly coupled with the system structure and interfaces.

#### Function-Oriented Design
- Function-oriented design is a design strategy that focuses on the identification and organization of the software system's functions and data.
- Function-oriented design follows the bottom-up design approach, which starts with the identification of the basic functions and data of the system and gradually combines them into higher-level functions and data structures.
- Function-oriented design is based on the principle of functional abstraction, which means that each function should perform a single and well-defined task and hide the details of how it is implemented.
- Function-oriented design is suitable for software systems that have complex and dynamic functions and data, and that require high performance and efficiency.
- Function-oriented design has some limitations, such as:
  - It does not support the concepts of classes, objects, and methods, which are essential for modeling the real-world entities and behaviors of the software system.
  - It does not handle the changes in the functions and data well, as it requires modifying the existing functions and data structures.
  - It does not facilitate the reuse of existing functions and data, as they are not modular and independent.

#### Object-Oriented Design
- Object-oriented design is a design strategy that focuses on the identification and organization of the software system's classes, objects, and methods.
- Object-oriented design follows the iterative and incremental design approach, which starts with the identification of the most important classes, objects, and methods of the system and gradually refines and extends them.
- Object-oriented design is based on the principle of object abstraction, which means that each class should represent a real-world entity or concept and hide the details of how it is implemented.
- Object-oriented design supports the concepts of inheritance, polymorphism, and encapsulation, which are essential for modeling complex and dynamic software systems.
- Object-oriented design is suitable for software systems that have complex and dynamic requirements and specifications, and that require high modularity, reusability, and scalability.
- Object-oriented design has some limitations, such as:
  - It requires more analysis and design effort, as it involves identifying and defining the classes, objects, and methods of the system.
  - It requires more testing and debugging effort, as it involves testing and debugging the interactions and behaviors of the classes, objects, and methods of the system.
  - It requires more memory and processing power, as it involves creating and managing the instances of the classes and objects of the system.

#### Mnemonics and Learning Tricks
- A possible mnemonic to remember the three types of design strategies is **SFO** (Structured, Function-oriented, Object-oriented).
- A possible learning trick to remember the differences between the three types of design strategies is to use the analogy of building a house:
  - Structured design is like building a house by dividing it into rooms and connecting them with doors and windows. Each room has a specific purpose and hides its internal details from other rooms. This works well for simple and linear houses, but not for complex and dynamic ones.
  - Function-oriented design is like building a house by identifying and organizing the functions and data that are needed in the house.



#### Function Oriented Design in Software Design

- Function Oriented Design (FOD) is a method to software design where the model is decomposed into a set of interacting units or modules where each unit or module has a clearly defined function .
- FOD is based on the idea of top-down design, where the system is first described at a high level of abstraction, and then refined into lower levels of details .
- FOD follows a generic procedure:
  - Start with a high level description of what the software/program does.
  - Identify the main functions or processes that the software/program performs.
  - Draw a data flow diagram (DFD) to show the flow of information between the functions or processes.
  - Define the data items used in the DFD using a data dictionary.
  - Refine the DFD into more detailed levels until the functions or processes are simple enough to be implemented as modules or subroutines.
  - Assign a structure chart to show the hierarchical relationship and control flow between the modules or subroutines.
- FOD uses some design notations :
  - Data Flow Diagram (DFD): A graphical representation of the flow of data through a system. It shows the sources and destinations of data, the processes that transform data, and the data stores that hold data. A DFD can have multiple levels of details, where each level shows more specific information about the system.
  - Data Dictionary: A repository of information about the data items used in the DFD. It defines the name, type, format, range, and description of each data item. It also shows the relationships and constraints among the data items.
  - Structure Chart: A graphical representation of the modular structure of a system. It shows the modules or subroutines that make up the system, and the control flow and data flow between them. A structure chart can have multiple levels of details, where each level shows more specific information about the modules or subroutines.
- FOD has some advantages :
  - It is easy to understand and communicate, as it uses graphical notations and natural language descriptions.
  - It supports top-down design and modularization, which can improve the clarity, maintainability, and reusability of the software.
  - It focuses on the functionality and behavior of the system, rather than the implementation details or data structures.
- FOD has some disadvantages :
  - It does not capture the dynamic aspects of the system, such as concurrency, synchronization, or exception handling.
  - It does not address the non-functional requirements of the system, such as performance, security, or reliability.
  - It may not be suitable for complex or object-oriented systems, where the data and the functions are tightly coupled and encapsulated.
- FOD is an example of a structured design method, which was popular in the 1970s and 1980s. It is still used for some types of software, such as batch processing, data processing, or scientific computing .
- FOD can be contrasted with other design methods, such as Object Oriented Design (OOD), which is based on the idea of bottom-up design, where the system is composed of a set of interacting objects that have both data and behavior .



#### Object Oriented Design in Software Design

- Object Oriented Design (OOD) is the process of planning a system of interacting objects for the purpose of solving a software problem.
- An object is an entity that contains data (attributes) and procedures (methods) that operate on the data.
- OOD is based on the principles of abstraction, encapsulation, inheritance, and polymorphism.
- Abstraction is the process of hiding the details and complexity of a system and exposing only the essential features and functionality.
- Encapsulation is the process of bundling the data and methods of an object together and restricting access to them from outside the object.
- Inheritance is the process of creating new classes (subclasses) from existing classes (superclasses) and inheriting their attributes and methods.
- Polymorphism is the ability of an object to take different forms and behave differently depending on the context or input.
- OOD aims to achieve the following benefits:
  - Modularity: The system is divided into smaller and independent units (modules) that can be developed, tested, and maintained separately.
  - Reusability: The modules can be reused in different systems or contexts, reducing the need to write new code.
  - Extensibility: The system can be easily extended by adding new modules or modifying existing ones without affecting the rest of the system.
  - Maintainability: The system can be easily modified or updated to meet changing requirements or fix errors.
  - Reliability: The system is less prone to errors and failures as the modules are well-defined and isolated from each other.
- OOD follows some design principles and patterns to achieve these benefits. Some of the most common ones are:
  - SOLID: A set of five principles that guide the design of cohesive, loosely coupled, and easily maintainable modules. SOLID stands for:
    - Single-responsibility Principle: A module should have only one reason to change and only one responsibility.
    - Open-closed Principle: A module should be open for extension but closed for modification.
    - Liskov Substitution Principle: A subclass should be substitutable for its superclass without breaking the system.
    - Interface Segregation Principle: A module should depend on the smallest possible interface that provides the required functionality.
    - Dependency Inversion Principle: A module should depend on abstractions rather than concretions.
  - GRASP: A set of nine principles that assign responsibilities to modules and define the relationships among them. GRASP stands for:
    - Creator: A module should be responsible for creating objects that it is closely related to.
    - Information Expert: A module should be responsible for the information and actions related to that information.
    - Low Coupling: A module should have minimal dependencies on other modules.
    - High Cohesion: A module should have a single, well-defined purpose.
    - Controller: A module should be responsible for handling user requests and delegating them to other modules.
    - Indirection: A module should mediate between two or more modules to reduce coupling and increase flexibility.
    - Polymorphism: A module should use polymorphism to handle variations in behavior based on the type of object.
    - Protected Variations: A module should protect itself from the variations and changes in other modules by using abstractions.
    - Pure Fabrication: A module should be created to fulfill a single responsibility that does not belong to any other module.
  - Design Patterns: A set of reusable solutions to common design problems that can be applied in different contexts and domains. Some of the most common ones are:
    - Creational Patterns: These patterns deal with the creation and initialization of objects, such as Factory, Singleton, Builder, Prototype, etc.
    - Structural Patterns: These patterns deal with the composition and arrangement of objects, such as Adapter, Bridge, Composite, Decorator, Facade, etc.
    - Behavioral Patterns: These patterns deal with the interaction and communication of objects, such as Observer, Strategy, Command, Iterator, Mediator, etc.

- A possible mnemonic to remember the SOLID principles is: **S**ome **O**bjects **L**ike **I**ce-cream **



#### Top-Down and Bottom-Up Design in Software Engineering

- Top-down and bottom-up design are two complementary approaches to software development.
- Top-down design starts with a high-level overview of the system and decomposes it into smaller and more specific components. Bottom-up design starts with the most basic and low-level components and builds them up into higher-level components or modules.
- Both approaches have advantages and disadvantages, and they can be combined in various ways to suit different types of problems and requirements.

##### Top-Down Design

- Top-down design is more suitable when the software solution needs to be designed from scratch and specific details are unknown.
- Top-down design emphasizes planning and a complete understanding of the system before coding begins.
- Top-down design follows a stepwise refinement process, where each component is further divided into subcomponents until they are simple enough to be implemented.
- Top-down design allows for a clear and consistent vision of the system, as well as easier testing and debugging of each component.
- However, top-down design can also lead to some drawbacks, such as:
  - Delayed feedback from the implementation phase, which can result in design flaws or unrealistic expectations.
  - Difficulty in integrating the components, especially if they are developed by different teams or using different technologies.
  - Overlooking some important details or requirements that are only discovered at the lower levels of the system.

##### Bottom-Up Design

- Bottom-up design is more suitable when the software solution is based on existing components or modules that can be reused or modified.
- Bottom-up design emphasizes the implementation and testing of the basic components before integrating them into higher-level modules.
- Bottom-up design follows a synthesis process, where each component is tested and verified before being combined with other components to form a larger system.
- Bottom-up design allows for a faster and more flexible development process, as well as easier adaptation to changing requirements or technologies.
- However, bottom-up design can also lead to some drawbacks, such as:
  - Lack of a clear and consistent vision of the system, which can result in inconsistency or redundancy among the components.
  - Difficulty in ensuring the compatibility and interoperability of the components, especially if they are developed by different teams or using different standards.
  - Overlooking some important features or functionalities that are only discovered at the higher levels of the system.

##### Combination of Top-Down and Bottom-Up Design

- Modern software design approaches usually combine both top-down and bottom-up design in various ways to achieve the best results.
- For example, a software project can start with a top-down analysis of the requirements and the overall architecture of the system, and then proceed with a bottom-up development of the components and modules, while ensuring their integration and alignment with the top-level design.
- Alternatively, a software project can start with a bottom-up development of some core components or modules that are well-defined and stable, and then use a top-down design to expand and refine the system with additional features or functionalities.
- The combination of top-down and bottom-up design can help to balance the trade-offs between planning and implementation, as well as between abstraction and detail, in software engineering.

##### Mnemonics and Learning Tricks

- One possible mnemonic to remember the difference between top-down and bottom-up design is: **TOP** stands for **T**hink **O**verview **P**lan, while **BOTTOM** stands for **B**uild **O**n **T**ested **T**ools **O**f **M**odules.
- Another possible mnemonic is: **TOP** stands for **T**ree **O**f **P**arts, while **BOTTOM** stands for **B**unch **O**f **T**echnical **T**erms **O**n **M**achines.
- A possible learning trick to understand the concept of top-down and bottom-up design is to use an analogy with a puzzle. Top-down design is like starting with the picture of the puzzle and then finding the pieces that fit together, while bottom-up design is like starting with the pieces of the puzzle and then forming the picture.



### Software Measurement and Metrics in Software Design

- Software measurement and metrics are used to quantify and evaluate the quality, performance, reliability, usability, and other attributes of a software product or process.
- Software measurement is the process of collecting data about a software product or process, such as the number of lines of code, the number of defects, the execution time, the user satisfaction, etc.
- Software metrics are functions that map the collected data to a numerical value that can be compared, analyzed, and interpreted. For example, the defect density metric is the number of defects per thousand lines of code.
- Software measurement and metrics can help software engineers and managers to monitor and control the software development process, identify and mitigate risks, improve the software quality, and estimate the cost and effort of software projects.
- There are three types of software metrics:
  - Product metrics: These metrics measure the characteristics of the software product, such as its size, complexity, functionality, maintainability, etc. Product metrics can be used to evaluate the software quality and to identify potential problems or improvement areas. For example, the cyclomatic complexity metric measures the number of independent paths in a program, which can indicate the difficulty of testing and maintaining the program.
  - Process metrics: These metrics measure the characteristics of the software development process, such as its efficiency, effectiveness, productivity, maturity, etc. Process metrics can be used to improve the software development methods, tools, and techniques, and to ensure that the process meets the standards and requirements. For example, the fault detection efficiency metric measures the percentage of faults detected before the software is delivered to the customer, which can indicate the quality of the testing process.
  - Project metrics: These metrics measure the characteristics of the software project, such as its scope, schedule, budget, resources, risk, etc. Project metrics can be used to plan, monitor, and control the software project activities, and to ensure that the project meets the objectives and expectations. For example, the earned value metric measures the progress of the project in terms of the work completed and the cost incurred, which can indicate the project performance and status.

- Some examples of software metrics are :
  - Code quality metrics: These metrics measure the quality of the code used for the software development, such as its readability, maintainability, reusability, testability, etc. Some examples of code quality metrics are the number of comments, the code coverage, the coupling, the cohesion, the duplication, etc.
  - Reliability metrics: These metrics measure the reliability of the software, which is the probability that the software will perform its intended functions without failure for a specified period of time under specified conditions. Some examples of reliability metrics are the mean time to failure, the mean time between failures, the failure rate, the availability, etc.
  - Performance metrics: These metrics measure the performance of the software, which is the degree to which the software meets the speed, response time, throughput, resource utilization, and other criteria that affect the user experience and the system efficiency. Some examples of performance metrics are the execution time, the latency, the throughput, the memory usage, the CPU usage, etc.
  - Usability metrics: These metrics measure the usability of the software, which is the degree to which the software is easy to learn, use, and remember by the intended users, and the degree to which the software meets the user needs and expectations. Some examples of usability metrics are the user satisfaction, the error rate, the completion rate, the time on task, the learnability, etc.

##### Halestead’s Software Science in software design

- Halestead’s Software Science is a set of metrics that measure the complexity and quality of a software program based on its source code.
- The metrics are derived from a few primitive parameters that count the number and types of operators and operands in the program.
- Operators are the basic syntactic units that perform some action, such as arithmetic operators, logical operators, keywords, etc.
- Operands are the basic syntactic units that represent some data, such as variables, constants, literals, etc.
- The metrics are based on the following assumptions:
  - A program is a collection of tokens that can be classified as either operators or operands.
  - The length of a program is a function of the number of operators and operands.
  - The vocabulary of a program is the set of unique operators and operands.
  - The difficulty and effort of writing or understanding a program depend on the vocabulary and the length of the program.
- The metrics are defined as follows:
  - n1: the number of distinct operators in the program
  - n2: the number of distinct operands in the program
  - N1: the total number of operators in the program
  - N2: the total number of operands in the program
  - n: the program vocabulary, n = n1 + n2
  - N: the program length, N = N1 + N2
  - N^: the estimated program length, N^ = n1 * log2(n1) + n2 * log2(n2)
  - V: the program volume, V = N * log2(n)
  - L: the program level, L = (2 * n2) / (n1 * N2)
  - D: the program difficulty, D = 1 / L
  - E: the program effort, E = D * V
  - T: the program time, T = E / 18 seconds
  - B: the number of delivered bugs, B = V / 3000
- The metrics can be used to evaluate the following aspects of a software program:
  - Size: the program length (N) and the program volume (V) measure the size of the program in terms of tokens and bits, respectively.
  - Complexity: the program difficulty (D) and the program level (L) measure the complexity of the program in terms of the ratio of operators to operands and the inverse of that ratio, respectively.
  - Quality: the program effort (E), the program time (T), and the number of delivered bugs (B) measure the quality of the program in terms of the amount of work, time, and errors involved in developing or maintaining the program.
- The metrics can be applied to any programming language that has a well-defined syntax and semantics.
- The metrics can be computed automatically by using tools that count the operators and operands in the source code.
- The metrics can be used to compare different programs or different versions of the same program, to identify the sources of complexity or inefficiency, and to suggest improvements or optimizations.
- The metrics have some limitations and criticisms, such as:
  - They are based on the syntactic structure of the program, not the semantic meaning or the functionality.
  - They do not account for the effects of comments, documentation, indentation, or formatting on the readability or maintainability of the program.
  - They do not account for the effects of external factors, such as the programmer's skill, experience, or motivation, on the development or maintenance of the program.
  - They do not account for the effects of different programming paradigms, such as procedural, object-oriented, or functional, on the complexity or quality of the program.
  - They do not account for the effects of different software development methodologies, such as agile, waterfall, or spiral, on the complexity or quality of the program.
  - They are based on empirical constants that may not be universally applicable or accurate for all programs or languages.

##### Function Point (FP) Based Measures in software design

- Function Point (FP) is a unit of measurement to express the amount of business functionality, an information system (as a product) provides to a user .
- FPs measure software size and are widely accepted as an industry standard for functional sizing.
- FPs are derived using an empirical relationship based on countable measures of software's information domain and assessments of software complexity.
- FPs can be used to estimate project cost and effort, as well as to compare the productivity and quality of different software projects .
- The basic steps of FP based estimation are  :
  - Identify the functions that the software system provides to the user. These functions are classified into five types: external inputs, external outputs, external inquiries, internal logical files, and external interface files.
  - Assign a complexity level (low, average, or high) to each function based on the number of data elements and file types involved.
  - Use a table of complexity weights to calculate the unadjusted function points (UFP) for each function type and sum them up.
  - Calculate the value adjustment factor (VAF) based on 14 general system characteristics that affect the functionality of the software system. The VAF ranges from 0.65 to 1.35.
  - Multiply the UFP by the VAF to get the adjusted function points (AFP).
  - Use a productivity factor (PF) to convert the AFP into effort or cost. The PF depends on the development environment, the programming language, the team experience, and other factors.

##### Cyclomatic Complexity Measures in software design

- Cyclomatic complexity is a software metric used to measure the complexity of a program .
- It is a count of the number of decisions in the source code. The higher the count, the more complex the code.
- It is calculated by using the control flow graph of the program, which is a graphical representation of the paths that can be traversed through the program during its execution .
- The formula for cyclomatic complexity is:

    `V(G) = E - N + 2P`

    where V(G) is the cyclomatic complexity, E is the number of edges, N is the number of nodes, and P is the number of connected components in the graph .

- Cyclomatic complexity can be used to:

    - Determine the number of independent paths through the program, which can help in designing test cases .
    - Assess the maintainability and readability of the code, as more complex code is harder to understand and modify.
    - Identify the potential defects and errors in the code, as more complex code is more prone to bugs.

- Some advantages of cyclomatic complexity are:

    - It is easy to compute and apply.
    - It is independent of the programming language and style.
    - It can help in improving the quality and reliability of the software.

- Some disadvantages of cyclomatic complexity are:

    - It does not consider the data flow or the logical complexity of the code.
    - It can be influenced by the coding conventions and the use of loops and conditional statements.
    - It does not account for the user requirements or the functionality of the software.

- An example of cyclomatic complexity calculation is shown below:

###### Control Flow Graphs in software design

## Unit 4 - Software Testing

Software testing is the process of verifying and validating that a software product or application meets the specified requirements and expectations of the stakeholders. Software testing helps to identify and correct defects, errors, and bugs in the software, and to ensure that the software is fit for use and delivers the desired functionality and quality .

There are many different types of software testing, each with specific objectives and strategies. Some of the common types of software testing are :

- **Acceptance testing**: Verifying whether the whole system works as intended and meets the acceptance criteria of the customers or users.
- **Integration testing**: Ensuring that software components or functions operate together and interact correctly with each other.
- **Unit testing**: Validating that each software unit performs as expected. A unit is the smallest testable component of an application, such as a function, a class, or a module.
- **Functional testing**: Checking functions by emulating business scenarios, based on functional requirements. Functional testing verifies the input-output behavior of the software and its compliance with the specifications.
- **Non-functional testing**: Assessing software properties non-critical to functionality but imperative for a positive user experience, such as performance, security, usability, reliability, compatibility, etc.
- **Regression testing**: Re-testing the software after changes or modifications to ensure that the existing functionality is not affected or broken by the new changes.
- **Smoke testing**: Performing a quick and basic check of the software to verify that the main features are working and the software is ready for further testing.
- **Exploratory testing**: Testing the software without a predefined test plan or script, relying on the tester's creativity, intuition, and experience to explore the software and discover defects or issues.
- **Manual testing**: Testing the software manually by human testers, without using any automated tools or scripts.
- **Automated testing**: Testing the software using automated tools or scripts that can execute predefined test cases, check the results, and generate reports.

Software testing methods are traditionally divided into white- and black-box testing. These two approaches are used to describe the point of view that the tester takes when designing test cases:

- **White-box testing**: Testing the software based on the internal structure, logic, and code of the software. White-box testing requires the tester to have knowledge of the software design and implementation, and to use techniques such as code analysis, code coverage, and code debugging.
- **Black-box testing**: Testing the software based on the external functionality and behavior of the software, without considering the internal structure, logic, or code of the software. Black-box testing requires the tester to have knowledge of the software requirements and specifications, and to use techniques such as input-output testing, boundary value analysis, and equivalence partitioning.
- **Grey-box testing**: Testing the software using a combination of white- and black-box testing techniques. Grey-box testing requires the tester to have some knowledge of the software design and implementation, but not as much as in white-box testing, and to use techniques such as state transition testing, decision table testing, and error guessing.

Software testing is an important and essential part of the software development life cycle (SDLC), as it helps to ensure the quality, reliability, and usability of the software product or application. Software testing also helps to reduce the risks, costs, and time associated with software development and maintenance, and to increase the customer satisfaction and confidence in the software.

Some of the benefits of software testing are :

- **Detecting and fixing defects**: Software testing helps to identify and correct defects, errors, and bugs in the software before it is delivered to the customers or users. This helps to avoid failures, malfunctions, or crashes of the software in the production environment, and to ensure that the software meets the expected standards and specifications.
- **Improving quality**: Software testing helps to improve the quality of the software by verifying and validating its functionality, performance, security, usability, compatibility, and other non-functional aspects. Software testing also helps to improve the quality of the software code by eliminating redundancies, complexities, and inefficiencies, and by enhancing readability, maintainability, and reusability.
- **Reducing risks**: Software testing helps to reduce the risks associated with software development and deployment, such as legal, financial, operational, reputational, and security risks. Software testing helps to ensure that the software complies with the regulatory, ethical, and contractual requirements, and that it does not cause any harm, damage, or loss to the customers, users, or stakeholders.

### Unit Testing in Software Testing

- Unit testing is a type of software testing that verifies the functionality and quality of individual units or components of a software system.
- A unit is the smallest testable part of a software system, such as a function, a class, a module, or an interface.

- Unit testing can be done in two ways: white-box testing and black-box testing.
  - White-box testing is a technique that tests the internal structure and logic of the code, using the knowledge of the code implementation and design.

- Unit testing can be done using different types of test cases, such as positive test cases, negative test cases, boundary test cases, equivalence test cases, or error test cases, depending on the input and output of the code.
- Unit testing can be done using different types of test data, such as valid data, invalid data, random data, or specific data, depending on the expected behavior and functionality of the code.

### Integration Testing in Software Testing

- Integration testing is a level of software testing where individual units or components of a software application are combined and tested to verify if they are working as they intend to when integrated  .
- The main aim of integration testing is to test the interface between the modules and identify any problems or bugs that arise when different components are combined and interact with each other .
- Integration testing is conducted to evaluate the compliance of a system or component with specified functional requirements and to ensure that the software meets the quality standards and expectations of the end-users.
- Integration testing is usually performed after unit testing and before system testing . It can be done in different ways, such as:
  - **Top-down approach**: The testing starts from the top-level modules and proceeds to the lower-level modules. The lower-level modules are simulated by stubs, which are dummy modules that provide predefined outputs  .
  - **Bottom-up approach**: The testing starts from the lower-level modules and proceeds to the higher-level modules. The higher-level modules are simulated by drivers, which are dummy modules that provide predefined inputs  .
  - **Sandwich approach**: The testing combines both top-down and bottom-up approaches. The middle-level modules are tested first, followed by the top-level and lower-level modules  .
  - **Big-bang approach**: The testing involves integrating all the modules at once and testing them as a whole. This approach is suitable for small and simple applications, but it can be risky and time-consuming for complex and large applications  .
- Integration testing can be further classified into different types, such as:
  - **Functional integration testing**: The testing focuses on verifying the functionality of the integrated modules and ensuring that they meet the specified requirements .
  - **Non-functional integration testing**: The testing focuses on verifying the non-functional aspects of the integrated modules, such as performance, security, reliability, usability, etc .
  - **Incremental integration testing**: The testing involves adding and testing one or more modules at a time until all the modules are integrated and tested .
  - **Continuous integration testing**: The testing involves integrating and testing the modules continuously and automatically using tools such as Jenkins, Travis CI, etc  .
- Integration testing can be performed using various tools, such as:
  - **Programming-language specific tools**: These are tools that are designed to test software coded in a specific coding language, such as JUnit for Java, PyTest for Python, etc.
  - **Rare-language tools**: These are tools that are used for rarer languages or languages with fewer tests available, such as CppUnit for C++, RSpec for Ruby, etc.
  - **Multiple-language tools**: These are tools that can test software coded in multiple languages, such as Selenium, Postman, SoapUI, etc.
- Integration testing can have several advantages, such as:
  - It can detect errors and defects that are not visible at the unit level .
  - It can improve the quality and reliability of the software .
  - It can reduce the risk of failure and rework in the later stages of testing .
  - It can facilitate the communication and collaboration among the developers and testers .
- Integration testing can also have some disadvantages, such as:
  - It can be complex and challenging to perform, especially for large and distributed applications .
  - It can be time-consuming and costly, especially if the integration testing tools are not available or compatible .
  - It can be dependent on the availability and quality of the modules, stubs, drivers, and test data .

### Testing for Performance in Software Testing

- Performance testing is a type of software testing that focuses on evaluating the performance and scalability of a system or application.
- The goal of performance testing is to identify bottlenecks, measure system performance under various loads and conditions, and ensure that the system can handle the expected number of users or transactions  .
- Performance testing can help to improve the quality, reliability, and user satisfaction of a software product.
- Performance testing can also help to avoid performance issues and failures in production, which can result in loss of revenue, reputation, and customer trust.
- Performance testing can be classified into different types, such as load testing, stress testing, spike testing, endurance testing, and volume testing .
  - Load testing measures system performance as the workload increases. That workload could mean concurrent users, requests, data, or transactions.
  - Stress testing measures system performance beyond the normal or peak load conditions. It is used to find the breaking point or limit of the system .
  - Spike testing measures system performance when there are sudden and extreme changes in the workload. It is used to check the system's ability to handle unexpected surges in traffic or demand.
  - Endurance testing measures system performance over a long period of time. It is used to check the system's ability to sustain the expected load without degradation or memory leaks .
  - Volume testing measures system performance with a large amount of data in the database or file system. It is used to check the system's ability to process and store the data efficiently .
- The steps involved in performance testing are:
  - Identify the testing environment, such as the hardware, software, network, and tools used for testing.
  - Identify the performance acceptance criteria, such as the goals and constraints for throughput, response time, resource utilization, and error rate.
  - Plan and design the performance tests, such as the test scenarios, test data, test scripts, and test schedule.
  - Execute the performance tests, such as running the test scripts, monitoring the system, and collecting the test results.
  - Analyze and report the performance test results, such as identifying the performance issues, bottlenecks, and recommendations for improvement.
- The best practices for performance testing are:
  - Define the performance test objectives and requirements clearly and realistically.
  - Choose the appropriate performance testing tools and techniques for the system under test.
  - Design the performance test scenarios and scripts to cover the critical and realistic user scenarios and workflows.
  - Use a representative test data and test environment that mimic the production environment as closely as possible.
  - Execute the performance tests iteratively and incrementally, starting from the baseline and increasing the load gradually.
  - Analyze and report the performance test results objectively and comprehensively, using graphs, charts, and metrics.
- The metrics used for performance testing are:
  - Throughput: the amount of data or transactions processed by the system per unit time, such as requests per second, transactions per minute, or bytes per second.
  - Response time: the time taken by the system to respond to a user request, such as average response time, minimum response time, maximum response time, or percentile response time.
  - Resource utilization: the amount of resources used by the system during the test, such as CPU, memory, disk, or network.
  - Error rate: the percentage of errors or failures encountered by the system during the test, such as HTTP errors, database errors, or application errors.



# Top-Down and Bottom-Up Testing Strategies in Software Testing

- Top-down and bottom-up testing are two types of **incremental testing** strategies that are used to integrate and test the modules of a software system.
- Incremental testing is a technique of testing the software in parts rather than as a whole. It involves integrating and testing the modules one by one until the entire system is ready.
- Top-down and bottom-up testing differ in the order of integration and testing of the modules.

## Top-Down Testing
- Top-down testing is a strategy that starts from the top-level module and proceeds to the lower-level modules in a hierarchical manner.
- The top-level module is the one that controls the main logic or functionality of the software system. It is tested first and then integrated with the lower-level modules that provide the supporting functions or services.
- The lower-level modules that are not yet ready are replaced by **stubs**, which are dummy modules that simulate the expected behavior of the real modules.
- The advantages of top-down testing are:
  - It allows early verification of the main logic and functional requirements of the software system.
  - It facilitates top-down design and development of the software system.
  - It helps in identifying the major errors and defects in the top-level module.
- The disadvantages of top-down testing are:
  - It requires a lot of stubs to be created and maintained, which can be time-consuming and error-prone.
  - It may delay the testing of the lower-level modules and their interactions, which can affect the quality and performance of the software system.
  - It may not detect the integration errors and interface mismatches between the modules.

## Bottom-Up Testing
- Bottom-up testing is a strategy that starts from the bottom-level modules and proceeds to the higher-level modules in a hierarchical manner.
- The bottom-level modules are the ones that provide the basic functions or services to the software system. They are tested first and then integrated with the higher-level modules that control the main logic or functionality of the software system.
- The higher-level modules that are not yet ready are replaced by **drivers**, which are dummy modules that invoke and test the lower-level modules.
- The advantages of bottom-up testing are:
  - It allows early verification of the basic functions and services of the software system.
  - It facilitates bottom-up design and development of the software system.
  - It helps in identifying the minor errors and defects in the bottom-level modules.
- The disadvantages of bottom-up testing are:
  - It requires a lot of drivers to be created and maintained, which can be time-consuming and error-prone.
  - It may delay the testing of the higher-level modules and their interactions, which can affect the quality and performance of the software system.
  - It may not detect the integration errors and interface mismatches between the modules.

## Sandwich Testing
- Sandwich testing is a strategy that combines both top-down and bottom-up testing approaches. It is also known as **hybrid testing** or **mixed testing**.
- In sandwich testing, the software system is divided into three layers: the top layer, the middle layer, and the bottom layer.
- The top layer and the bottom layer are tested using the top-down and bottom-up testing strategies respectively, while the middle layer is tested using either of the strategies or both.
- The advantages of sandwich testing are:
  - It overcomes the limitations of both top-down and bottom-up testing strategies.
  - It allows parallel testing of the different layers of the software system, which can save time and resources.
  - It helps in detecting the integration errors and interface mismatches between the modules at different levels.
- The disadvantages of sandwich testing are:
  - It requires more planning and coordination among the testers and developers, which can be complex and challenging.
  - It may increase the complexity and cost of the testing process, as it involves both stubs and drivers.

#### Structural Testing (White Box Testing) software testing strategy

- Structural testing is a software testing strategy that verifies the internal structure, design, and implementation of an application, rather than just its functionality.
- Structural testing is also known as white box testing, clear box testing, open box testing, glass box testing, transparent box testing, or code-based testing.
- Structural testing requires the testers to have access to the source code or binaries of the application, and to have knowledge of the devices and systems it is running on.
- Structural testing can be performed at different levels of testing, such as unit testing, integration testing, system testing, or acceptance testing, depending on the scope and complexity of the application.
- Structural testing can be done manually or automatically, using tools that can analyze the code and generate test cases based on various criteria, such as code coverage, data flow, control flow, logic, etc.
- Structural testing can help to improve the design, usability, security, and performance of the application, by identifying and fixing errors, bugs, vulnerabilities, and inefficiencies in the code.
- Structural testing can also help to measure the quality and complexity of the code, by using metrics such as cyclomatic complexity, lines of code, code coverage, etc.

Some of the common techniques and types of structural testing are:

- Statement coverage: This technique measures the percentage of executable statements in the code that are executed by the test cases. It aims to cover all the statements at least once.
- Branch coverage: This technique measures the percentage of branches or decision points in the code that are executed by the test cases. It aims to cover all the possible outcomes of each branch, such as true or false, yes or no, etc.
- Path coverage: This technique measures the percentage of paths or sequences of statements and branches in the code that are executed by the test cases. It aims to cover all the possible paths from the entry point to the exit point of the code.
- Condition coverage: This technique measures the percentage of conditions or logical expressions in the code that are evaluated to true or false by the test cases. It aims to cover all the possible values of each condition, such as AND, OR, NOT, etc.
- Loop coverage: This technique measures the percentage of loops or iterations in the code that are executed by the test cases. It aims to cover all the possible scenarios of each loop, such as zero, one, or more iterations, entry or exit conditions, etc.
- Data flow coverage: This technique measures the percentage of data flows or interactions between variables in the code that are executed by the test cases. It aims to cover all the possible states of each variable, such as definition, use, modification, etc.
- Mutation testing: This technique involves modifying or mutating the code in small ways, such as changing a variable, operator, or statement, and then running the test cases to see if they can detect the change. It aims to measure the effectiveness and robustness of the test cases.

Some of the advantages and disadvantages of structural testing are:

- Advantages:
  - It can help to find errors and bugs that are not visible or detectable by functional testing.
  - It can help to improve the quality and maintainability of the code by enforcing coding standards and best practices.
  - It can help to optimize the performance and security of the code by eliminating redundant or unnecessary code, and by detecting vulnerabilities and weaknesses.
  - It can help to measure the code coverage and complexity, and to provide feedback and suggestions for improvement.
- Disadvantages:
  - It can be time-consuming and costly, as it requires access to the source code or binaries, and knowledge of the internal structure and logic of the code.
  - It can be difficult and challenging, as it requires a high level of technical and analytical skills, and the use of specialized tools and techniques.
  - It can be incomplete and insufficient, as it cannot cover all the possible scenarios and inputs that the code may encounter in the real world.
  - It can be biased and subjective, as it depends on the perspective and assumptions of the testers, and may not reflect the expectations and requirements of the users or customers.

#### Alpha and Beta Testing of Products  software testing strategy

Beta testing is more user-oriented and experiential, as the testers are expected to provide feedback, opinions, and recommendations on the software.

### Static Testing Strategies in Software Testing

- Static testing is a software testing method that examines a program and its associated documents without executing the code. It is done to find and remove errors and ambiguities in the software development cycle and thus reduce the cost of fixing them later.
- Static testing can be performed in two main ways: review and static analysis.
- Review is a manual examination of the code and the documents by the developers, testers, or other stakeholders. It can be done in different forms, such as:
  - Informal review: A casual and unstructured discussion of the code or document with no formal records or outcomes.
  - Walkthrough: A formal meeting where the author of the code or document presents it to the reviewers and solicits feedback and suggestions.
  - Technical review: A formal meeting where a group of technical experts evaluates the code or document against predefined criteria and standards.
  - Inspection: A formal and rigorous process where a group of trained inspectors follows a checklist of rules and guidelines to identify defects and deviations in the code or document.
- Static analysis is an automated examination of the code and the documents by using tools that check for syntax errors, coding standards, complexity, security vulnerabilities, etc. It can be done in different stages, such as:
  - Code analysis: A tool scans the source code and reports any errors, warnings, or suggestions for improvement.
  - Design analysis: A tool analyzes the design documents and diagrams and checks for consistency, completeness, and feasibility.
  - Requirement analysis: A tool verifies the requirement specifications and ensures that they are clear, testable, and traceable.
- Static testing has several advantages, such as:
  - It can detect defects early in the development cycle and prevent them from propagating to later stages.
  - It can improve the quality and reliability of the software by reducing the number of defects and rework.
  - It can save time and resources by avoiding unnecessary testing and debugging of faulty code or documents.
  - It can enhance the communication and collaboration among the development team and the stakeholders by providing feedback and suggestions.
  - It can facilitate the compliance with standards and regulations by ensuring that the code and documents follow the best practices and guidelines.
- Static testing has some limitations, such as:
  - It cannot verify the functionality or performance of the software by executing the code or simulating the user scenarios.
  - It may not detect all the defects or errors in the code or documents, especially those that are related to logic, data flow, or integration.
  - It may require specialized tools and skills to perform the static analysis and interpret the results.
  - It may generate false positives or negatives, which are incorrect or misleading reports of defects or errors.



#### Formal Technical Reviews (Peer Reviews) Static testing strategy

- Formal Technical Reviews (FTRs) or Peer Reviews are a type of static testing technique that involves the examination of software artifacts by a team of experts or peers.
- FTRs aim to find defects, issues, and ambiguities in the software documents, such as requirements, design, code, test cases, etc.
- FTRs also help to improve the quality of the software, verify its compliance with standards and specifications, and ensure its readiness for the next phase of development or testing.
- FTRs are usually led by a trained moderator, who is not the author of the document being reviewed. The moderator's role is to facilitate the review process, ensure that the review objectives are met, and record the review findings and outcomes.
- FTRs follow a formal and structured process that consists of the following steps:
  - Planning: The moderator selects the review team, defines the review scope and objectives, and distributes the review materials to the reviewers.
  - Preparation: The reviewers study the review materials and identify any potential defects, questions, or comments. They also prepare a checklist of items to be verified during the review.
  - Review meeting: The review team meets to discuss the review materials and share their findings. The moderator guides the discussion, ensures that all the review items are covered, and records the defects and issues identified. The review team also decides on the actions to be taken to resolve the defects and issues.
  - Rework: The author of the document performs the necessary corrections or modifications based on the review feedback and actions.
  - Follow-up: The moderator verifies that the rework has been done correctly and that all the defects and issues have been resolved. The moderator also prepares a review report that summarizes the review results and outcomes.
- FTRs are the most formal and rigorous type of reviews, and they require more time and effort than other types of reviews, such as walkthroughs or inspections. However, they also provide more benefits, such as:
  - Detecting defects early in the software development life cycle, which reduces the cost and effort of fixing them later.
  - Improving the communication and collaboration among the software team members, which enhances the team's performance and productivity.
  - Increasing the confidence and satisfaction of the software stakeholders, such as customers, users, and managers, who can rely on the quality and reliability of the software.
- A mnemonic to remember the steps of FTRs is **PPRRF**, which stands for Planning, Preparation, Review meeting, Rework, and Follow-up.



#### Walk Through (Walkthrough) Static testing strategy

- A walkthrough is a type of static testing technique that involves a group of people reviewing a document or a piece of code to find defects, errors, or improvements.
- The walkthrough is usually led by the author of the document or code, who explains the logic and purpose of the work product to the reviewers.
- The reviewers can ask questions, make comments, or suggest changes to the author during the walkthrough.
- The walkthrough is informal and does not follow a predefined process or checklist. The author can decide how to conduct the walkthrough and who to invite as reviewers.
- The walkthrough is useful for early detection and prevention of defects, as well as for knowledge transfer and team collaboration.
- The walkthrough can be applied to any type of document or code, such as requirements, design, test cases, user manuals, etc.

Some possible mnemonics and learning tricks for the walkthrough static testing strategy are:

- WALK: Work product, Author, Logic, Knowledge. These are the four elements of a walkthrough: the work product to be reviewed, the author who leads the walkthrough, the logic and purpose of the work product, and the knowledge transfer and collaboration among the reviewers.
- WALKTHROUGH: What, Author, Logic, Key points, Team, How, Review, Outcome, Understand, Goals, Help. These are the steps of a walkthrough: explain what the work product is, introduce the author, explain the logic and purpose of the work product, highlight the key points, introduce the team of reviewers, explain how the walkthrough will be conducted, review the work product, summarize the outcome, check the understanding of the reviewers, state the goals of the walkthrough, and ask for help or feedback.



#### Code Inspection (Code Inspection) Static testing strategy

- Code inspection is a static testing technique that involves a systematic and formal examination of the source code by a team of experts.
- The main objectives of code inspection are to find defects, improve code quality, ensure compliance with coding standards and guidelines, and facilitate knowledge transfer among developers.
- Code inspection is usually performed after the code is written and before it is tested. It can be applied to any programming language or platform.
- Code inspection follows a structured process that consists of the following steps:

  1. Planning: The inspection team is formed, the roles and responsibilities are assigned, the scope and objectives of the inspection are defined, and the inspection checklist is prepared.
  2. Overview: The author of the code presents an overview of the code to the inspection team, explaining the design, logic, and functionality of the code.
  3. Preparation: The inspection team reviews the code individually, using the inspection checklist and other tools to identify potential defects and issues.
  4. Inspection meeting: The inspection team meets to discuss the findings, classify the defects, and agree on the actions to be taken.
  5. Rework: The author of the code fixes the defects and issues identified by the inspection team, and documents the changes made.
  6. Follow-up: The inspection team verifies that the defects have been fixed, and closes the inspection.

- Code inspection has several benefits, such as:

  - It can detect defects early in the software development life cycle, reducing the cost and effort of fixing them later.
  - It can improve the quality and reliability of the code, enhancing the performance and functionality of the software.
  - It can ensure that the code conforms to the coding standards and guidelines, improving the readability and maintainability of the code.
  - It can facilitate knowledge transfer and collaboration among developers, improving the skills and productivity of the team.

- Code inspection also has some challenges, such as:

  - It can be time-consuming and resource-intensive, requiring a high level of expertise and commitment from the inspection team.
  - It can be subjective and inconsistent, depending on the skills and experience of the inspectors and the quality of the inspection checklist and tools.
  - It can be affected by human factors, such as bias, fatigue, and communication issues, leading to errors and conflicts among the inspection team.

- A possible mnemonic to remember the steps of code inspection is: **P**lan, **O**verview, **P**repare, **I**nspect, **R**ework, **F**ollow-up, or **POP IRF**.



#### Compliance with Design and Coding Standards (Coding Standards) Static testing strategy

- Coding standards are a set of rules or guidelines that define how the source code of a software system should be written and formatted.
- Coding standards aim to improve the quality, readability, maintainability, and consistency of the code, as well as to prevent errors and defects.
- Static testing is a type of software testing that involves the analysis of the code or other software artifacts without executing them.
- Static testing can be performed manually or with the help of tools, such as code analyzers, code reviewers, code inspectors, code linters, etc.
- Static testing can detect syntax errors, logical errors, coding violations, design flaws, security vulnerabilities, performance issues, etc.
- Static testing can be applied at any stage of the software development life cycle, but it is more effective and efficient when performed early, such as during the design or coding phases.
- Static testing can complement dynamic testing, which involves executing the code or software system and observing its behavior and outputs.
- Static testing can reduce the cost and time of testing, as well as the number of defects that need to be fixed later.

Some of the benefits of applying static testing to check the compliance with design and coding standards are:

- It can improve the readability and understandability of the code, which can facilitate the communication and collaboration among the developers and other stakeholders.
- It can enhance the maintainability and modifiability of the code, which can reduce the effort and risk of making changes or adding new features.
- It can increase the reusability and portability of the code, which can enable the reuse of existing components or the adaptation of the code to different platforms or environments.
- It can ensure the consistency and uniformity of the code, which can prevent confusion and ambiguity among the developers and the users.
- It can prevent or reduce the occurrence of errors and defects, which can improve the reliability and functionality of the software system.
- It can identify and eliminate potential security vulnerabilities, which can protect the software system and the data from unauthorized access or manipulation.
- It can optimize the performance and efficiency of the code, which can improve the speed and resource utilization of the software system.

Some of the challenges or limitations of applying static testing to check the compliance with design and coding standards are:

- It can be difficult or impractical to define and enforce a universal or consistent set of coding standards, as different projects, languages, platforms, or organizations may have different preferences, conventions, or requirements.
- It can be time-consuming or tedious to perform manual static testing, especially for large or complex code bases, which can reduce the productivity and motivation of the developers.
- It can be costly or challenging to acquire, configure, or use the appropriate tools for static testing, as some tools may be expensive, incompatible, or unavailable for certain languages, platforms, or environments.
- It can be inaccurate or incomplete to rely solely on static testing, as some errors or defects may not be detectable or visible by analyzing the code or artifacts, but only by executing them and observing their behavior and outputs.

Some of the best practices or recommendations for applying static testing to check the compliance with design and coding standards are:

- It is advisable to adopt and follow a well-defined and agreed-upon set of coding standards, which can be documented and communicated to all the developers and other stakeholders involved in the project.
- It is advisable to perform static testing as early and as frequently as possible, which can enable the early detection and correction of errors and defects, as well as the prevention of their propagation or accumulation.
- It is advisable to use a combination of manual and automated static testing, which can leverage the strengths and overcome the weaknesses of both approaches, as well as to cross-check and verify the results.
- It is advisable to use a variety of tools and techniques for static testing, which can provide different perspectives and insights into the code or artifacts, as well as to cover different aspects and dimensions of quality.
- It is advisable to review and update the coding standards and the static testing methods and tools periodically, which can reflect the changes and improvements in the software development practices and technologies.

### Software as an Evolutionary Entity

- Software is an evolutionary entity because it changes over time in response to changing requirements, environments, technologies, and user feedback.
- Software evolution is the process of developing, maintaining, and improving software systems throughout their life cycle.
- Software evolution can be classified into two types: software maintenance and software evolution proper.
- Software maintenance is the process of correcting faults, improving performance, or adapting software to a changed environment. Software maintenance can be further divided into four categories: corrective, adaptive, perfective, and preventive maintenance.
- Software evolution proper is the process of adding new functionality, modifying existing functionality, or reorganizing software to meet new requirements or improve quality. Software evolution proper can be further divided into two categories: incremental and innovative evolution.
- Incremental evolution is the process of making small changes to software that do not alter its basic structure or functionality. Incremental evolution is usually driven by user feedback or market demand.
- Innovative evolution is the process of making large changes to software that alter its basic structure or functionality. Innovative evolution is usually driven by technological advances or paradigm shifts.
- Software evolution is influenced by various factors, such as user needs, business goals, technical constraints, organizational culture, legal regulations, and ethical principles.
- Software evolution is governed by various laws, such as Lehman's laws, which describe the empirical observations and trends of software evolution. Some of these laws are:

  - Law of Continuing Change: A software system must be continually adapted or it becomes progressively less satisfactory.
  - Law of Increasing Complexity: As a software system evolves, its complexity increases unless work is done to maintain or reduce it.
  - Law of Self-Regulation: A software system's evolution process is self-regulating with the distribution of product and process measures close to normal.
  - Law of Conservation of Organizational Stability: The average effective global activity rate in a software system's evolution process is invariant over the product's lifetime.
  - Law of Conservation of Familiarity: As a software system evolves, all associated with it must maintain mastery of its content and behavior to achieve satisfactory evolution.
  - Law of Continuing Growth: The functionality offered by a software system must be continually increased to maintain user satisfaction.
  - Law of Declining Quality: The quality of a software system will appear to be declining unless it is rigorously maintained and adapted to operational environment changes.
  - Law of Feedback System: Software evolution processes constitute multi-level, multi-loop, multi-agent feedback systems and must be treated as such to achieve significant improvement over any reasonable base.

- Software evolution is a challenging and complex task that requires careful planning, management, and evaluation. Some of the challenges and issues of software evolution are:

  - Managing the scope and cost of software evolution
  - Balancing the trade-offs between stability and change
  - Ensuring the quality and reliability of software evolution

  - Coping with the diversity and heterogeneity of software systems and environments

  - Adapting to the changing needs and expectations of software users and customers
  - Leveraging the opportunities and risks of emerging technologies and paradigms
  - Addressing the ethical and social implications of software evolution

### Categories of Maintenance of Software

Software maintenance is the process of modifying and updating a software product after its delivery to correct faults, improve performance, or adapt to changes in the environment. Software maintenance can be classified into four categories, namely:

- **Corrective maintenance**: This involves fixing errors and bugs in the software system that are discovered during its operation. Corrective maintenance is usually reactive and unplanned, and it aims to restore the normal functioning of the software system. An example of corrective maintenance is patching a security vulnerability in a web application.

- **Adaptive maintenance**: This involves modifying the software system to adapt it to changes in the environment, such as changes in hardware, software, or user requirements. Adaptive maintenance is usually proactive and planned, and it aims to keep the software system compatible and usable in the new environment. An example of adaptive maintenance is upgrading a software system to run on a newer operating system.

- **Perfective maintenance**: This involves enhancing the software system to improve its functionality, performance, usability, or quality. Perfective maintenance is usually initiated by the user or the developer, and it aims to add new features or improve existing ones in the software system. An example of perfective maintenance is adding a new functionality to a software product based on user feedback.

- **Preventive maintenance**: This involves modifying the software system to prevent potential problems or reduce the complexity of the software system. Preventive maintenance is usually done by the developer, and it aims to improve the maintainability, reliability, or security of the software system. An example of preventive maintenance is refactoring the code to make it more readable and modular.

A mnemonic to remember the four categories of software maintenance is **CAPT** (Corrective, Adaptive, Perfective, Preventive).

### Cost of Maintenance of Software

- The cost of maintenance of software is the amount of money and resources required to keep the software system running after it has been delivered to the end users.
- The cost of maintenance of software depends on various factors, such as:
  - The quality of the software design and implementation
  - The complexity and size of the software system
  - The number and frequency of changes requested by the users or stakeholders
  - The availability and skill of the maintenance staff
  - The tools and methods used for maintenance activities
  - The type and level of documentation provided with the software system
- The cost of maintenance of software can be classified into four categories, according to the IEEE Standard 1219-1998:
  - Corrective maintenance: The cost of fixing errors or defects in the software system that affect its functionality or performance.
  - Adaptive maintenance: The cost of modifying the software system to cope with changes in the environment, such as new hardware, operating systems, or standards.
  - Perfective maintenance: The cost of enhancing the software system to improve its quality, usability, or functionality, according to the users' or stakeholders' needs or expectations.
  - Preventive maintenance: The cost of modifying the software system to prevent potential errors or defects, or to improve its maintainability, reliability, or security.
- The cost of maintenance of software can be estimated using various models, such as:
  - The Boehm model: This model assumes that the cost of maintenance of software is proportional to the size of the software system, measured in lines of code (LOC), and the annual change traffic (ACT), which is the percentage of LOC that are added, modified, or deleted per year. The formula is:

    `Maintenance cost = A * Size * ACT`

    where A is a constant that depends on the type of software system and the maintenance staff.

  - The COCOMO II model: This model extends the Boehm model by considering various cost drivers, such as the complexity of the software system, the quality of the software design and implementation, the experience and capability of the maintenance staff, the tools and methods used for maintenance activities, and the type and level of documentation provided with the software system. The formula is:

    `Maintenance cost = A * Size * EAF * ACT`

    where A is a constant that depends on the type of software system and the maintenance staff, EAF is the effort adjustment factor that reflects the cost drivers, and ACT is the annual change traffic.

  - The SLIM model: This model is based on the assumption that the cost of maintenance of software is related to the software life cycle, which consists of four phases: development, transition, production, and retirement. The formula is:

    `Maintenance cost = A * Size * (B + C * T)`

    where A is a constant that depends on the type of software system and the maintenance staff, B is a constant that reflects the cost of transition and retirement phases, C is a constant that reflects the cost of production phase, and T is the time spent in the production phase.

- A mnemonic to remember the four categories of maintenance cost is:

  - CAP: Corrective, Adaptive, Perfective
  - PAP: Preventive, Adaptive, Perfective
  - PAC: Preventive, Adaptive, Corrective
  - CPA: Corrective, Perfective, Adaptive

  The first letter of each mnemonic corresponds to the most expensive category of maintenance cost, and the last letter corresponds to the least expensive category of maintenance cost. For example, CAP means that corrective maintenance is the most expensive, and adaptive maintenance is the least expensive.

### Reverse Engineering (RE) of Software

- Reverse engineering (RE) of software is the process of analyzing a software system to identify its components and their interrelationships and to create representations of the system in another form or at a higher level of abstraction.
- RE can be used for various purposes, such as:
  - Improving the quality, performance, and maintainability of a software system by redesigning and modifying its structure and functionality.
  - Recovering the source code of a software system from its executable or binary form, when the original source code is unavailable or lost.
  - Understanding the behavior and functionality of a software system, especially when it is complex, undocumented, or poorly documented.
  - Detecting and fixing errors, vulnerabilities, or malicious code in a software system.
  - Synthesizing higher-level abstractions or models of a software system, such as data flow diagrams, class diagrams, or state machines.
  - Facilitating the reuse of existing software components or systems by identifying their interfaces, dependencies, and specifications.
- RE can be performed at different levels of granularity, such as:
  - Instruction level: analyzing the machine code or assembly code of a software system to understand its low-level operations and logic.
  - Function level: analyzing the functions or procedures of a software system to understand their inputs, outputs, and effects.
  - Module level: analyzing the modules or components of a software system to understand their structure, functionality, and interactions.
  - System level: analyzing the software system as a whole to understand its architecture, design, and behavior.
- RE can be performed using different techniques, such as:
  - Static analysis: analyzing the software system without executing it, by examining its code, data, or structure.
  - Dynamic analysis: analyzing the software system by executing it, by observing its behavior, output, or performance.
  - Hybrid analysis: combining static and dynamic analysis to obtain more comprehensive and accurate results.
- RE can be performed using different tools, such as:
  - Disassemblers: tools that convert machine code or binary code into assembly code or human-readable instructions.
  - Decompilers: tools that convert machine code or binary code into source code or high-level programming languages.
  - Debuggers: tools that allow the execution, inspection, and modification of a software system at run time.
  - Analyzers: tools that perform various types of analysis on a software system, such as control flow analysis, data flow analysis, or dependency analysis.
  - Visualizers: tools that create graphical representations of a software system, such as graphs, charts, or diagrams.
- RE can be challenging and time-consuming, depending on the complexity, size, and quality of the software system, as well as the availability and accuracy of the documentation and the tools.
- RE can be subject to legal and ethical restrictions, depending on the ownership, license, and purpose of the software system, as well as the jurisdiction and regulations of the country or region where the RE is performed.



### Software Configuration Management Activities

Software Configuration Management (SCM) is the process of identifying, controlling, and tracking the changes made to the software during its development and maintenance. SCM aims to ensure the integrity, reliability, and quality of the software products.

- **Configuration identification**: This activity involves defining and documenting the features, functions, and components of the software product. It also involves assigning unique identifiers and version numbers to each configuration item. Configuration identification helps to establish a baseline for the software product and to manage the changes made to it.

- **Configuration control**: This activity involves reviewing, approving, and implementing the changes requested or proposed to the software product. It also involves updating the configuration identification documents and maintaining the traceability of the changes. Configuration control helps to ensure that only authorized and consistent changes are made to the software product.

- **Configuration status accounting**: This activity involves recording and reporting the status and history of the configuration items and the changes made to them. It also involves maintaining the configuration audit trail and providing information to the stakeholders about the software product. Configuration status accounting helps to monitor and verify the configuration of the software product and to support decision making.

- **Configuration audit**: This activity involves verifying that the configuration items and the changes made to them conform to the requirements, standards, and specifications. It also involves checking that the configuration identification documents are accurate and complete. Configuration audit helps to ensure the quality and compliance of the software product.

- **Configuration management planning**: This activity involves defining and documenting the policies, procedures, roles, responsibilities, tools, and techniques for performing the SCM activities. It also involves establishing the scope, objectives, and deliverables of the SCM process. Configuration management planning helps to provide a framework and a roadmap for the SCM process.

### Change Control Process in software project management

- Change control is the process of managing and assessing changes to a software project and its procedures.
- Change control helps to ensure that the project scope, schedule, budget, quality and risks are aligned with the agreed-upon objectives and expectations of the stakeholders.
- Change control can also help to avoid scope creep, which is the uncontrolled addition of features or requirements to a project without proper authorization or documentation.
- Change control typically involves the following steps:

  1. **Change request initiation**: A change request is a formal document that describes the proposed change, the reason for it, the expected benefits and impacts, and the estimated cost and time. A change request can be initiated by anyone involved in the project, such as the project manager, the project team, the client, the sponsor, or the end-users.
  2. **Change request assessment**: The change request is reviewed by the project manager and the change control board (CCB), which is a group of authorized stakeholders who have the power to approve or reject changes. The CCB evaluates the change request based on its feasibility, alignment with the project objectives, priority, urgency, and risk. The CCB may also request more information, clarification, or analysis from the change requestor or the project team.
  3. **Change request analysis**: The project team performs a detailed analysis of the change request, including its technical, functional, and operational implications, its dependencies and interdependencies with other project components, its impact on the project scope, schedule, budget, quality, and risks, and its alternatives and trade-offs. The project team also prepares a change proposal that outlines the recommended solution, the required resources, the revised project plan, and the expected outcomes and benefits.
  4. **Change request implementation**: If the change request is approved by the CCB, the project team implements the change according to the change proposal. The project manager monitors and controls the change implementation process, ensuring that the change is executed within the agreed-upon parameters and that any issues or deviations are reported and resolved. The project manager also communicates the change status and progress to the relevant stakeholders and updates the project documentation and records accordingly.
  5. **Change request evaluation**: After the change is implemented, the project team evaluates the change results and outcomes, comparing them with the expected benefits and impacts. The project team also collects feedback from the stakeholders and the end-users, and identifies any lessons learned or best practices for future reference. The project manager closes the change request and reports the change completion and evaluation to the CCB and the other stakeholders.

- A mnemonic to remember the steps of the change control process is **CRAIC** (Change Request, Assessment, Analysis, Implementation, and Evaluation).
- A change log is a tool that helps to track and document the changes that occur during a project. A change log typically includes the following information:

  - Change ID: A unique identifier for each change request
  - Change description: A brief summary of the change request
  - Change requestor: The name and role of the person or group who initiated the change request
  - Change date: The date when the change request was submitted
  - Change status: The current status of the change request, such as pending, approved, rejected, in progress, completed, or closed
  - Change priority: The level of importance or urgency of the change request, such as high, medium, or low
  - Change impact: The degree of impact of the change request on the project scope, schedule, budget, quality, and risks, such as major, moderate, or minor
  - Change approval: The name and role of the person or group who approved or rejected the change request
  - Change implementation: The name and role of the person or group who implemented the change request
  - Change evaluation: The name and role of the person or group who evaluated the change request

### Software Version Control in software project management

- Software Version Control (SVC) is a management strategy to track and store changes to a software development document or set of files that follow the development project from beginning to end-of-life.
- SVC helps software teams to manage changes to source code over time, solve integration conflicts in code, and manage different artifacts involved in software projects .
- SVC can also apply to other files, such as videos, images, and any other deliverables that have multiple iterations.
- SVC can be implemented using software tools, such as Git, SVN, Mercurial, etc., that provide features such as branching, merging, tagging, version history, etc.
- Some of the benefits of using SVC in software project management are:
  - It improves collaboration and communication among team members, as they can share and review code changes easily.
  - It enhances quality and reliability of the software, as it allows to track and fix bugs, test and deploy code, and revert to previous versions if needed.
  - It increases efficiency and productivity of the software development process, as it reduces duplication of work, enables parallel development, and automates workflows.
  - It facilitates documentation and auditability of the software, as it records who, when, and why made changes to the code, and provides a history of the project evolution.
- Some of the challenges of using SVC in software project management are:
  - It requires training and discipline of the team members, as they need to follow best practices and conventions for using the SVC tool and managing the code changes.
  - It involves trade-offs and compromises among team members, as they need to coordinate and resolve conflicts in code, and agree on the branching and merging strategies.
  - It adds complexity and overhead to the software development process, as it requires setting up and maintaining the SVC tool, and dealing with technical issues and errors.

- A possible mnemonic to remember the benefits of SVC is **CQEPD** (Collaboration, Quality, Efficiency, Productivity, Documentation).
- A possible mnemonic to remember the challenges of SVC is **TTC** (Training, Trade-offs, Complexity).



# An Overview of CASE Tools in Software Project Management

- CASE stands for Computer-Aided Software Engineering, which refers to the use of software applications to automate, support, and improve the software development process.
- CASE tools are used by software project managers, analysts, and engineers to develop software systems of high quality and free of defects.
- CASE tools can be classified into two categories: upper CASE and lower CASE.
  - Upper CASE tools are used for the early stages of software development, such as analysis, design, and specification. They help in creating diagrams, models, and documentation of the software requirements and architecture.
  - Lower CASE tools are used for the later stages of software development, such as implementation, testing, and maintenance. They help in generating code, debugging, testing, and deploying the software system.
- CASE tools can also be categorized based on their functions, such as:
  - Diagramming tools: They help in diagrammatic and graphical representations of the data and system processes. Examples are data flow diagrams, entity-relationship diagrams, and UML diagrams.
  - Process modeling tools: They help in creating and managing the software process model, which defines the activities, tasks, roles, and deliverables of the software project. Examples are Gantt charts, PERT charts, and CPM charts.
  - Project management tools: They help in planning, organizing, monitoring, and controlling the software project. They provide features such as scheduling, budgeting, resource allocation, risk management, and quality assurance. Examples are Microsoft Project, Jira, and Trello.
  - Database management tools: They help in designing, creating, and manipulating the database that stores the data of the software system. They provide features such as data modeling, query processing, and data integrity. Examples are MySQL, Oracle, and MongoDB.
  - Documentation tools: They help in creating and maintaining the documentation of the software system, such as user manuals, technical manuals, and reports. They provide features such as formatting, editing, and indexing. Examples are Microsoft Word, LaTeX, and Markdown.
- CASE tools have several advantages, such as:
  - They increase the productivity and efficiency of the software development team by automating and simplifying the tasks.
  - They improve the quality and reliability of the software system by reducing errors and defects.
  - They enhance the communication and collaboration among the software development team members and stakeholders by providing a common platform and language.
  - They facilitate the reuse and maintenance of the software system by providing standardization and documentation.
- CASE tools also have some disadvantages, such as:
  - They require a high initial investment and maintenance cost for acquiring and updating the tools.
  - They may not be compatible or interoperable with each other or with the existing software systems and platforms.
  - They may impose some limitations or constraints on the software development process and creativity of the software developers.
  - They may not be able to handle complex or dynamic software systems or requirements.



### Estimation of Various Parameters such as Cost and Time in software project management

- Estimation is the process of predicting the required resources, effort, cost and time for a software project based on the available information and assumptions.
- Estimation is important for planning, budgeting, scheduling, controlling and managing the software project.
- Estimation can be done at different levels of granularity, such as project level, phase level, activity level or task level.
- Estimation can be done using different techniques, such as expert judgment, analogy, parametric, bottom-up, top-down, three-point, etc.
- Estimation can be affected by various factors, such as project scope, complexity, size, quality, risk, uncertainty, productivity, experience, etc.
- Estimation can be improved by using historical data, calibration, validation, feedback, adjustment, etc.

Some of the common estimation techniques are:

- **Expert judgment**: This technique relies on the experience and expertise of the project team or external experts to provide estimates based on their judgment and intuition. This technique is simple, fast and flexible, but it can be subjective, biased and inconsistent.
- **Analogy**: This technique uses the similarity between the current project and a previous similar project to derive estimates based on the historical data. This technique is easy, reliable and accurate, but it requires the availability and validity of the historical data and the similarity of the projects.
- **Parametric**: This technique uses a mathematical model or formula to calculate estimates based on the relationship between the project parameters and the project outcomes. This technique is objective, precise and scalable, but it requires the availability and validity of the model and the data, and the accuracy of the parameters.
- **Bottom-up**: This technique breaks down the project into smaller and more manageable units, such as tasks or activities, and estimates each unit separately. Then, the estimates of the units are aggregated to get the estimate of the whole project. This technique is detailed, accurate and realistic, but it can be time-consuming, complex and prone to errors.
- **Top-down**: This technique estimates the project as a whole based on the high-level information and assumptions. Then, the estimate of the project is allocated to the lower-level units, such as phases or activities. This technique is quick, simple and consistent, but it can be vague, inaccurate and unrealistic.
- **Three-point**: This technique uses three estimates for each unit of the project, such as the most likely, the optimistic and the pessimistic estimate. Then, the estimates are combined using a weighted average formula to get the final estimate. This technique is comprehensive, realistic and risk-aware, but it can be complex, subjective and uncertain.

Some of the mnemonics and learning tricks for the estimation techniques are:

- **EAP**: Expert, Analogy, Parametric. These are the three techniques that use historical data or models to estimate the project.
- **BUT**: Bottom-Up, Top-Down. These are the two techniques that use decomposition or aggregation to estimate the project.
- **TOM**: Three-point, Optimistic, Most likely, Pessimistic. These are the four terms that are used in the three-point technique to estimate the project.

### Schedule/Duration of Maintenance in software project management

- Software maintenance is the process of modifying, updating, or correcting a software system after its delivery to the customer.
- Software maintenance can be classified into four types: corrective, adaptive, perfective, and preventive.
- Corrective maintenance is the process of fixing errors or defects in the software system that affect its functionality or performance.
- Adaptive maintenance is the process of modifying the software system to cope with changes in the environment, such as new hardware, operating systems, or standards.
- Perfective maintenance is the process of enhancing the software system by adding new features, improving usability, or increasing efficiency.
- Preventive maintenance is the process of improving the software system's quality, reliability, or maintainability by removing potential errors or reducing complexity.
- The schedule or duration of software maintenance depends on several factors, such as:
  - The type and complexity of the software system
  - The quality and documentation of the software system
  - The availability and skill of the maintenance staff
  - The frequency and severity of the maintenance requests
  - The budget and resources allocated for the maintenance activities
- A common way to estimate the schedule or duration of software maintenance is to use the following formula:

  - Maintenance effort = A * Size * B * C * D * E
  - Where:
    - A is a constant that depends on the type of software system and the maintenance organization
    - Size is the size of the software system measured in lines of code or function points
    - B is a factor that reflects the quality of the software system and the documentation
    - C is a factor that reflects the type of maintenance (corrective, adaptive, perfective, or preventive)
    - D is a factor that reflects the skill and experience of the maintenance staff
    - E is a factor that reflects the environmental changes that affect the software system
  - The values of A, B, C, D, and E can be determined by using historical data, expert judgment, or empirical models.
- A mnemonic to remember the formula is: **M**aintenance **E**ffort = **A**ll **S**oftware **B**ecomes **C**rappy **D**ue to **E**nvironment
- An example of applying the formula is:

  - Suppose we have a software system of 10,000 lines of code that requires adaptive maintenance to run on a new operating system.
  - Assume that A = 0.2, B = 0.8, C = 1.2, D = 0.9, and E = 1.5
  - Then, the maintenance effort is:

    - Maintenance effort = 0.2 * 10,000 * 0.8 * 1.2 * 0.9 * 1.5
    - Maintenance effort = 2592 person-hours
  - If we have a maintenance team of 4 people working 8 hours per day, then the duration of the maintenance is:

    - Duration = 2592 / (4 * 8)
    - Duration = 81 days



# Constructive Cost Models (COCOMO) in software project management

- Constructive Cost Models (COCOMO) are a set of empirical models that estimate the effort, cost and schedule of software projects based on various input parameters such as size, complexity, quality, experience, etc.
- COCOMO was developed by Barry Boehm in 1981 and has been revised and extended over the years to adapt to different types of software projects and development environments.
- COCOMO consists of three levels of models: basic, intermediate and detailed, each with increasing accuracy and complexity.
- Basic COCOMO model estimates the effort and duration of a software project based on a single parameter: the number of delivered source lines of code (SLOC). It also assumes a nominal value for all other factors affecting the project.
- Intermediate COCOMO model refines the basic model by introducing 15 cost drivers that adjust the effort and duration estimates based on the characteristics of the software product, the hardware platform, the personnel and the project attributes.
- Detailed COCOMO model further refines the intermediate model by dividing the software project into different phases or modules and applying different effort multipliers and scale factors for each phase or module.
- COCOMO models use the following formula to estimate the effort (E) in person-months:

  E = a * (KLOC)^b * EM

  where a and b are constants derived from historical data, KLOC is the number of delivered source lines of code in thousands, and EM is the effort multiplier that accounts for the cost drivers.

- COCOMO models use the following formula to estimate the duration (D) in months:

  D = c * (E)^d * SCED

  where c and d are constants derived from historical data, E is the effort in person-months, and SCED is the schedule compression or expansion factor that accounts for the project deadline.

- COCOMO models can be used to support various software project management activities such as planning, budgeting, monitoring, controlling and risk analysis. They can also be used to compare different alternatives and trade-offs in software development.



### Resource Allocation Models (RAIM) in software project management

- Resource allocation is a process in project management that helps project managers identify the right resources, and assign them to project tasks in order to meet project objectives.
- Project resources can be material, equipment, financial, or human resources.
- Resource allocation is a critical step in the project management process, as it can affect the project's scope, quality, cost, and schedule.
- Resource allocation can help project managers to optimize the use of available resources, avoid resource conflicts and shortages, and improve project performance and profitability .
- Resource allocation models (RAIM) are tools and techniques that can help project managers to plan, monitor, and control the allocation of resources in software projects.
- Some examples of resource allocation models are:

  - **Resource leveling**: This model aims to balance the demand and supply of resources over the project duration, by adjusting the start and finish dates of tasks, or splitting tasks into smaller units. This model can help to reduce resource fluctuations, idle time, and overtime costs, but it can also increase the project duration and risk.
  - **Resource smoothing**: This model aims to minimize the variations in resource usage, by shifting tasks within their float (the amount of time a task can be delayed without affecting the project end date). This model can help to optimize resource utilization and avoid resource conflicts, but it can also reduce the flexibility and buffer of the project schedule.
  - **Resource aggregation**: This model aims to estimate the total amount of resources required for each period of the project, by adding up the resources needed for each task. This model can help to plan the budget and resource procurement, but it can also ignore the specific availability and constraints of resources.
  - **Resource allocation matrix**: This model aims to assign resources to tasks, by creating a table that shows the relationship between resources and tasks. This model can help to clarify the roles and responsibilities of resources, and identify the critical and non-critical tasks, but it can also be complex and time-consuming to create and update.

- A mnemonic to remember the four resource allocation models is **L-S-A-M**, which stands for Leveling, Smoothing, Aggregation, and Matrix.

# Software Project Management

Software project management is a proper way of planning and leading software projects. It is a part of project management in which software projects are planned, implemented, monitored, and controlled. Software project management involves the following activities:

- **Project initiation**: This is the first phase of software project management, where the project scope, objectives, deliverables, and stakeholders are defined. The project manager also identifies the risks, assumptions, and constraints that may affect the project.
- **Project planning**: This is the second phase of software project management, where the project manager develops a detailed plan for the project, including the schedule, budget, resources, quality standards, and communication methods. The project manager also defines the project milestones, tasks, and dependencies, and assigns roles and responsibilities to the project team members.
- **Project execution**: This is the third phase of software project management, where the project manager leads the project team to execute the project plan and deliver the software products. The project manager also monitors the project progress, performance, and quality, and reports the status to the stakeholders.
- **Project monitoring and control**: This is the fourth phase of software project management, where the project manager tracks and measures the project performance against the project plan, and identifies and resolves any issues or changes that may arise. The project manager also ensures that the project deliverables meet the quality standards and the stakeholder expectations.
- **Project closure**: This is the final phase of software project management, where the project manager formally closes the project and delivers the final products to the stakeholders. The project manager also evaluates the project outcomes, lessons learned, and best practices, and documents the project results and feedback.

Software project management is a complex and dynamic process that requires the project manager to have the skills and knowledge of software development, project management, and communication.
