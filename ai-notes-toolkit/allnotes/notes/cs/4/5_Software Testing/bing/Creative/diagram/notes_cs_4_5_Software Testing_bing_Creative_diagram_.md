

## Unit 1 - Review of Software Engineering

- Software engineering is the application of engineering principles and practices to the development and maintenance of software systems that meet the needs and expectations of users and stakeholders.
- Software engineering involves activities such as requirements analysis, design, implementation, testing, deployment, maintenance, and evolution of software systems.
- Software engineering also encompasses the management of software projects, the quality assurance of software products and processes, and the ethical and professional issues related to software engineering.
- Software engineering is a discipline that requires both technical and interpersonal skills, as well as creativity and problem-solving abilities.
- Software engineering is influenced by and interacts with other disciplines such as computer science, mathematics, engineering, psychology, sociology, and management.
- Software engineering is a dynamic and evolving field that responds to the changing needs and demands of society and technology.



### Overview of Software Evolution

- Software evolution is the continual development of a piece of software after its initial release to address changing stakeholder and/or market requirements .
- Software evolution is important because organizations invest large amounts of money in their software and are completely dependent on this software. Software evolution helps software adapt to new business needs, improve quality, fix defects, and cope with environmental changes.
- Software evolution refers to the dynamic behavior of software systems, as they are maintained and enhanced over their lifetimes. Software evolution is particularly important as systems in organizations become longer-lived.
- Software development and evolution can be thought of as an integrated, iterative process that can be represented using a spiral model. The spiral model combines the features of the waterfall model and the prototyping model, and adds a new element of risk analysis.
- The process of software evolution is driven by requests for changes and includes change impact analysis, change implementation, system testing, and system release. Requests for changes may come from different sources, such as users, customers, developers, or regulators.
- Software evolution is governed by some empirical laws, such as Lehman's laws, which describe the properties and behavior of evolving software systems. Some of these laws are:

  - Continuing change: A program that is used in a real-world environment must change, or else it becomes progressively less useful in that environment.
  - Increasing complexity: As a program evolves, its structure tends to become more complex, unless work is done to maintain or reduce it.
  - Self-regulation: The global activity of a software system tends to remain constant over its lifetime, unless there is a change in the operational environment or the requirements.
  - Conservation of familiarity: The incremental change in each release of a software system is approximately constant.
  - Continuing growth: The functionality of a software system tends to increase over its lifetime to maintain user satisfaction.
  - Declining quality: The quality of a software system will appear to decline unless it is rigorously maintained and adapted to operational environment changes.
  - Feedback system: Software evolution is a multi-level, multi-loop, multi-agent feedback system, and thus must be treated as such to achieve significant improvement over any reasonable base.

- SDLC stands for Software Development Life Cycle    .
- It is a process used in software engineering to design, develop, test, and deploy software applications    .
- It is a structured approach to software development that helps organizations to improve the quality of their software products, reduce costs, and minimize risks  .
- It consists of several phases that cover the entire life cycle of a software project, from the initial idea to the final delivery and maintenance   .
- The phases of SDLC are   :
  - Requirement analysis: This phase involves gathering and analyzing the needs and expectations of the stakeholders and users of the software   .
  - Planning: This phase involves defining the scope, objectives, budget, schedule, and resources of the software project   .
  - Software design: This phase involves creating the architectural and detailed design of the software, such as the data structures, algorithms, interfaces, and modules   .
  - Software development: This phase involves writing and testing the code of the software, following the design specifications and coding standards   .
  - Software testing: This phase involves verifying and validating the functionality, performance, usability, security, and quality of the software, using various testing techniques and tools   .
  - Software deployment: This phase involves delivering and installing the software to the target environment, such as a server, a cloud, or a device   .
  - Software maintenance: This phase involves providing support and updates to the software, such as fixing bugs, adding features, and enhancing performance   .
- There are different models of SDLC, such as waterfall, agile, iterative, spiral, and V-shaped, that vary in the order, frequency, and flexibility of the phases   .
- The choice of the SDLC model depends on the nature, size, complexity, and requirements of the software project, as well as the preferences and capabilities of the software team   .
- The benefits of using SDLC are  :
  - It provides a clear and consistent framework for software development, ensuring that all the aspects and stages of the project are covered and documented  .
  - It improves the communication and collaboration among the stakeholders and the software team, facilitating the alignment of the expectations and the feedback  .
  - It enhances the efficiency and effectiveness of the software development process, reducing the errors, delays, and rework  .
  - It increases the quality and reliability of the software product, meeting the standards and specifications of the software engineering discipline  .
  - It lowers the costs and risks of the software project, optimizing the use of the resources and minimizing the impact of the changes and issues  .

### Testing Process

The testing process is a set of activities that aim to verify and validate the quality of a software product. The testing process can be divided into four main phases: planning, analysis, design, and execution.

- Planning: In this phase, the test objectives, scope, strategy, resources, schedule, and deliverables are defined. The test plan document is created to guide the testing activities and ensure alignment with the project goals and requirements.
- Analysis: In this phase, the test requirements, specifications, and scenarios are identified and prioritized. The test cases and test data are derived from the test scenarios and the software specifications. The test coverage and traceability matrices are created to ensure completeness and consistency of the test cases.
- Design: In this phase, the test environment, test tools, test scripts, and test procedures are prepared and configured. The test cases and test data are reviewed and verified for accuracy and feasibility. The test cases and test data are also mapped to the test scenarios and the software specifications.
- Execution: In this phase, the test cases and test data are executed on the test environment using the test tools and test scripts. The test results and test logs are recorded and analyzed. The test defects and test incidents are reported and tracked. The test metrics and test reports are generated and communicated to the stakeholders.

The testing process is iterative and incremental, meaning that it can be repeated and refined throughout the software development life cycle. The testing process is also adaptive and flexible, meaning that it can be tailored and customized according to the specific needs and characteristics of the software project.



### Terminologies in Testing

- **Software Testing**: The process of verifying and validating that a software product or system meets the specified requirements and expectations of the stakeholders .
- **Software Testing Life Cycle (STLC)**: The sequence of activities performed during the testing process, from planning to closure .
- **Test Level**: A specific instantiation of a test process, such as unit testing, integration testing, system testing, or acceptance testing .
- **Test Type**: A group of test activities aimed at testing a component or system regarding one or more quality attributes, such as functional testing, performance testing, security testing, or usability testing .
- **Test Design Technique**: A procedure to derive and/or select test cases based on an analysis of the test basis, such as specification-based testing, structure-based testing, or experience-based testing .
- **Test Case**: A set of input values, execution preconditions, expected results and execution postconditions, developed for a particular objective or test condition, such as to exercise a particular program path or to verify compliance with a specific requirement .
- **Test Script**: A sequence of instructions for the execution of a test .
- **Test Data**: Data that exists (for example, in a database) before a test is executed, and that affects or is affected by the component or system under test .
- **Test Environment**: An environment containing hardware, instrumentation, simulators, software tools, and other support elements needed to conduct a test .
- **Test Execution**: The process of running a test on the component or system under test, producing actual result(s) .
- **Test Result**: The outcome of the test execution, such as pass, fail, inconclusive, blocked, etc .
- **Test Log**: A chronological record of relevant details about the execution of tests .
- **Test Report**: A document summarizing testing activities and results, and providing an evaluation of the component or system under test and the testing process .
- **Test Plan**: A document describing the scope, approach, resources and schedule of intended test activities. It identifies amongst others test items, the features to be tested, the testing tasks, who will do each task, degree of tester independence, the test environment, the test design techniques and entry and exit criteria to be used, and the rationale for their choice, and any risks requiring contingency planning .
- **Test Strategy**: A high-level description of the test levels to be performed and the testing within those levels for an organization or program (one or more projects) .
- **Test Policy**: A high-level document describing the principles, approach and major objectives of the organization regarding testing .
- **Test Objective**: A reason or purpose for designing and executing a test .
- **Test Basis**: The body of knowledge used as the basis for test analysis and design, such as requirements, design specifications, user stories, etc .
- **Test Coverage**: The degree, expressed as a percentage, to which a specified coverage item has been exercised by a test suite .
- **Test Oracle**: A source to determine expected results to compare with the actual result of the software under test .
- **Test Automation**: The use of software to perform or support test activities, such as test management, test design, test execution and test evaluation .
- **Test Tool**: A software product that supports one or more test activities, such as planning and control, specification, building initial files and data, test execution and test analysis .
- **Test Management**: The planning, estimating, monitoring and control of test activities, typically carried out by a test manager .
- **Test Analysis**: The activity that identifies test conditions by analyzing the test basis .

### Fault
- A fault is a defect or an error in the software that causes it to behave incorrectly or unexpectedly.
- A fault can be introduced at any stage of the software development life cycle, such as during requirements analysis, design, coding, testing, or maintenance.
- A fault can be classified into different types, such as:
  - Syntax fault: A fault that violates the rules of the programming language or the syntax of the code.
  - Semantic fault: A fault that causes the software to produce incorrect or undesired results or behavior.
  - Logic fault: A fault that results from a flaw in the algorithm or the logic of the software.
  - Data fault: A fault that occurs due to incorrect or inconsistent data or data structures.
  - Interface fault: A fault that arises due to mismatch or inconsistency between the components or modules of the software or between the software and its environment.
  - Performance fault: A fault that affects the efficiency, reliability, or usability of the software.
- A fault can be detected by various techniques, such as:
  - Static analysis: A technique that analyzes the software without executing it, such as by using code reviews, inspections, or tools.
  - Dynamic analysis: A technique that analyzes the software by executing it, such as by using testing, debugging, or monitoring.
  - Formal methods: A technique that uses mathematical models and proofs to verify the correctness and consistency of the software.
- A fault can be corrected by various methods, such as:
  - Debugging: A method that involves locating and fixing the fault in the code.
  - Refactoring: A method that involves improving the structure and quality of the code without changing its functionality.
  - Patching: A method that involves applying a small change or update to the software to fix the fault.
  - Reengineering: A method that involves redesigning and redeveloping the software to fix the fault and enhance its features.



### Failure

Failure is the inability of a software system or component to perform its required functions within specified performance requirements. Failure can occur due to various reasons, such as defects in the software design, coding, testing, deployment, or maintenance. Failure can also result from external factors, such as hardware malfunction, network outage, user error, or malicious attack. Failure can have serious consequences, such as loss of data, revenue, reputation, or even lives.

Some of the common reasons leading to software failure are:

- Unclear or changing software requirements: If the software requirements are not well-defined, understood, or agreed upon by the stakeholders, the software development process can become chaotic and inefficient. The software may not meet the expectations or needs of the users or clients, or may have to undergo frequent changes or revisions, leading to delays, rework, and increased costs.
- Lack of user involvement: If the users or clients are not involved in the software development process, the software may not reflect their actual needs, preferences, or feedback. The software may have usability, functionality, or compatibility issues that could have been avoided or resolved with proper user input and testing.
- Lack of communication between clients and developers: If the clients and developers do not communicate effectively and frequently, the software development process can suffer from misunderstandings, misalignment, or conflicts. The software may not meet the requirements or specifications of the clients, or may have quality, performance, or security issues that could have been prevented or detected with better communication and collaboration.
- Poor or no planning: If the software development process is not planned properly, the software may face various challenges, such as scope creep, budget overrun, schedule slippage, resource shortage, or technical debt. The software may not be delivered on time, within budget, or with the desired quality or functionality.
- Failure to focus: If the software development process is not focused on the core features or value proposition of the software, the software may become bloated, complex, or irrelevant. The software may have unnecessary or redundant features, or may lack the essential or differentiating features that make it competitive or attractive to the users or clients.
- Unclear or unrealistic goals: If the software development goals are not clear, measurable, achievable, relevant, or time-bound, the software development process can become directionless, inefficient, or ineffective. The software may not have a clear vision, purpose, or scope, or may have unrealistic or conflicting expectations or constraints.
- Unrealistic or unmanageable time frames or deadlines: If the software development time frames or deadlines are too short, too long, or too variable, the software development process can become stressful, rushed, or delayed. The software may not have enough time for proper design, development, testing, or deployment, or may have too much time for unnecessary or excessive changes or revisions.
- Insufficient or inadequate testing: If the software testing is not sufficient or adequate, the software may have undetected or unresolved defects, errors, or bugs that can affect its functionality, reliability, or security. The software may not meet the quality standards or expectations of the users or clients, or may cause failures or damages in the production environment.
- Lack of or poor documentation: If the software documentation is not available, complete, accurate, or updated, the software development process can become difficult, confusing, or inconsistent. The software documentation may not provide enough information or guidance for the developers, testers, users, or maintainers of the software, or may have errors or discrepancies that can affect the software quality or performance.
- Lack of or poor quality control: If the software quality control is not performed or performed poorly, the software may have defects, errors, or bugs that can affect its functionality, reliability, or security. The software quality control may not follow the best practices or standards for software development, testing, or deployment, or may not use the appropriate tools or methods for quality assurance or verification.
- Lack of or poor change management: If the software change management is not performed or performed poorly, the software may have issues with compatibility, integration, or configuration. The software change management may not follow the best practices or standards for software development, testing, or deployment, or may not use the appropriate tools or methods for change control or tracking.
- Lack of or poor risk management: If the software risk management is not performed or performed poorly, the software may face unexpected or undesirable outcomes, such as failures, damages, or losses. The software risk management may not identify, analyze, prioritize, mitigate, or monitor the potential risks or threats to the software development process or the software product.

### Oracles

- An oracle is a mechanism for determining whether a test has passed or failed  .
- An oracle compares the output of the system under test, for a given test-case input, to the expected output   .
- An oracle can be a human, a document, a program, or another system that provides the expected output   .
- An oracle can specify the expected output for all possible inputs, or only for specific inputs .
- An oracle can also specify constraints or properties that the output should satisfy, rather than exact values .
- An oracle can be derived from various sources, such as requirements, specifications, design, domain knowledge, or intuition  .
- An oracle can be complete, partial, inconsistent, or nonexistent  .
- A complete oracle can determine the correctness of any output  .
- A partial oracle can determine the correctness of some outputs, but not all  .
- An inconsistent oracle can give different or contradictory results for the same output  .
- A nonexistent oracle means that there is no way to determine the correctness of any output  .
- Oracles are important for software testing, because they provide the basis for evaluating the quality of the system under test  .
- Oracles are also challenging for software testing, because they can be difficult to obtain, implement, or apply  .
- Oracles can be affected by errors, ambiguities, incompleteness, or inconsistencies in the sources from which they are derived  .
- Oracles can also introduce errors, biases, or limitations in the testing process  .
- Oracles can be classified into different types, such as specification-based, program-based, implicit, explicit, heuristic, or metamorphic  .
- Specification-based oracles use the specifications of the system under test as the source of expected output  .
- Program-based oracles use another program that implements the same functionality as the system under test as the source of expected output  .
- Implicit oracles use the inherent properties or behavior of the system under test as the source of expected output  .
- Explicit oracles use the explicitly stated or predefined expected output as the source of expected output  .
- Heuristic oracles use the general rules or principles that guide the testing process as the source of expected output  .
- Metamorphic oracles use the relations or transformations between different test cases and their outputs as the source of expected output  .

### Impracticality of Testing All Data

- Testing all data is the process of executing a software system with every possible input value or combination of values to verify its correctness and reliability.
- Testing all data is impractical for most software systems because:
  - It is impossible to test all possible inputs for systems that have infinite or very large input domains, such as numerical or text processing software.
  - It is very costly and time-consuming to test all possible inputs for systems that have finite but complex input domains, such as graphical user interfaces or web applications.
  - It is unnecessary to test all possible inputs for systems that have simple or regular input domains, such as sorting or searching algorithms, because a small subset of inputs can cover the most important cases and reveal the most common errors.
- Testing all data is also impractical because:
  - It does not guarantee the absence of errors or defects in the software system, because some errors may only occur in specific contexts or situations that are not covered by the inputs.
  - It does not account for the quality attributes of the software system, such as usability, performance, security, or maintainability, that are not directly related to the inputs and outputs of the system.
  - It does not reflect the actual usage scenarios or user expectations of the software system, because some inputs may be more frequent or important than others, and some outputs may be more desirable or acceptable than others.
- Therefore, testing all data is not a feasible or effective strategy for software testing. Instead, software testers should use techniques such as equivalence partitioning, boundary value analysis, error guessing, or test case design heuristics to select a representative and meaningful subset of inputs that can achieve a high level of test coverage and quality assurance.



### Impracticality of Testing All Paths

- Testing all paths of a software system is impractical because the number of paths grows exponentially with the complexity of the system.
- For example, if a system has n independent binary decisions, then there are 2^n possible paths to test.
- Even for a small value of n, such as 10, the number of paths is 1024, which is too large to test exhaustively in a reasonable time.
- Moreover, some paths may be infeasible or unreachable due to logical or physical constraints, such as hardware limitations, user input, or error handling.
- Therefore, testing all paths of a software system is not only impractical, but also unnecessary and inefficient.

### Verification Methods

Verification methods are the techniques that are used to check that a software product meets its specifications and requirements. Verification ensures that the software is built correctly and does what it is supposed to do. Verification is also known as static testing, as it does not involve executing the software.

Some common verification methods in software engineering are:

- **Peer reviews**: This is an informal and easy way of reviewing the documents or the source code of the software with a group of peers, looking for errors, inconsistencies, and improvements. Peer reviews can be done by anyone who has some knowledge of the software, such as developers, testers, managers, or customers. ### Equivalence Class Testing

- Equivalence class testing reduces the number of test cases needed to achieve a certain level of coverage, by avoiding redundant or unnecessary test cases.
- Equivalence classes can be derived from the specification, design, or implementation of the software under test, depending on the level of testing.
- Equivalence classes can be either valid or invalid, depending on whether they represent valid or invalid inputs for the software under test.
- Valid equivalence classes are those that satisfy the input requirements or constraints of the software under test, and are expected to produce correct outputs.
- Invalid equivalence classes are those that violate the input requirements or constraints of the software under test, and are expected to produce error messages or exceptions.
- Test cases should be selected from both valid and invalid equivalence classes, to test both the normal and the exceptional behavior of the software under test.
- Equivalence class testing can be applied to both black-box and white-box testing, as well as to both functional and non-functional testing.
- Equivalence class testing can be combined with other techniques, such as boundary value analysis, decision table testing, or state transition testing, to enhance the effectiveness and efficiency of testing.

### Mutation Testing

Mutation testing is a form of white box testing in which testers change specific components of an application's source code to ensure a software test suite will be able to detect the changes. Changes introduced to the software are intended to cause errors in the program. Mutation testing is used to design new software tests and evaluate the quality of existing software tests. Mutation testing involves modifying a program in small ways.

The main steps of mutation testing are :

- Faults are introduced into the source code of the program by creating many versions called mutants. Each mutant has a single change from the original program, such as replacing an operator, changing a variable name, or deleting a statement.
- Test cases are applied to the original program and also to the mutant program. A test case is said to kill a mutant if it causes the mutant to produce a different output from the original program. A test case is said to be ineffective if it does not kill any mutant.
- The mutation score is calculated as the ratio of the number of killed mutants to the total number of mutants. The mutation score indicates the effectiveness of the test suite in detecting faults in the program. A high mutation score means that the test suite is able to find most of the faults introduced by mutation, while a low mutation score means that the test suite is missing many faults.

The benefits of mutation testing are :

- It helps to improve the quality and coverage of the test suite by identifying weak or redundant test cases.
- It helps to find subtle or hidden errors in the program that may not be detected by other testing techniques.
- It helps to measure the adequacy of the test suite in terms of fault detection capability.
- It helps to provide feedback and guidance to the testers on how to design better test cases.

The challenges of mutation testing are :

- It is computationally expensive and time-consuming, as it requires generating and executing many mutants and test cases.
- It may generate equivalent mutants, which are mutants that produce the same output as the original program for all test cases. Equivalent mutants cannot be killed by any test case and they reduce the mutation score artificially.
- It may generate trivial mutants, which are mutants that are easily killed by any test case. Trivial mutants do not provide much information about the quality of the test suite and they increase the mutation score artificially.
- It may require manual analysis and verification of the mutants and the test results, which can be tedious and error-prone.

This requires identifying the dependencies and impacts of the changes on the test cases, which can be done manually or with the help of traceability matrices or tools.
  - Regression test selection: This type of regression testing involves selecting a subset of test cases from the test suite that are most likely to detect defects caused by the changes. This requires applying some criteria or heuristics to prioritize and select the test cases, such as risk-based testing, test coverage, test history, or test cost.
  - Test case prioritization: This type of regression testing involves ordering the test cases in the test suite according to some criteria or heuristics, such as severity, frequency, complexity, or business value, and executing them in that order. This aims to increase the rate of fault detection and reduce the testing time.

## Techniques of Regression Testing

- There are different techniques of regression testing, depending on the methods and tools that are used to perform the retesting. Some common techniques are:

  - Manual regression testing: This technique involves retesting the software system manually by following the test cases and comparing the actual and expected results. This technique is simple but also prone to human errors, fatigue, and boredom.
  - Automated regression testing: This technique involves retesting the software system automatically by using test scripts and tools that can execute the test cases and verify the results. This technique is fast, reliable, and consistent, but also requires high initial investment, maintenance, and expertise.
  - Hybrid regression testing: This technique involves combining manual and automated regression testing, by using both test cases and test scripts to retest the software system. This technique can leverage the advantages of both manual and automated regression testing, but also requires coordination and integration between them.

### Software Test Plan

A software test plan is a document that describes the objectives, scope, approach, and focus of a software testing effort. It also includes the schedule, resources, risks, and deliverables of the testing activities.

A software test plan is usually prepared before the start of the testing phase, and it is updated and refined throughout the testing process. A software test plan helps to:

- Define the testing scope and coverage
- Identify the testing objectives and criteria
- Establish the testing strategy and methods
- Allocate the testing resources and responsibilities
- Estimate the testing effort and schedule
- Identify the testing risks and mitigation plans
- Define the testing deliverables and reporting mechanisms
- Communicate the testing expectations and assumptions to the stakeholders

A software test plan typically consists of the following sections:

- Introduction: This section provides an overview of the software test plan, its purpose, scope, objectives, and references.
- Test Items: This section lists the software items or features that are to be tested, and their versions, configurations, and dependencies.
- Features to be Tested: This section describes the functional and non-functional requirements or specifications that are to be verified by the testing activities.
- Features not to be Tested: This section specifies the requirements or specifications that are out of scope or not applicable for the testing activities.
- Approach: This section defines the overall testing strategy and methodology, such as the types, levels, techniques, and tools of testing to be applied.
- Item Pass/Fail Criteria: This section specifies the criteria or metrics for determining the success or failure of the testing activities, such as the defect severity, priority, and resolution status.
- Suspension Criteria and Resumption Requirements: This section defines the conditions or thresholds for suspending or resuming the testing activities, such as the number or type of defects, the availability of resources, or the completion of milestones.
- Test Deliverables: This section lists the documents, reports, data, or artifacts that are to be produced or delivered as a result of the testing activities, such as the test cases, test results, test logs, defect reports, or test summary reports.
- Testing Tasks: This section describes the tasks or activities that are to be performed as part of the testing process, such as the test planning, design, execution, evaluation, or closure.
- Environmental Needs: This section identifies the hardware, software, network, or other resources that are required to support the testing activities, such as the test environment, test data, test tools, or test personnel.

## Unit 6 - Object Oriented Testing

Object oriented testing is a testing technique that focuses on the behavior and structure of classes and objects in an object oriented system. Object oriented testing can be divided into two categories: class testing and system testing.

Class testing is the testing of individual classes and their methods, attributes, and interactions with other classes. Class testing can be further divided into state-based testing and interaction-based testing.

- State-based testing verifies the internal state of a class and its methods by checking the values of its attributes and the results of its operations. State-based testing can use techniques such as equivalence partitioning, boundary value analysis, and decision tables to generate test cases.
- Interaction-based testing verifies the external behavior of a class and its methods by checking the messages it sends and receives from other classes. Interaction-based testing can use techniques such as sequence diagrams, collaboration diagrams, and state transition diagrams to generate test cases.

System testing is the testing of the whole object oriented system and its functionality, usability, reliability, and performance. System testing can be further divided into scenario-based testing and use case-based testing.

- Scenario-based testing verifies the system's behavior and functionality by executing a sequence of actions and events that simulate a realistic situation. Scenario-based testing can use techniques such as user stories, storyboards, and scripts to generate test scenarios.
- Use case-based testing verifies the system's behavior and functionality by executing a sequence of actions and events that satisfy a user's goal. Use case-based testing can use techniques such as use case diagrams, use case specifications, and use case scenarios to generate test cases.

- Scenario-based testing: This technique involves testing the class as part of a larger system or scenario, using a sequence of actions and events that simulate a realistic use case. - Post deployment testing can be done using various strategies, such as:
  - Rolling update deployment: A subset of running application instances is updated instead of simultaneously updating every application instance.
  - Blue-green deployment: Two identical environments are created, one for production and one for testing. The traffic is switched between them after testing is completed.
  - Canary deployment: A small percentage of users are exposed to the new version of the software application and their feedback is collected before rolling out to the rest of the users.
  - Feature flags: A feature or functionality is enabled or disabled for a specific group of users or conditions using a configuration setting.
- Post deployment testing is an essential part of the software development life cycle and helps to ensure the quality, reliability, and user satisfaction of the software application.
