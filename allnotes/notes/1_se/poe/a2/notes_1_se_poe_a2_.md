### Software Crisis

1. Complex software - Software systems have become increasingly complex with more functionality and customization options. This makes software development challenging and prone to errors or bugs.
2. Shortage of skilled programmers - There is a shortage of programmers and software engineers with sufficient skills and experience to develop high quality software solutions. This leads to hiring of lesser skilled resources which results in poor quality software.

4. Time constraints - There are tight timelines to release software to meet business demands. This results in taking shortcuts and not spending enough time on quality assurance. Hence, the software ends up with many errors or bugs.
5. Software testing challenges - It is difficult and time consuming to test all features and options of a complex software system. This makes it hard to identify and fix all bugs before release. Some bugs may remain undetected until users detect and report them.

To address the software crisis, more skilled programmers should be trained. Software requirements should be better understood and frozen earlier. Adequate time should be spent on software testing and quality assurance. Automated testing tools can also help to improve software quality. With concerted efforts, the software crisis can be managed to a large extent.

### Prototype Model in SDLC

1. Prototyping is a software development model in which prototypes are developed to provide users an idea of how the final product will look like and work.
2. It involves iterative development of prototypes where each prototype is refined based on user feedback.
3. Prototypes can be of two types:

- Throwaway Prototypes: Prototypes that are eventually discarded and not part of the final product. They are developed to help understand user requirements.
- Evolutionary Prototypes: Prototypes that evolve into the final system through iterative refinements. Part of the final system is developed from the prototype.

4. The key steps involved in Prototype Model are:

- Identify basic requirements and assumptions
- Develop initial prototype
- Review prototype and gather feedback
- Refine prototype
- Repeat above two steps until acceptable prototype is achieved
- Deploy the system

5. The advantages of Prototype Model are:

- Users get an early idea of the system and can provide valuable feedback.
- Risks can be identified early and eliminated.
- Customizations can be incorporated easily.

6. The disadvantages of Prototype Model are:

- Insufficient analysis may lead to rework as hidden requirements may surface later.
- The cost of making changes increases as the process progresses.
- The model does not work well for large and complex systems.

### Spiral Model in SDLC

1. The spiral model is a software development process combining elements of both design and prototyping-in-stages, in an effort to combine advantages of top-down and bottom-up concepts.

2. The process is divided into four quadrants:

- Planning: Determine objectives, alternatives, and constraints of the iteration.
- Risk analysis: Identify and resolve risks and uncertainties.
- Engineering: Design and develop the product.
- Evaluation: Evaluate the product and review process.

3. The spiral model reduces risk by making development incremental. Each portion proceeds in a spiral, passing through the steps of planning, risk analysis, engineering and evaluation over and over.

4. Each loop around the spiral represents a phase in the process where the product is evaluated against new requirements and risks. The process allows for incremental releases of the product, or for phases of the project to be terminated if the risk is deemed too great.

5. The spiral model is best suited for large, expensive, complicated projects where software requirements are not well understood and risks are significant. The approach allows for incremental releases of the software, reducing risk and allowing requirements to change. The spiral model framework provides opportunities for user involvement in the system development.

## Unit 2 - Software Requirement Specifications (SRS)

- SRS is a formal document that captures all requirements for a software solution. It acts as a communication vehicle between customers and developers.
- It includes both functional and non-functional requirements. Functional requirements specify functions or capabilities a system must have, while non-functional requirements specify system properties such as performance, security, etc.
- SRS is usually created in the initial stages of SDLC by business analysts or requirements engineers after meeting with clients and stakeholders.
- Components of a good SRS:

- Introduction: Purpose, Scope, Definitions, References, Overview
- Overall Description: Product Perspective, System Features
- System Features: Functional requirements
- External Interface Requirements: User Interfaces, Hardware Interfaces, Software Interfaces, Communication Interfaces
- System Features: Non-functional requirements like Performance, Security, Safety, Reliability, etc.
- Other Requirements: Business Rules, Constraints, Assumptions,Dependencies

- Benefits of SRS: Helps bridge communication gap between stakeholders, Acts as a reference throughout the project, Increases productivity by avoiding rework, Reduces cost and time, Improves quality as requirements are clearly documented.

- Best practices for writing SRS:

- Use simple and clear language
- Be precise and unambiguous
- Prioritize requirements
- modularize the document
- Use diagrams/examples to enhance understanding
- Review and verify the SRS

### Review and Management of User Needs in Requirement Engineering Process in SRS

### Feasibility Study in Software Requirement Specification (SRS)

- Technical Feasibility: This checks if the technology needed to develop the software is available or not. Things to consider are:
- Do we have the required expertise available?
- Do we have the required infrastructure, tools, and software available?
- Is the technology stable and mature enough to be used?

- Economic Feasibility: This checks if the software can be developed within the budget constraints. Things to consider are:
- Cost of resources (hardware, software)
- Cost of development (salaries, infrastructure, etc.)
- Cost of maintenance
- Expected revenue from the software
- If expected revenue > cost, then economically feasible else not.

- Legal Feasibility: This checks if the software meets the legal and regulatory requirements. Things to consider are:
- Licenses and agreements required
- Laws and regulations to be adhered to (privacy, security, etc.)
- If the software is violating any existing laws or agreements, then it is not legally feasible.

- Operational Feasibility: This checks if the software can be integrated with existing systems and if the organization is capable of handling the changes brought about by the software. Things to consider are:
- Changes required in the existing infrastructure/software/skills to accommodate the new software
- If the organization can bear the resource and operational changes required, then it is operationally feasible else not.

The above feasibility checks help determine if the SRS can actually be implemented or not. Only if all the feasibility studies result in a positive outcome should the SRS be accepted and implemented.

### Data Flow Diagrams in Software Requirement Specification (SRS)

1. Data Flow Diagrams (DFDs) are graphical representations of the "flow" of data through an information system. They can be used to model processes or systems.
2. DFDs depict processes, data stores, data flows, and sources/sinks in a system. They show the flow of data between processes, data stores, and terminals.
3. In SRS, DFDs are used to model the functionality of the system and identify the interfaces between the system and external entities. They provide an overview of the system and how it interacts with the outside world.
4. The top level DFD shows the entire system as a single process and the input/outputs from/to the external entities as a whole. Then, successive lower-level DFDs break down this single process into a series of sub-processes.
5. DFDs help to understand the system in a graphical and structured manner. They facilitate communication between stakeholders, uncover additional requirements, and tackle complexity by breaking down the system hierarchically.
6. However, DFDs cannot capture sequencing/timing information, exception conditions, and attribute information. They do not explicitly specify data types and may become complex as we go into lower levels.

### Entity Relationship Diagrams in Software Requirement Specification (SRS)

### Decision Tables in Software Requirement Specification (SRS)

- Decision tables are a useful way to specify conditional logic in software requirements.
- They show the combination of conditions and the corresponding outcomes in a tabular format.
- Each column in a decision table represents a condition or set of conditions. Each row shows a unique combination of conditions and the associated outcome.
- Decision tables are useful to specify complicated business rules or complex logic. They provide a comprehensive view of various scenarios and their expected outputs.
- While writing decision tables in SRS, follow these guidelines:

- Clearly state the purpose and usage of the decision table.
- Identify all input conditions and list them in the first column. Ensure there are no duplication or overlap between conditions.
- List all possible combinations of conditions in separate rows. The number of rows depends on the number of conditions.

### Basic Concept of Software Design

##### Cyclomatic Complexity Measures in software design

1. Cyclomatic complexity: It is a software metric used to indicate the complexity of a program. It is computed as:

M = E - N + 2P

Where E is the number of edges of the graph, N is the number of nodes of the graph, and P is the number of connected components.

A lower value of Cyclomatic Complexity indicates simpler code which is easier to understand, test and maintain. A higher value indicates more complex code which is difficult and error prone.

2. Essential Complexity: It is the minimum Cyclomatic Complexity required to satisfy all the requirements of a system. It gives a measure of the inherent complexity of the problem being solved.

3. Accidental Complexity: It is the difference between total Cyclomatic Complexity and Essential Complexity. It arises due to poor design choices and can be reduced by proper design techniques.

4. Nesting Level: It is a measure of how functions/modules are nested within each other. A higher nesting level indicates more complex code which is difficult to understand and debug. Nesting should be minimized to improve comprehensibility.

###### Control Flow Graphs in software design

1. Control flow graphs are a way to represent all paths that might be traversed through a program during its execution.
2. They are made up of nodes and directed edges.
    - Nodes represent points where control flow decisions are made or where control flow merges.
    - Directed edges represent the possible transfers of control from one node to another.
3. Control flow graphs are useful for:
    - Visualizing and understanding the control flow of a program.
    - Detecting structural problems like infinite loops.
    - Optimizing code by identifying independent paths that can be executed in parallel.
4. To construct a control flow graph:
    - Identify all possible execution paths through the code.
    - Represent each point where control flow changes as a node.
    - Draw directed edges between nodes to show all possible transitions.
5. Limitations:
    - Control flow graphs can become complex for long or convoluted programs.
    - They only show control flow and do not reveal data flows or other aspects of program execution.
    - Loops must be unrolled in some way which can introduce inefficiencies.

### Need for Maintenance and Maintenance Planning

1. Preventive maintenance: Regular maintenance of equipment helps to identify and rectify minor faults or wear and tear before they lead to major failures. This increases the operational life of the equipment and reduces downtime.

Maintenance planning involves the following steps:

1. Data collection: Operational data such as number of hours for which equipment functioned without failure, types of past failures, etc. are collected. This helps in assessing the maintenance requirements of the equipment.

2. Evaluation: The collected data is evaluated to analyze the maintenance needs of the equipment. The types of maintenance required are identified for each equipment.

3. Maintenance scheduling: Based on the evaluation, a maintenance schedule is prepared, specifying the types of maintenance, frequency of maintenance, and time required for maintenance for each equipment. The schedule is prepared such that it does not disrupt production.

- Static analysis - examining source code, executable code, documentation.
- Dynamic analysis - analyzing the software during execution using debugging, tracing or monitoring.
- Decompilation - converting executable code into a higher-level language.
- Pattern analysis - identifying repetitive patterns in the software to infer its structure.

### Constructive Cost Models (COCOMO) in software project management.

1. COCOMO stands for Constructive Cost Models. It is a regression model based on lines of code, used to estimate effort, cost, and schedule when planning software projects.
2. COCOMO was created by Barry Boehm in 1981. It provides a basic way to estimate software development effort based on program size expressed in estimated lines of code (LOC).
3. There are three COCOMO models:
- Basic COCOMO: Estimates effort and cost. Requires only one input - lines of code.
- Intermediate COCOMO: Estimates effort, cost, and schedule. Requires four inputs - lines of code, program type, hardware constraints, personnel quality.
- Detailed COCOMO: Estimates effort, cost, and schedule. Requires 15 inputs related to software, hardware, personnel, etc.
4. The COCOMO models use effort to derive estimates of cost and schedule. Effort is expressed in person-months or person-years. These metrics can then be converted to time and cost. The more complex the software, the more effort and cost is required.
5. advantages:
- COCOMO is simple and easy to use.
- It relates program size to effort, so it is understandable and credible.
- It has been widely used and tested on many projects.
- Disadvantages:
- The COCOMO models are quite crude and the estimates can be inaccurate.
- The input parameters are difficult to estimate.
- COCOMO does not adequately consider factors like software complexity and team capability.

### Resource Allocation Models (RAIM) in software project management

1. Resource allocation involves determining how to deploy limited resources to tasks to meet project objectives. Some key resource allocation models in software project management are:
- Linear Programming: Determines the optimal allocation of resources to tasks to minimize costs or maximize benefits while meeting constraints. It handles resource constraints and is useful for small-sized projects.
- Graph Modelling: Models the project as a network with tasks as nodes and dependencies as arcs. It can handle intertask dependencies but does not consider resource constraints. Useful for medium-sized projects.
- Heuristic Methods: Use rules of thumb to arrive at a near-optimal solution. They are fast but do not guarantee optimal solutions. Useful for large and complex projects.
- Simulation: Creates a model of the project and simulates it under different resource allocations to determine the best option. It can handle complexity and uncertainty but requires significant time and effort. Useful for risk analysis.

2. The appropriate RAIM depends on project size and complexity. Project managers must evaluate RAIMs based on parameters like time, cost, and resource constraints; level of precision required; and project scale to determine the suitable approach for a given project. The final allocation plan should efficiently meet project objectives within resource constraints.

3. In summary, RAIMs are tools to optimize resource allocation to tasks in software projects. Project managers must choose an appropriate model based on project needs and complexity. The optimal plan should maximize benefits or minimize costs while meeting time, cost, and resource constraints.
