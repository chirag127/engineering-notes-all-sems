

## Unit 1 - Review of Software Engineering

Software engineering is the systematic application of engineering approaches to the development of software. It involves the use of principles and practices from computer science, project management, and other fields to design, implement, test, and maintain software systems.

Some key points to remember about software engineering include:

1. Software engineering is concerned with all aspects of software production, from the early stages of system specification to maintaining the system after it has been put into use.

2. Software engineering involves the use of various tools, techniques, and methodologies to ensure that software is developed in a systematic, disciplined, and quantifiable manner.

3. The goal of software engineering is to produce high-quality software that meets the needs of its users, is delivered on time, and is developed within budget.

4. Software engineering is a collaborative process that involves working with stakeholders, including customers, users, and other members of the development team, to ensure that the software meets their needs.

5. Software engineering is an iterative process, with each iteration building upon the previous one to improve the software and bring it closer to the final product.

6. Software engineering involves the use of various software development models, such as the waterfall model, the agile model, and the spiral model, to guide the development process.

7. Software engineering is a constantly evolving field, with new tools, techniques, and methodologies being developed to improve the software development process.

8. Software engineering is a challenging and rewarding field, with many opportunities for growth and advancement for those who are skilled in the field.



### Overview of Software Evolution

Software evolution refers to the process of developing software initially, then repeatedly updating or improving it. This is an important aspect of software engineering, as it enables software to adapt to changing user needs and environments.

1. **Software maintenance:** This is the process of modifying a software system or component after delivery, to correct faults, improve performance or other attributes, or adapt to a changed environment.
2. **Software reengineering:** This is the examination and alteration of a software system to reconstitute it in a new form, and the subsequent implementation of the new form.
3. **Software migration:** This is the process of moving from one operating environment to another. This can include moving from one hardware platform to another, from one operating system to another, or from one application server to another.
4. **Software retirement:** This is the process of phasing out a software system, typically because it has been replaced by a newer system or because it is no longer needed.

These processes are important for ensuring that software remains useful and relevant over time. They can help to extend the lifespan of software, reduce maintenance costs, and improve user satisfaction.



### SDLC for the notes of the Unit 1 - Review of Software Engineering in the subject of Software Testing

SDLC, or Software Development Life Cycle, is a process used by the software industry to design, develop, and test high-quality software. The SDLC aims to produce high-quality software that meets or exceeds customer expectations, reaches completion within times and cost estimates, and works effectively and efficiently in the current and planned IT infrastructure.

The SDLC process includes the following stages:

1. **Planning:** This stage involves determining the scope of the project, identifying the resources required, and developing a project plan.

2. **Analysis:** During this stage, the requirements of the software are gathered and analyzed. This includes understanding the needs of the users, the business, and any technical constraints.

3. **Design:** In this stage, the software is designed based on the requirements gathered in the analysis stage. This includes creating a detailed design of the software, including the user interface, data structures, and algorithms.

4. **Implementation:** During this stage, the software is actually developed and coded. This includes writing the code, testing it, and integrating it with other software components.

5. **Testing:** In this stage, the software is tested to ensure that it meets the requirements and is free of defects. This includes unit testing, integration testing, system testing, and acceptance testing.

6. **Deployment:** Once the software has been tested and is ready for release, it is deployed to the production environment.

7. **Maintenance:** After the software has been deployed, it enters the maintenance stage. This includes fixing any defects that are discovered, as well as adding new features and enhancements.

The SDLC process is an iterative process, with each stage building on the previous one. It is important to follow the SDLC process to ensure that the software is of high quality and meets the needs of the users.



### Testing Process

The testing process is a critical part of software engineering and is used to ensure that software meets the specified requirements and is free from defects. The process typically involves the following steps:

1. **Planning:** The first step in the testing process is to plan the testing activities. This includes identifying the objectives of testing, selecting the testing techniques to be used, and determining the resources required for testing.

2. **Design:** The next step is to design the test cases. This involves identifying the inputs and expected outputs for each test case, as well as the conditions under which the test case will be executed.

3. **Execution:** Once the test cases have been designed, they are executed. This involves running the software with the specified inputs and comparing the actual outputs with the expected outputs.

4. **Reporting:** After the test cases have been executed, the results are reported. This includes documenting any defects that were found, as well as any other issues that were encountered during testing.

5. **Verification:** The final step in the testing process is to verify that the defects that were found have been fixed. This involves re-running the test cases to ensure that the software now behaves as expected.

The testing process is an iterative one, with each iteration involving the execution of a set of test cases and the reporting and verification of any defects that are found. The process continues until all defects have been fixed and the software meets the specified requirements.



### Terminologies in Testing

1. **Software Testing**: The process of evaluating a system or its component(s) with the intent to find whether it satisfies the specified requirements or not.
2. **Test Case**: A set of conditions or variables under which a tester will determine whether a system under test satisfies requirements or works correctly.
3. **Test Suite**: A collection of test cases that are intended to be used to test a software program to show that it has some specified set of behaviors.
4. **Test Plan**: A document describing the scope, approach, resources, and schedule of intended test activities. It identifies test items, the features to be tested, the testing tasks, who will do each task, and any risks requiring contingency planning.
5. **Test Scenario**: A test scenario is a description of an objective a user might face when using the program. It is used to ensure that all possible scenarios are considered when testing.
6. **Test Script**: A test script is a set of instructions that will be performed on the system under test to test that the system functions as expected.
7. **Test Harness**: A test harness is a collection of software and test data configured to test a program unit by running it under varying conditions and monitoring its behavior and outputs.
8. **Test Driver**: A test driver is a program that sets up the test environment, executes the tests, and reports the results.
9. **Test Stub**: A test stub is a small program that simulates the behavior of a software component that a module undergoing tests depends on.
10. **Test Data**: Test data is data that has been specifically identified for use in tests, typically of a computer program.

### Impracticality of Testing All Data

1. **Exhaustive testing is impossible:** Testing all possible data inputs and scenarios is impractical and time-consuming. The number of possible test cases for even simple software can be very large.

2. **Diminishing returns:** As more and more tests are performed, the likelihood of finding new defects decreases. At some point, the cost of testing outweighs the benefits.

3. **Risk-based testing:** Instead of attempting to test all data, it is more practical to prioritize testing based on the likelihood and impact of potential failures. This approach is known as risk-based testing.

4. **Testing can never prove the absence of defects:** Even if all possible tests were performed, it is still possible for defects to exist in the software. Testing can only show the presence of defects, not their absence.

5. **Limited resources:** Time, budget, and personnel constraints limit the amount of testing that can be performed. It is important to use these resources effectively by focusing on the most important tests.

6. **Changing requirements:** Software requirements often change during development, making it difficult to test all data. Testing must be flexible and adapt to these changes.

7. **Complexity of software:** Modern software systems are often very complex, with many interacting components. It is difficult to test all possible interactions and scenarios.

In summary, it is impractical to test all data in software testing. A more practical approach is to prioritize testing based on risk and to use resources effectively. Testing can never prove the absence of defects, so it is important to focus on finding the most critical defects.



### Impracticality of Testing All Paths

1. **Exponential growth of paths:** The number of possible paths in a program grows exponentially with the number of decisions. This makes it impractical to test all paths, even for small programs.

2. **Infeasible paths:** Not all paths in a program are feasible, meaning that some paths cannot be executed due to the program's logic. Attempting to test all paths would include testing infeasible paths, which is a waste of time and resources.

3. **Limited resources:** Testing all paths would require a large amount of time, money, and human resources. These resources are limited and must be used efficiently.

4. **Diminishing returns:** The more paths that are tested, the less likely it is that additional testing will uncover new defects. At some point, the cost of testing additional paths outweighs the benefits.

5. **Risk-based approach:** A more practical approach is to prioritize testing based on the risk associated with each path. High-risk paths are tested first, while low-risk paths may not be tested at all.

In summary, testing all paths in a program is impractical due to the exponential growth of paths, the presence of infeasible paths, limited resources, diminishing returns, and the need for a risk-based approach. Instead of attempting to test all paths, it is more efficient to prioritize testing based on risk.
