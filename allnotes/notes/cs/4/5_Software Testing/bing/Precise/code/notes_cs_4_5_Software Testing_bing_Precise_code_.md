

## Unit 1 - Review of Software Engineering

Software engineering is the systematic application of engineering approaches to the development of software. It involves the use of principles, methods, and tools to design, develop, test, and maintain software systems.

Some key points to remember about software engineering include:

1. Software engineering is concerned with the entire software development life cycle, from requirements gathering to maintenance and evolution of the software system.
2. Software engineering involves the use of various methodologies, such as agile development, waterfall, and spiral, to manage the software development process.
3. Software engineering involves the use of various tools, such as integrated development environments (IDEs), version control systems, and testing frameworks, to support the development process.
4. Software engineering involves the use of various techniques, such as object-oriented design, design patterns, and refactoring, to improve the quality of the software system.
5. Software engineering involves the use of various quality assurance techniques, such as testing, code reviews, and static analysis, to ensure the reliability and correctness of the software system.




### Overview of Software Evolution

Software evolution refers to the process of developing software initially, then repeatedly updating or improving it. This is an important aspect of software engineering, as it enables software to adapt to changing user needs and environments.

1. **Software maintenance:** This refers to the modification of a software product after delivery to correct faults, improve performance, or adapt to a changing environment.

2. **Software evolution process:** This process involves the continuous adaptation and transformation of software to meet changing requirements and environments. It includes activities such as requirements analysis, design, implementation, testing, and maintenance.

3. **Lehman's laws of software evolution:** These laws, proposed by Meir M. Lehman in 1974, describe the behavior of software systems as they evolve. Some of these laws include the law of continuing change, the law of increasing complexity, and the law of self-regulation.

4. **Software reengineering:** This refers to the examination and alteration of a software system to reconstitute it in a new form. It involves the application of software engineering techniques to improve the structure, performance, and maintainability of the system.

5. **Reverse engineering:** This is the process of analyzing a software system to identify its components and their relationships, and to create representations of the system in another form or at a higher level of abstraction.

6. **Software migration:** This refers to the process of moving a software system from one platform or operating environment to another. It involves the adaptation of the software to the new environment, as well as the transfer of data and other components.

7. **Software retirement:** This refers to the process of phasing out a software system that has become obsolete or is no longer needed. It involves the removal of the system from service, as well as the transfer of data and other components to a new system.

In summary, software evolution is an important aspect of software engineering that enables software systems to adapt to changing requirements and environments. It involves a range of activities, including maintenance, reengineering, reverse engineering, migration, and retirement. Understanding these concepts is essential for the effective management of software systems over their lifecycle.



### SDLC for the notes of the Unit 1 - Review of Software Engineering in the subject of Software Testing

SDLC (Software Development Life Cycle) is a process used by the software industry to design, develop and test high-quality software. The SDLC aims to produce a high-quality software that meets or exceeds customer expectations, reaches completion within times and cost estimates.

Here are the key stages of the SDLC:

1. **Planning**: In this stage, the project team defines the overall objectives and scope of the project, identifies potential risks, and develops a project plan.

2. **Analysis**: During the analysis stage, the project team works with stakeholders to gather and analyze requirements. This stage is critical to the success of the project, as it lays the foundation for the design and development stages.

3. **Design**: In the design stage, the project team develops a detailed design for the software system. This includes creating a technical specification, which outlines how the system will be built, and designing the user interface.

4. **Development**: During the development stage, the project team builds the software system according to the design. This includes writing code, testing individual components, and integrating the components into a working system.

5. **Testing**: In the testing stage, the project team tests the software system to ensure that it meets the requirements and performs as expected. This includes conducting unit tests, integration tests, and system tests.

6. **Deployment**: Once the software system has passed testing, it is deployed to the production environment. This may involve installing the software on the customer's hardware, configuring the system, and training users.

7. **Maintenance**: After the software system is deployed, the project team provides ongoing support and maintenance. This includes fixing bugs, adding new features, and updating the system to keep up with changing business needs.

Each stage of the SDLC is important and plays a critical role in the success of a software project. By following a structured process, project teams can ensure that they deliver high-quality software on time and within budget.



### Testing Process

The testing process is an integral part of software engineering and is used to ensure that the software meets the specified requirements and is free from defects. The testing process typically involves the following steps:

1. **Planning:** In this phase, the test strategy is developed, and the objectives of testing are defined. The test plan is created, which outlines the scope, approach, resources, and schedule of the testing activities.

2. **Design:** In this phase, test cases are designed to cover all the possible scenarios and use cases. The test cases should be designed to ensure maximum coverage of the software requirements.

3. **Execution:** In this phase, the test cases are executed, and the results are recorded. Any defects or issues found during the testing are reported and tracked.

4. **Reporting:** In this phase, the results of the testing are analyzed, and a test report is generated. The test report provides information on the quality of the software and any issues that were found during the testing.

5. **Maintenance:** In this phase, the test cases are maintained and updated as the software evolves. This ensures that the test cases remain relevant and effective in identifying defects in the software.

The testing process is an iterative process, and it is important to continually review and improve the testing activities to ensure that the software is of high quality and meets the specified requirements.



### Terminologies in Testing

1. **Testing**: The process of evaluating a system or its component(s) with the intent to find whether it satisfies the specified requirements or not.
2. **Test Case**: A set of conditions or variables under which a tester will determine whether a system under test satisfies requirements or works correctly.
3. **Test Suite**: A collection of test cases that are intended to be used to test a software program to show that it has some specified set of behaviors.
4. **Test Plan**: A document describing the scope, approach, resources, and schedule of intended test activities. It identifies test items, the features to be tested, the testing tasks, who will do each task, and any risks requiring contingency planning.
5. **Test Scenario**: A test scenario is a description of an objective a user might face when using the software. It is used to ensure that all possible scenarios are considered when testing.
6. **Test Script**: A test script is a set of instructions that will be performed on the system under test to test that the system functions as expected.
7. **Test Harness**: A test harness is a collection of software and test data configured to test a program unit by running it under varying conditions and monitoring its behavior and outputs.
8. **Test Driver**: A test driver is a program that is used to execute tests on the system under test.
9. **Test Stub**: A test stub is a small program that simulates the behavior of a component that the system under test interacts with.
10. **Test Data**: Test data is data that is used in tests of a software system.

These are some of the basic terminologies used in the field of software testing. It is important to understand these terms in order to effectively communicate and understand the testing process.



### Error
- An error is a human action that produces an incorrect or unexpected result.
- In the context of software engineering, an error refers to a mistake made by a developer while designing or coding a software program.
- Errors can occur at any stage of the software development process, including requirements gathering, design, coding, testing, and maintenance.
- Common causes of errors in software development include miscommunication, lack of understanding of the problem domain, incorrect assumptions, and programming mistakes.
- Errors can result in software defects, which can cause the software to behave in unexpected ways or fail to meet its intended purpose.
- To prevent errors, software development teams can use various techniques such as code reviews, pair programming, and automated testing.
- It is important to identify and correct errors early in the development process to minimize their impact and reduce the cost of fixing them later on.



### Fault
- A fault, also known as a defect or a bug, is an error or flaw in a software system that can cause the system to behave in unintended ways.
- Faults can occur at any stage of the software development process, from requirements gathering to design, coding, testing, and maintenance.
- Faults can be introduced by human error, such as a mistake in coding or a misunderstanding of the requirements, or by environmental factors, such as hardware failure or changes in the operating system.
- The goal of software testing is to identify and remove faults from the system before it is released to the end user.
- Faults can be classified into different types, such as syntax errors, logic errors, and runtime errors.
- Faults can also be categorized based on their severity, with critical faults having the potential to cause significant harm to the system or its users, while minor faults may have little or no impact on the system's functionality.
- The process of identifying and removing faults from a software system is known as debugging.
- Debugging can be a time-consuming and complex process, and it is important to have a systematic approach to identifying and fixing faults.
- Techniques such as code reviews, static analysis, and dynamic testing can be used to identify faults in the system.
- Once a fault has been identified, it can be fixed by making changes to the code or design of the system.
- It is important to verify that the fix has been successful and that it has not introduced any new faults into the system.
- The goal of software engineering is to develop high-quality software systems with as few faults as possible. This can be achieved through the use of best practices, such as following a well-defined software development process, using appropriate tools and techniques, and conducting thorough testing of the system.



### Failure

- Failure is an event that occurs when the delivered service of a software system deviates from its expected behavior.
- Failure is the inability of a system or component to perform its required functions within specified performance requirements.
- Failure can occur due to various reasons such as incorrect implementation, incorrect requirements, incorrect design, or incorrect testing.
- Failure can have serious consequences such as loss of data, loss of revenue, or even loss of life.
- Failure can be detected through testing, monitoring, or user feedback.
- Failure can be prevented or mitigated through proper design, implementation, testing, and maintenance.
- Failure can be classified into different types such as functional failure, performance failure, security failure, or usability failure.
- Failure can be measured in terms of its severity, frequency, and impact.
- Failure can be managed through proper risk management, incident management, and problem management processes.
- Failure is an important aspect of software engineering and should be carefully considered throughout the software development lifecycle.

### Difference Between Verification and Validation

Verification and validation are two important concepts in software engineering. They are often used together to ensure that a software product meets the requirements and specifications of the user. However, they are two distinct processes with different objectives.

1. **Verification** is the process of checking that a product, system, or component meets specified requirements. It is a static process, meaning that it does not involve executing the code. Instead, it involves reviewing documents, conducting inspections, and performing other activities to ensure that the product is being developed according to the specified requirements.

2. **Validation**, on the other hand, is the process of evaluating a system or component during or at the end of the development process to determine whether it satisfies the specified requirements. It is a dynamic process, meaning that it involves executing the code and testing the product to ensure that it meets the user's needs.

In summary, verification is concerned with ensuring that the product is being built correctly, while validation is concerned with ensuring that the right product is being built. Both processes are important for ensuring the quality of a software product.

### Oracles

An oracle is a mechanism for determining whether a software system has passed or failed a test. It is a source of expected outcome for a test case. Oracles can be derived from various sources, including:

1. **Specification-based oracles:** These oracles are derived from the system's specifications or requirements. They compare the system's behavior with its expected behavior as described in the specifications.

2. **Program-based oracles:** These oracles are derived from the system's code. They use the system's internal data structures and algorithms to determine the expected outcome of a test.

3. **Heuristic-based oracles:** These oracles use heuristics or rules of thumb to determine the expected outcome of a test. They are often used when the expected outcome is not precisely defined.

4. **History-based oracles:** These oracles use the system's past behavior to determine the expected outcome of a test. They are often used in regression testing to ensure that the system's behavior has not changed.

5. **User-based oracles:** These oracles rely on the user's judgment to determine the expected outcome of a test. They are often used in usability testing to ensure that the system is easy to use.

Oracles are an essential part of software testing, as they provide a means of determining whether a test has passed or failed. However, they are not always perfect, and there may be situations where the oracle is unable to determine the expected outcome of a test. In such cases, additional testing or analysis may be required to determine the system's behavior.



### Impracticality of Testing All Data

1. **Time-consuming:** Testing all possible data combinations is impractical because it would take an enormous amount of time to complete.
2. **Expensive:** The cost of testing all data combinations would be prohibitively high.
3. **Redundant:** Many data combinations may be similar or equivalent, making it unnecessary to test all of them.
4. **Diminishing returns:** The benefit of testing all data combinations decreases as the number of combinations increases, as the likelihood of finding new defects decreases.
5. **Infeasible:** In some cases, it may be impossible to test all data combinations due to limitations in resources or technology.

In summary, it is impractical to test all data combinations due to the time, cost, redundancy, diminishing returns, and infeasibility of doing so. Instead, a more practical approach is to use techniques such as risk-based testing, equivalence partitioning, and boundary value analysis to select a representative subset of data combinations to test.



### Impracticality of Testing All Paths

- Testing all paths in a software system is often impractical or even impossible due to the large number of possible paths.
- The number of possible paths increases exponentially with the number of decisions in the code.
- Even for relatively small programs, the number of paths can quickly become unmanageable.
- Testing all paths would require a large amount of time and resources, which is often not feasible in a real-world development environment.
- Instead of attempting to test all paths, testers typically use techniques such as risk analysis, equivalence partitioning, and boundary value analysis to select a representative subset of paths to test.
- These techniques help to identify the most important paths to test, while reducing the overall testing effort.
- In summary, while testing all paths in a software system may seem like a desirable goal, it is often impractical and unnecessary. Testers can use various techniques to select a representative subset of paths to test, which can provide a high level of confidence in the quality of the software without requiring an exhaustive testing effort.
