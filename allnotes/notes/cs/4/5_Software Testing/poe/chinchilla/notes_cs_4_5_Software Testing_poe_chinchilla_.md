

## Unit 1 - Review of Software Engineering

Software engineering is a discipline that involves the application of engineering principles to the development of software. It involves the use of a systematic and disciplined approach to the design, development, and maintenance of software. In this unit, we will review the basic concepts and principles of software engineering.

### Software Engineering Process

The software engineering process involves a series of steps that are followed in order to develop software. The steps in the software engineering process include:

1. Requirements gathering: This involves gathering information about the requirements of the software from the user or client.

2. Analysis and design: In this step, the requirements are analyzed, and a design is created that meets those requirements.

3. Implementation: This is the stage where the software is developed using programming languages and tools.

4. Testing: The software is tested to ensure that it meets the requirements and operates as expected.

5. Deployment: The software is deployed to the end-users.

6. Maintenance: The software is maintained to ensure that it continues to operate as expected.

### Software Development Life Cycle (SDLC)

The software development life cycle (SDLC) is a framework that outlines the steps involved in the development of software. The steps in the SDLC include:

1. Planning: This involves defining the goals and objectives of the software.

2. Analysis: In this stage, the requirements of the software are gathered and analyzed.

3. Design: A design is created for the software.

4. Implementation: The software is developed and tested.

5. Deployment: The software is deployed to the end-users.

6. Maintenance: The software is maintained to ensure that it continues to operate as expected.

### Software Development Models

There are different models that can be used to develop software. These models include:

1. Waterfall model: This model involves a linear approach to software development, where each stage of development is completed before moving on to the next stage.

2. Agile model: This model involves an iterative approach to software development, where the development process is broken down into smaller cycles.

3. Spiral model: This model involves a combination of the waterfall and agile models, where each cycle is broken down into smaller cycles.

### Software Testing

Software testing is the process of verifying that the software meets the requirements and operates as expected. There are different types of software testing, including:

1. Unit testing: This involves testing individual units or components of the software.

2. Integration testing: This involves testing the interaction between different components of the software.

3. System testing: This involves testing the software as a whole.

4. Acceptance testing: This involves testing the software with the end-users to ensure that it meets their requirements.

### Software Maintenance

Software maintenance is the process of making changes to the software to ensure that it continues to operate as expected. There are different types of software maintenance, including:

1. Corrective maintenance: This involves fixing defects or errors in the software.

2. Adaptive maintenance: This involves making changes to the software to accommodate changes in the environment or requirements.

3. Perfective maintenance: This involves making improvements to the software to enhance its functionality or performance.

4. Preventive maintenance: This involves making changes to the software to prevent future problems or issues.



### Overview of Software Evolution

Software evolution refers to the process of making changes to software over time to meet changing requirements, fix errors, and improve performance. The software evolution process is an essential part of software engineering and testing processes. In this section, we will provide an overview of the software evolution process.

1. Software Maintenance: 
   - Software maintenance is the process of modifying software after delivery to correct faults and improve performance.
   - There are three types of software maintenance: corrective, adaptive, and perfective.
   - Corrective maintenance is the process of fixing bugs and errors found in the software.
   - Adaptive maintenance involves modifying the software to meet changing user needs.
   - Perfective maintenance is the process of improving software to meet new requirements or to improve performance.

2. Software Enhancement:
   - Software enhancement is the process of adding new features to software to meet user needs.
   - This process is the result of changing market demands or business requirements.

3. Software Reengineering:
   - Software reengineering is the process of changing the software's structure without changing its functionality.
   - This process is done to improve software maintainability, reusability, and other non-functional requirements.

4. Software Retirement:
   - Software retirement refers to the process of removing software from the system when it is no longer needed.
   - This process is necessary to free up resources and reduce maintenance costs.

5. Software Migration:
   - Software migration refers to the process of moving software from one platform to another.
   - This process is necessary when the current platform becomes outdated or is no longer supported.

In conclusion, software evolution is an essential process that ensures software remains relevant, functional, and efficient. It involves maintenance, enhancement, reengineering, retirement, and migration. Understanding the software evolution process is crucial for software engineers and testers to ensure software remains up-to-date, secure, and meets changing user needs.



### SDLC

Software Development Life Cycle (SDLC) is a systematic approach to software development that involves a series of well-defined phases. Each phase of SDLC has its own set of goals, deliverables, and activities that are executed in a specific sequence. The following are the different phases of SDLC:

1. Planning: The first phase of SDLC is planning, where the objectives, requirements, and constraints of the software project are identified. The planning phase involves the following activities:
    - Defining the scope of the project
    - Identifying the project stakeholders
    - Analyzing the feasibility of the project
    - Defining the project requirements
    - Creating a project plan

2. Analysis: In the analysis phase, the requirements of the software project are analyzed in detail. The analysis phase involves the following activities:
    - Gathering and documenting the requirements
    - Analyzing the requirements for accuracy, completeness, and feasibility
    - Identifying any potential risks or issues

3. Design: In the design phase, the software architecture and design are created based on the requirements identified in the analysis phase. The design phase involves the following activities:
    - Creating the software architecture
    - Creating the detailed design
    - Identifying the software components
    - Creating the user interface design

4. Implementation: In the implementation phase, the software solution is developed based on the design created in the previous phase. The implementation phase involves the following activities:
    - Writing the software code
    - Testing the software code
    - Integrating the software components

5. Testing: In the testing phase, the software solution is tested for defects and errors. The testing phase involves the following activities:
    - Creating the test plan
    - Creating the test cases
    - Executing the test cases
    - Reporting and tracking the defects

6. Deployment: In the deployment phase, the software solution is released to the end-users. The deployment phase involves the following activities:
    - Preparing the software for deployment
    - Deploying the software
    - Verifying the software deployment

7. Maintenance: In the maintenance phase, the software solution is monitored and maintained to ensure its effective functioning. The maintenance phase involves the following activities:
    - Identifying and fixing defects
    - Enhancing the software functionality
    - Updating the software documentation

SDLC is a crucial part of software development, as it ensures that the software solution is developed and delivered in a systematic and structured manner. Proper execution of SDLC ensures that the software solution meets the requirements of the stakeholders and is of high quality.

### Terminologies in Testing

In the field of software testing, there are various terminologies that are commonly used. Understanding these terminologies is crucial to effectively communicate and perform testing activities. In this unit, we will review some of the key terminologies in testing.

1. **Test Case:** A set of conditions or variables under which a tester will determine whether an application or software system is working correctly or not.

2. **Test Plan:** A document that outlines the testing strategy, objectives, scope, resources, and schedule for a software testing project.

3. **Test Suite:** A collection of test cases that are grouped together to test certain functionalities or features of a software application.

4. **Defect:** A flaw or error in a software application that prevents it from functioning as intended.

5. **Bug:** A defect or error that is discovered during testing and needs to be fixed by the development team.

6. **Regression Testing:** Testing performed to ensure that changes or modifications to a software application have not adversely affected its existing functionality.

7. **Smoke Testing:** A preliminary test performed to check whether the basic functionalities of a software application are working correctly or not.

8. **Integration Testing:** Testing performed to ensure that different modules or components of a software application are working together as expected.

9. **Acceptance Testing:** Testing performed by end-users to ensure that a software application meets their requirements and needs.

10. **Black Box Testing:** A testing technique where the tester does not have any knowledge of the internal workings of a software application and only tests its functionality from the user's perspective.

11. **White Box Testing:** A testing technique where the tester has knowledge of the internal workings of a software application and tests its functionality based on that knowledge.

12. **Boundary Value Analysis:** A testing technique that involves testing the boundaries or limits of input values to ensure that the software application behaves correctly.

13. **Equivalence Partitioning:** A testing technique that involves dividing the input data into different partitions or categories and testing each partition separately.

14. **Traceability Matrix:** A document that links the requirements of a software application to the test cases that are used to test them.

15. **Verification:** The process of evaluating whether a software application meets its specified requirements.

16. **Validation:** The process of evaluating whether a software application meets the needs and requirements of its end-users.

Understanding these key terminologies in testing is crucial for effective communication and testing activities. These terminologies provide a common language and understanding for testers, developers, and other stakeholders involved in software testing.

### Difference Between Verification and Validation

Software testing is a crucial part of the software development life cycle (SDLC). It ensures that the software product is of high quality and meets the user's requirements. Software testing comprises two essential activities, Verification and Validation. Although they sound similar, these activities are different and are performed at different stages of the SDLC.

#### Verification

Verification is the process of evaluating the software system or component to ensure that it meets the design specifications and requirements. It is a static process and is usually performed before the coding phase. Verification activities include:

- Reviewing the software requirements to ensure that they are complete, consistent, and unambiguous
- Inspecting the software design and architecture to ensure that they comply with the specifications and requirements
- Conducting a code review to verify that the code is well-structured, readable, maintainable, and adheres to coding standards
- Conducting a walkthrough to ensure that the software system is ready for testing

The goal of verification is to ensure that the software system meets its functional and non-functional requirements and is ready for the next phase of the SDLC.

#### Validation

Validation is the process of evaluating the software system or component to ensure that it meets the user's requirements and needs. It is a dynamic process and is usually performed after the coding phase. Validation activities include:

- Conducting functional testing to ensure that the software system meets its functional requirements
- Conducting non-functional testing to ensure that the software system meets its non-functional requirements, such as performance, reliability, and security
- Conducting user acceptance testing (UAT) to ensure that the software system meets the user's requirements and expectations
- Conducting regression testing to ensure that the software system has not regressed and still meets its requirements after changes or modifications

The goal of validation is to ensure that the software system meets the user's requirements and needs and is ready for release.

#### Key Differences

The key differences between verification and validation are:

- Verification is a static process, while validation is a dynamic process.
- Verification is performed before the coding phase, while validation is performed after the coding phase.
- Verification ensures that the software system meets its design specifications and requirements, while validation ensures that the software system meets the user's requirements and needs.
- Verification focuses on the software system's internal quality, while validation focuses on the software system's external quality.

In conclusion, verification and validation are two crucial activities in software testing that ensure the software system's quality and readiness for release. Understanding the differences between these activities is essential for software testers and developers to develop high-quality software products.

### Impracticality of Testing All Data

Software testing is a critical part of software engineering that ensures the quality of software products. Testing is done to identify defects, errors, and bugs in the software code and fix them before the software is released to the end-users. However, it is not always practical to test all the data in a software program due to the following reasons:

1. Time Constraints: 

Testing every possible input for a software program can be a time-consuming process. Software programs can have millions of possible inputs, and testing each one of them is not practical. The time required to test every input could delay the software release date, and in some cases, the software may become obsolete before it gets released.

2. Cost:

Testing all data in a software program can be an expensive process. The cost involved in testing every possible input can exceed the budget of the project, making it impractical to test all data.

3. Infeasibility:

In some cases, it may not be possible to test all data due to technical limitations, such as limited computing resources. Large software programs with complex algorithms may require excessive computing resources to test all data, making it impractical to test all data.

4. Risk management:

Testing all data is not always necessary to ensure that the software program is functional and reliable. Instead, testing a representative sample of data can be sufficient to identify most of the defects and errors. Testing a representative sample can help to manage risks associated with software development and release.

5. Human error:

Testing all data is not a foolproof method to ensure that software programs are free of defects and errors. Human error can still occur during testing, leading to missed defects and errors. Therefore, it is important to use a combination of automated and manual testing methods to identify defects and errors.

In conclusion, testing all data in a software program is not always practical due to time constraints, cost, infeasibility, risk management, and the possibility of human error. Instead, testing a representative sample of data can be sufficient to identify most of the defects and errors in a software program. A combination of automated and manual testing methods can be used to ensure software quality and reliability.



### Impracticality of Testing AllPaths

When it comes to software testing, one of the most important goals is to ensure that all possible paths through the software are tested. However, in practice, testing all paths can be extremely impractical, if not impossible. Here are some reasons why:

1. Time Constraints: Testing every possible path through the software is a time-consuming process. With the complexity of modern software, it can take weeks or even months to test every path, which is often not feasible.

2. Combinatorial Explosion: Even for relatively simple software, the number of possible paths through the code can be astronomical. As the number of inputs and conditions increases, the number of possible paths can quickly spiral out of control, making it impossible to test them all.

3. Infeasibility of Execution: Some paths through the software may be impossible to execute, making it impossible to test them. For example, if a certain input value can never be reached due to a programming error, it is impossible to test the path that would be executed if that input were received.

4. Limited Resources: Testing all possible paths through the software requires significant resources, including time, personnel, and computing power. In many cases, these resources are simply not available.

5. Diminishing Returns: Even if it were possible to test all possible paths through the software, the cost-benefit ratio may not be favorable. As the number of paths tested increases, the incremental benefit of testing each additional path decreases.

In summary, while testing all possible paths through software is an ideal goal, it is often impractical, if not impossible, in practice. Testing strategies need to be carefully designed to balance the need for comprehensive testing with the practical constraints of time, resources, and feasibility.

### Equivalence Class Testing

Equivalence Class Testing is a software testing technique used to reduce the number of test cases while maintaining the same level of test coverage. This technique is based on the assumption that if one test case in an equivalence class passes or fails, all other test cases in the same equivalence class will have the same result.

Here are some key points to keep in mind when using Equivalence Class Testing:

- Equivalence classes are defined as a set of input values that produce the same output when processed by the software being tested.
- Equivalence classes are identified by partitioning the input domain into mutually exclusive and exhaustive subsets.
- Test cases are selected from each equivalence class to ensure all possible scenarios are covered.
- Equivalence class testing can be used for both positive and negative testing.
- Positive testing is used to verify that the software functions as intended when valid inputs are provided.
- Negative testing is used to verify that the software can handle invalid inputs appropriately.

To effectively use Equivalence Class Testing, follow these steps:

1. Identify the input domain: Determine the range of possible values that can be provided as input to the software being tested.

2. Partition the input domain: Divide the input domain into mutually exclusive and exhaustive subsets, or equivalence classes.

3. Define test cases: Select one or more test cases from each equivalence class. Make sure that each test case tests a different scenario.

4. Execute the test cases: Run the selected test cases to verify that the software functions as intended for each scenario.

5. Analyze the results: Evaluate the results of the test cases and identify any defects or issues that need to be addressed.

In summary, Equivalence Class Testing is a powerful technique that can be used to reduce the number of test cases required for software testing while maintaining the same level of test coverage. By carefully partitioning the input domain and selecting test cases from each equivalence class, you can ensure that your software functions as intended under all possible scenarios.

### Path Testing

Path testing is a structural testing technique that is used to ensure that all possible paths through a program have been executed at least once. The goal of path testing is to identify any logical errors that may occur as a result of the program's execution.

Path testing involves creating a control flow graph (CFG) for the program under test. The CFG is a graphical representation of the program's control flow, which shows the order in which program statements are executed. The CFG is created by identifying all of the program's decision points and branching statements, and then connecting them with arrows to create a directed graph.

Once the CFG has been created, path testing involves identifying all of the possible paths through the graph. This is done by starting at the entry point of the program and following each possible path through the graph. Each path is then tested to ensure that it is executed correctly.

Path testing is a white-box testing technique, which means that it requires knowledge of the program's internal structure in order to be effective. It is typically used in conjunction with other structural testing techniques, such as statement coverage and branch coverage.

### Debugging

Debugging is the process of identifying and resolving defects or bugs in software. 1. **Manual Debugging** - This is the traditional approach to debugging, where the developer manually identifies the source of the defect and fixes it. This method involves analyzing logs, tracing code, and using print statements to find the bug.

2. **Automated Debugging** - This is a more advanced technique that involves using tools and software to automatically identify and fix bugs. Automated debugging tools can analyze code, logs, and other data to identify defects and suggest fixes.

#### Debugging Techniques

1. **Cause-Effect Graphing** - This technique involves creating a graphical representation of the system and identifying the inputs and outputs of each component. By analyzing the graph, the developer can identify the cause of the defect and fix it.

2. **Fault Injection** - This technique involves intentionally introducing faults or defects into the system to test its ability to detect and recover from them. Fault injection is commonly used in testing safety-critical systems.

3. **Backtracking** - This technique involves tracing the execution of the program backward from the point of failure to identify the cause of the defect. Backtracking can be done manually or using automated tools.

#### Debugging Tools

1. **Debuggers** - These are software tools that allow developers to step through the code line by line, set breakpoints, and inspect variables and memory. Debuggers are essential tools for manual debugging.

2. **Isolate the Problem** - Once the bug is reproduced, the developer should isolate the problem by narrowing down the scope of the code that is causing the defect. This will make it easier to debug and fix the issue.

3. **Use Version Control** - Version control systems like Git can help developers track changes to the code and revert to previous versions if necessary. This can be useful in debugging, as it allows developers to isolate changes that may have introduced the defect.

4. **Document the Process** - It is important to document the debugging process, including the steps taken to identify and fix the bug. This documentation can be used for future reference and to improve the quality of the software.

Debugging is a complex and challenging task, requiring a combination of technical skill, analytical thinking, and patience. By using the right techniques and tools, developers can identify and fix defects quickly and efficiently, ensuring that the software meets the required quality standards.

Use cases are scenarios that describe how the software application is expected to behave in different situations. Test data is generated for each use case, ensuring that the software application is tested thoroughly.

### Issues for the notes of the Unit 6 - Object Oriented Testing in the subject of Software Testing

Object-oriented programming (OOP) is a widely used programming paradigm that emphasizes the use of objects to represent real-world concepts. Here are some of the key issues to keep in mind when testing object-oriented software:

1. **Complexity**: Object-oriented software can be very complex, with multiple layers of abstraction and interdependent objects. This complexity can make testing difficult, as it can be hard to identify and isolate individual components for testing purposes.

2. **Inheritance**: Inheritance is a key feature of object-oriented programming, but it can also make testing more complicated. Inherited methods and properties can have unintended effects on derived classes, which can make it hard to predict the behavior of the system as a whole.

3. **Encapsulation**: Encapsulation is another key feature of object-oriented programming, but it can also make testing more challenging. The encapsulation of objects can make it difficult to access and test certain components of the system.

4. **Polymorphism**: Polymorphism is the ability of objects to take on different forms or behaviors depending on the context in which they are used. This can make testing more complex, as it can be difficult to predict the behavior of objects in different contexts.

5. **Integration testing**: Integration testing is the process of testing how different components of a system work together. In object-oriented software, integration testing can be particularly challenging due to the complexity of the system and the interdependence of objects.

6. **Test coverage**: Test coverage is the extent to which a test suite covers the functionality of a system. In object-oriented software, it can be difficult to achieve complete test coverage due to the complexity of the system and the large number of possible permutations of object interactions.

7. **Mocking and stubbing**: Mocking and stubbing are techniques used in object-oriented testing to simulate the behavior of objects that are not yet implemented or that are difficult to test. However, these techniques can also introduce their own set of challenges, such as the need to maintain mock and stub implementations as the system evolves.

In conclusion, testing object-oriented software can be challenging due to the complexity of the system and the interdependence of objects. 1. Identify potential threats: The first step in security testing is to identify potential threats to the software application. This can include common attacks such as SQL injection, cross-site scripting (XSS), and cross-site request forgery (CSRF). By identifying potential threats, you can create test cases that simulate these attacks and test the application's ability to handle them.

2. Test authentication and authorization: Authentication and authorization are two critical components of security testing. Authentication is the process of verifying the identity of a user, while authorization involves determining what actions a user can perform within the application. Ensure that the application properly authenticates users and restricts access to sensitive data and functions based on the user's role and permissions.

3. Test input validation: Input validation is the process of checking user input to ensure that it is valid and safe. This is particularly important for applications that accept user input, such as web forms. Test input validation by entering invalid data, such as special characters or SQL injection code, and ensuring that the application handles it correctly.

4. Test error handling: Error handling is another critical component of security testing. Ensure that the application handles errors gracefully and does not reveal sensitive information to the user. For example, if an error occurs during the login process, the application should display a generic error message rather than indicating that the username or password was incorrect.

5. Test session management: Session management is the process of managing user sessions and ensuring that they are secure. Test session management by logging in as a user and then attempting to access the application using a different browser or device. The application should prompt the user to log in again and invalidate the previous session.

6. Test encryption and decryption: Encryption and decryption are essential for securing sensitive data. Test encryption and decryption by encrypting data and then attempting to decrypt it using a different key. The application should not be able to decrypt the data without the correct key.
