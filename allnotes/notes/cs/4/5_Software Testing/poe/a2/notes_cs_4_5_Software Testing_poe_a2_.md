## Unit 1 - Review of Software Engineering

1. Software Engineering: Software Engineering is the application of engineering principles to software development. It involves a systematic approach to the development, operation, maintenance, and retirement of computer software.
2. Software Development Life Cycle: The Software Development Life Cycle or SDLC is a process used by the software industry to design, develop and test high quality softwares. The SDLC aims to produce a high-quality software that meets or exceeds customer expectations, reaches completion within times and cost estimates. The basic SDLC methodologies are:
    - Waterfall model: Requirements -> Design -> Implementation -> Testing -> Deployment
    - Agile model: Short iterations of Requirements -> Design -> Implementation -> Testing
3. Requirements Analysis: The first phase of SDLC is Requirements Analysis where the software requirements are studied and specified. The goal is to determine what exactly the customer needs and ensure that the software meets those requirements. Use cases and user stories are tools used to understand requirements.
4. Design: The design phase translates the requirements into a blueprint of the software. The software architecture is defined in this phase along with major components and interfaces. Common design methodologies are object-oriented design, component-based design, service-oriented design, etc.
5. Implementation: The implementation phase involves converting the design into code. The source code is written in a programming language using the chosen software architecture and design.
6. Testing: The testing phase evaluates the software to identify and fix any bugs, errors or other defects. Different testing methodologies like unit testing, integration testing, system testing, acceptance testing, etc. are employed to test the software.
7. Deployment: The deployment phase delivers the final software product to the customer. The software is installed and made operational in the customer environment.

### SDLC for the notes of the Unit 1 - Review of Software Engineering in the subject of Software Testing

1. Requirement Analysis: The first phase of SDLC is Requirement Analysis. In this phase, the requirements of the proposed system are collected by analyzing the needs of the user. The requirements are gathered from the user and the system analyst studies the user requirements and prepares the SRS (Software Requirement Specification).

2. Feasibility Study: After the requirement analysis, a feasibility study is performed. The feasibility study evaluates the project from an operational and economical perspective. 3. Design: In the design phase, the proposed system is designed. The design phase can be further divided into the architectural design and detailed design. 4. Implementation / Coding: The design model is implemented in a programming language in this phase. The system is first developed in small programs called units, which are integrated in the next phase.

5. Testing: In the testing phase, the implemented software is evaluated for correctness, completeness, security and quality. It is tested for the functional and non-functional requirements. Various types of testing like unit testing, integration testing, system testing, acceptance testing, etc. are performed in this phase.

6. Deployment: Once the software is tested and satisfied, it is deployed to the customer environment. The deployment process may involve installation, configuration, and execution of the software.

7. Maintenance: Once the software is deployed, regular maintenance and review are necessary. The software may require enhancement or modification to meet the changing needs of the business. Also, errors may be detected and corrected. Thus, maintenance is an ongoing phase that continues as long as the software is used.

### Terminologies in Testing for the notes of the Unit 1 - Review of Software Engineering in the subject of Software Testing.

5. Bug - A flaw in a system that can cause the system to work incorrectly. Also known as a defect.
6. Bug report - A document reporting on any flaw found during testing that could lead to incorrect or unexpected behavior. A good bug report contains a description of the bug, steps to reproduce it, expected behavior, and actual behavior.

### Oracles for the notes of the Unit 1 - Review of Software Engineering in the subject of Software Testing.

1. Specification-based oracle: Compares the actual output with the specified output. The specified output acts as an oracle.
2. Exception-based oracle: Checks if the software under test raises the expected exceptions. If unexpected exceptions occur or expected exceptions do not occur, it indicates a fault.
3. Domain expert-based oracle: A domain expert evaluates the output of the software under test. The domain expert acts as the oracle.
4. Pattern-based oracle: Checks if the output of the software under test matches some expected pattern. The pattern acts as the oracle.
5. Contract-based oracle: Checks if the software under test meets certain preconditions and postconditions. The contracts act as oracles.
6. Behavioral oracle: Checks if the software under test behaves as expected. The expected behavior acts as the oracle.
7. Model-based oracle: The software under test is executed with a model of its specification. The output is checked against the model, which acts as the oracle.

### Impracticality of Testing All Data for the notes of the Unit 1 - Review of Software Engineering in the subject of Software Testing

- The input data can be huge in volume. For example, testing all possible inputs for a calculator application or testing all possible values for an temperature converting application is not feasible.

- Common scenarios and usage patterns
- Boundary values like maximum, minimum, just inside/outside boundaries, etc.
- Error prone situations like empty fields, invalid data, database errors, etc.
- Business critical functionality and impact

3. Though testing all input data is impossible, using structured testing techniques and covering major scenarios leads to increased test coverage and reduced number of bugs escaping to the production environment. A balance between exhaustive testing and resource optimization has to be achieved.

### Impracticality of Testing AllPaths for the notes of the Unit 1 - Review of Software Engineering in the subject of Software Testing

1. It is impossible to test all possible paths through a software due to following reasons:
- The number of possible paths increases exponentially with the number of decision points.
- The time required to test all paths is very huge and is not feasible in practice.
- It is impossible to anticipate all possible sequences of inputs and events.
- Real world software systems are very complex with numerous paths, inputs, and events.

2. Instead of attempting an impossible task of testing all paths, software testers focus on:
- Testing the most important and frequently used paths through a software.
- Testing boundary conditions and exceptions.
- Using techniques like equivalence partitioning and boundary value analysis to reduce the number of test cases.
- Risk-based testing to focus on the most risky areas of the software.

- Follow-up: Once rework is done, reviewers verify whether the changes were done properly. If everything is fine, the review is closed.

- Review code in small chunks to minimize context switching.
- Focus on high impact areas and major changes.
- Provide concrete and actionable feedback.
- Discuss differences in opinions respectfully.
- Ensure the author understands and agrees to the feedback.
- Track review metrics to monitor effectiveness.

### Cycyclomatic Complexity for the notes of the Unit 3 - Structural Testing in Software Testing

1. Cyclomatic Complexity is a software metric used to indicate the complexity of a program.
2. It measures the number of independent paths through the source code.
3. It was developed by Thomas J. McCabe, Sr. in 1976.
4. It is computed using the control flow graph of the program. The control flow graph is a directed graph where nodes represent basic blocks and edges represent control flow between basic blocks.

V(G) = E - N + 2

6. A program with high cyclomatic complexity is harder to test and is more prone to errors.
7. It can be used to determine the number of test cases required to obtain adequate coverage of a program.
8. The optimal value for cyclomatic complexity can vary but a value of 10 or less is desirable.
9. Some ways to reduce cyclomatic complexity are:
- Removing unnecessary conditional logic

### Mutation Testing

For the notes of the Unit 3 - Structural Testing in the subject of Software Testing:

1. Mutation Testing is a method of software testing that involves making small changes to the code under test and seeing if the test suite catches these errors. These small changes are known as mutations.

2. The key idea behind mutation testing is that if a test suite is good, it should be able to detect changes that break the code (mutations). If it cannot detect these errors, then it indicates weaknesses in the test suite.

3. Mutation testing is more powerful than other testing methods as it evaluates both the test input and the test oracle. It can identify ineffective tests and provide a measure of the quality of a test suite.

4. The steps involved in mutation testing are:

a) Select a program component to mutate (class, function, etc.)
b) Select a mutation operator (e.g. replace > with >=)
c) Apply the mutation operator to the selected component to create a mutant
d) Run the test suite on the mutant
e) If the test suite fails, then the mutant is killed. If the test suite passes, then it is a surviving mutant.
f) Repeat steps b-e for all mutation operators and components
g) Analyze the results to evaluate the test suite

5. Some pros of mutation testing are:

- It can identify redundant or inefficient tests
- It provides a measure of test suite effectiveness
- It ensures that the tests check for a wide range of errors

6. Some cons of mutation testing are:

- It can be computationally expensive
- It may produce equivalent mutants that make the test suite appear weaker than it is
- It can be difficult to automatically generate meaningful mutations for complex software

### Test Data Generation using Genetic Algorithm

2. The steps involved in GA for test data generation are:
- Representation: Encode input variables and constraints into chromosomes (binary strings)
- Population Initialization: Create initial population of chromosomes (input test data) randomly
- Fitness Evaluation: Evaluate fitness of each chromosome using coverage criterion
- Selection: Select fitter chromosomes from population for next generation
- Crossover: Perform crossover on selected chromosomes to produce offspring
- Mutation: Mutate offspring chromosomes to add diversity
- Survival Selection: Select fittest chromosomes from combined parent and offspring population for next generation
3. The process is repeated over multiple generations until a sufficient coverage goal is reached or computational budget is exhausted.

### Database testing for the notes of the Unit 7 - Testing Web Applications in the subject of Software Testing.

1. Database testing is done to check the data integrity i.e. accuracy, consistency and security of data in the database.
2. Some common database testing techniques are:
- Data validity testing - Check if the data types, sizes, ranges, values, etc. are as expected. Also, check for orphaned and missing data.
- Referential integrity testing - Check if the relationships between tables are intact like foreign key constraints.
- Authorization and access control testing - Test if only authorized users can access and modify data. Check for SQL injection vulnerabilities.
- Backup and recovery testing - Test the database backup and recovery process.
- Stored procedures testing - Test the stored procedures for expected input/output and check if there are any errors or side effects.
3. Some tools used for database testing are:
- SQLUnit - An open source tool for testing database queries and stored procedures.
- DbFit - A database testing tool that supports various databases like MySQL, Oracle, etc.
- UAT-Database Tester - A commercial tool to automate database testing for queries, procedures, functions, etc. across different databases.
4. Database testing should be performed continuously to catch issues early and ensure a robust database for the application. It is an important part of testing web applications and overall software quality assurance.

### Post Deployment Testing

1. Objectives
- Check application performance and behavior in actual user environment.
- Identify issues that were not discovered during development and testing phases.
- Measure application performance, load handling capability and resource utilization.

2. Types
- Load Testing: Check application performance under different loads. Identify maximum load handling capacity.
- Stress Testing: Check application behavior under extreme workloads that are expected to strain system resources.
- Volume Testing: Check application performance by varying the volume of data.
- Scalability Testing: Check application capability to scale up or scale down and handle increased or decreased workload.
- Compliance Testing: Check if application complies with standards, specifications, design guidelines, etc.
- Business Process Testing: Check end-to-end business processes and scenarios.
- Usability Testing: Check ease of use and user satisfaction.

3. Methods
- Monitoring application performance, resource usage, server logs, etc.
- Recording and analyzing user interactions with the application.
- Comparing actual results with expected performance and usage parameters.
- Reviewing user feedback and complaints.
- Simulating various loads and scenarios and measuring response times and resource consumption.

4. Significance
- Identifies residual defects and performance bottlenecks.
- Measures actual application quality and user experience.
- Provides valuable feedback to improve the application.
- Gains user confidence by demonstrating application stability and reliability.
