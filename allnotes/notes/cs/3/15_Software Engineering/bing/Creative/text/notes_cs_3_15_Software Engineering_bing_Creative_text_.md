

## Unit 1 - Introduction to Software Engineering

- Software engineering is the discipline of applying engineering principles and practices to the design, development, testing, deployment, and maintenance of software systems.
- Software engineering aims to produce software that is reliable, efficient, secure, usable, and meets the requirements and expectations of the stakeholders.
- Software engineering involves various activities, such as:
  - Requirements engineering: eliciting, analyzing, specifying, and validating the needs and constraints of the software system and its users.
  - Software design: defining the architecture, components, interfaces, data structures, algorithms, and behavior of the software system.
  - Software implementation: writing, debugging, and testing the source code of the software system.
  - Software verification and validation: ensuring that the software system conforms to its specifications and meets its quality attributes.
  - Software deployment: installing, configuring, and running the software system on the target environment.
  - Software maintenance: modifying, updating, and correcting the software system to cope with changing requirements, errors, or new technologies.
- Software engineering also involves various processes, methods, tools, and standards that support and guide the software engineering activities, such as:
  - Software development models: frameworks that define the phases, tasks, roles, and deliverables of a software project, such as waterfall, agile, spiral, etc.
  - Software development methodologies: approaches that prescribe the principles, practices, and techniques for planning, executing, and managing a software project, such as Scrum, XP, RUP, etc.
  - Software engineering tools: software applications that assist the software engineers in performing their tasks, such as editors, compilers, debuggers, testing tools, configuration management tools, etc.
  - Software engineering standards: norms and guidelines that define the quality criteria, best practices, and conventions for software engineering, such as ISO/IEC 12207, IEEE 830, CMMI, etc.



### Introduction to Software Engineering

- Software engineering is the branch of computer science that deals with the design, development, testing, and maintenance of software applications.
- Software engineers apply engineering principles and knowledge of programming languages to build software solutions for end users.

- Software engineering is a discipline that requires creativity, problem-solving, teamwork, and communication skills.
- Software engineering is a dynamic and evolving field that responds to the changing needs and demands of the software industry and society.

- Software engineering is a challenging and rewarding career that offers many opportunities for learning and growth.



### Software Components

- Software components are parts of a system or application that have well-defined interfaces and can be deployed independently  .
- Software components are a means of breaking the complexity of software into manageable parts. Each component hides the complexity of its implementation behind an interface.
- Software components can be as small as a block of reusable code, or as big as an entire application.
- Software components are subject to composition by third parties, meaning that they can be combined with other components to form larger systems.
- Software components are based on the principle of separation of concerns, meaning that each component should only deal with a specific functionality or responsibility.
- Software components can improve the quality, reusability, maintainability, and scalability of software systems.
- Software components can be classified into different types, such as user interface components, business logic components, data access components, etc., depending on their role and functionality.



### Software Characteristics

Software is a set of instructions, data or programs used to operate computers and execute specific tasks. Software can be classified into different types based on its functionality, complexity, quality, and cost. Some of the common types of software are:

- System software: This is the software that provides the basic functions of the computer, such as operating system, device drivers, utilities, etc.
- Application software: This is the software that performs specific tasks for the user, such as word processor, spreadsheet, web browser, etc.
- Embedded software: This is the software that is embedded in a hardware device, such as firmware, microcontroller, etc.
- Web-based software: This is the software that runs on a web server and can be accessed through a web browser, such as web applications, web services, etc.

Software characteristics are the attributes or properties that describe the quality and performance of the software. Software characteristics are classified into six major components :

- Functionality: This refers to the degree of performance of the software against its intended purpose. It includes aspects such as correctness, completeness, security, interoperability, etc.
- Reliability: This refers to the ability of the software to provide desired functionality under the given conditions. It includes aspects such as availability, fault tolerance, recoverability, etc.
- Usability: This refers to the ease of use and learnability of the software for the intended users. It includes aspects such as understandability, operability, attractiveness, etc.
- Efficiency: This refers to the optimal use of resources by the software, such as time, space, energy, etc. It includes aspects such as performance, scalability, resource utilization, etc.
- Maintainability: This refers to the ease of modifying and updating the software to cope with changing requirements and environments. It includes aspects such as modularity, readability, testability, etc.
- Portability: This refers to the ability of the software to run on different platforms and environments without significant changes. It includes aspects such as adaptability, installability, compatibility, etc.

Software characteristics can be measured and evaluated using various methods and tools, such as metrics, standards, models, etc. Some of the common methods and tools are:

- ISO/IEC 25010:2011 Software Quality Model: This is a standard that describes a hierarchy of eight quality characteristics, each composed of sub-characteristics. The eight quality characteristics are: functional suitability, reliability, operability, performance efficiency, security, compatibility, maintainability, and transferability.
- Software Metrics: These are quantitative measures that can be used to assess the software characteristics, such as size, complexity, quality, etc. Some of the common software metrics are: lines of code, cyclomatic complexity, defect density, etc.
- Software Testing: This is the process of verifying and validating the software characteristics, such as functionality, reliability, usability, etc. Some of the common software testing techniques are: unit testing, integration testing, system testing, etc.



### Software Crisis

- Software crisis is a term used to describe the difficulty of developing high-quality software systems that meet the user requirements, within the budget and time constraints.
- Software crisis was first observed in the 1960s and 1970s, when the demand for software increased rapidly, but the available tools and methods were inadequate to cope with the complexity and scale of the problems .
- Some of the causes of software crisis are:
  - The cost of owning and maintaining software was as expensive as developing the software.
  - Projects were running over-time and over-budget, often resulting in incomplete or unreliable software.
  - Software was very inefficient and consumed a lot of resources.
  - The quality of the software was low and prone to errors and failures.
  - Software often did not meet user requirements or expectations.
  - Software was difficult to modify or adapt to changing needs or environments.
  - Software development was not a well-defined or disciplined process, and lacked standards and best practices.
- Some of the examples of software crisis are:
  - The OS/360 operating system, which was a decade-long project from the 1960s that eventually produced one of the most complex software systems at the time, but also suffered from delays, defects, and compatibility issues.
  - The Ariane 5 rocket, which exploded in 1996 due to a software error that caused an overflow in a variable that was reused from the previous version of the rocket.
  - The Therac-25 radiation therapy machine, which caused several deaths and injuries in the 1980s due to a software bug that allowed the machine to deliver lethal doses of radiation.
- Software crisis led to the emergence of software engineering as a discipline that aims to apply systematic, rigorous, and quantifiable approaches to the development, operation, and maintenance of software systems.



### Software Engineering Processes

Software engineering processes are the methods and techniques used to develop and maintain software products that meet the requirements and expectations of the clients and users. Software engineering processes aim to ensure the quality, reliability, security, and efficiency of the software products, as well as the satisfaction of the stakeholders involved in the software development life cycle (SDLC).

Some of the main objectives of software engineering processes are:

- To define the scope and goals of the software project
- To plan and manage the resources, tasks, and risks of the software project
- To specify, design, implement, test, and document the software product
- To verify, validate, and evaluate the software product
- To deploy, maintain, and evolve the software product

Software engineering processes can be classified into different types, depending on the level of abstraction, the degree of formality, the degree of flexibility, and the degree of involvement of the stakeholders. Some of the common types of software engineering processes are:

- Linear processes: These are sequential and rigid processes that follow a fixed order of phases, such as the waterfall model, the V-model, and the spiral model. Linear processes are suitable for well-defined and stable software projects, but they may not be able to cope with changing requirements and feedback.
- Iterative and incremental processes: These are processes that divide the software project into smaller and manageable units, called iterations or increments, that are developed and delivered in cycles, such as the agile model, the scrum model, and the extreme programming model. Iterative and incremental processes are suitable for dynamic and complex software projects, as they allow for frequent testing, feedback, and adaptation.
- Model-driven processes: These are processes that rely on the use of models, such as diagrams, graphs, or mathematical expressions, to represent and manipulate the software product and its components, such as the unified modeling language (UML), the model-driven architecture (MDA), and the model-driven engineering (MDE). Model-driven processes are suitable for large and heterogeneous software projects, as they enable the automation, integration, and verification of the software product.
- Component-based processes: These are processes that reuse existing software components, such as libraries, frameworks, or services, to assemble and configure the software product, such as the service-oriented architecture (SOA), the component-based development (CBD), and the software product line (SPL). Component-based processes are suitable for modular and scalable software projects, as they reduce the development time and cost, and improve the quality and reliability of the software product.

- Differences:
  - Software engineering is only related to programming, but conventional engineering is related to thinking, designing, and building tasks.
  - Software engineering products are intangible and abstract, but conventional engineering products are tangible and concrete.
  - Software engineering products are more prone to changes and errors, but conventional engineering products are more stable and robust.
  - Software engineering products have higher complexity and diversity, but conventional engineering products have lower complexity and diversity.
  - Software engineering products have shorter life cycle and faster development, but conventional engineering products have longer life cycle and slower development.
  - Software engineering products have more opportunities of foreign settlement, but conventional engineering products have higher government sector opportunity.
  - Software engineering products have a typical office job, whereas conventional engineering products have a more physically active role.



### Software Quality Attributes

- Software quality attributes are the characteristics or properties that affect the software's ability to meet the requirements and expectations of the stakeholders.
- Software quality attributes can be classified into two categories: functional and non-functional.
- Functional quality attributes are those that relate to the specific functions or features that the software provides, such as correctness, completeness, security, usability, etc.
- Non-functional quality attributes are those that relate to the overall behavior or performance of the software, such as reliability, efficiency, maintainability, portability, scalability, etc.
- Software quality attributes can be measured using various methods, such as metrics, standards, models, testing, reviews, etc.
- Software quality attributes can be prioritized and traded off based on the needs and constraints of the project, such as cost, time, resources, etc.
- Software quality attributes can be improved by applying various techniques, such as design principles, patterns, best practices, refactoring, etc.



### Software Development Life Cycle (SDLC) Models

- Software Development Life Cycle (SDLC) is a **workflow process** that defines the **core stages and activities** of a software development project .
- SDLC models are **frameworks** that describe the **operations performed** at each phase of a software development project.
- SDLC models allow developers to **effectively plan and follow** a software development process step-by-step, making it as **predictable** as possible.
- SDLC models also help developers to **ensure quality**, **manage risks**, and **meet customer requirements** .
- There are **different types** of SDLC models, each with its own **approach** to the software development process .
- Some of the **common SDLC models** are:

  - **Waterfall model**: The **oldest and most widely used** SDLC model. It follows a **sequential** and **linear** process, where each phase is **completed** before moving to the next one. It is **simple** and **easy** to follow, but **rigid** and **inflexible** to changes  .
  - **Rapid Application Development (RAD) model**: A **variation** of the waterfall model. It focuses on **speed** and **flexibility**, using **prototyping** and **iterative** development to deliver software quickly. It is **suitable** for projects with **dynamic** and **changing** requirements, but **requires** high user involvement and skilled developers  .
  - **Spiral model**: A **risk-based** approach to software development. It combines the **waterfall** and **prototyping** models, using **cycles** of **planning**, **analysis**, **design**, **implementation**, and **evaluation**. It is **effective** for complex and large-scale projects, but **expensive** and **time-consuming** to implement  .
  - **V-model**: A **verification and validation** model. It follows a **parallel** process, where each development phase is **matched** with a testing phase. It is **reliable** and **thorough**, ensuring high-quality software, but **costly** and **difficult** to accommodate changes  .
  - **Incremental model**: A **modular** approach to software development. It divides the software into **smaller** and **independent** units, which are developed and delivered **incrementally**. It is **adaptive** and **responsive** to customer feedback, but **requires** careful planning and coordination  .
  - **Agile model**: A **collaborative** and **iterative** approach to software development. It follows a **flexible** and **incremental** process, where software is delivered in **short** and **frequent** cycles. It is **customer-oriented** and **innovative**, but **challenging** to manage and scale  .
  - **Iterative model**: A **repetitive** approach to software development. It follows a **cyclical** process, where software is developed and improved **iteratively**. It is **evolutionary** and **learning-oriented**, but **risky** and **dependent** on user feedback  .
  - **Big bang model**: A **minimalistic** approach to software development. It follows a **random** and **exploratory** process, where software is developed with **little** or **no** planning. It is **simple** and **creative**, but **unpredictable** and **unreliable**  .

- The **choice** of a SDLC model depends on the **nature**, **scope**, **budget**, **time**, and **quality** of a software development project  .
- The **advantages** and **disadvantages** of each SDLC model should be **evaluated** and **compared** before selecting one  [

- The phases of the waterfall model are: **requirement analysis, system design, implementation, testing, deployment, and maintenance** .
- The waterfall model has some **advantages**, such as:
  - It is **simple** and easy to understand and use .

  - It **facilitates** documentation and quality control .

  - It is **rigid** and inflexible, with no room for changes or feedback .

### Prototype Model

- A prototype is a working version of a software system that has some functionality, but is not complete or fully tested.
- A prototype model is a software development approach that involves creating and evaluating prototypes before developing the final system.
- The prototype model can be used to:
  - Validate the user requirements and expectations
  - Demonstrate the feasibility and usability of the system
  - Reduce the risks and uncertainties of the project
  - Obtain feedback and suggestions from the stakeholders
- The prototype model consists of the following phases:
  - Communication: The developers communicate with the customers and users to understand their needs and expectations.
  - Quick design: The developers design a quick and rough prototype that satisfies some of the user requirements.
  - Modeling: The developers implement the prototype using tools and techniques that allow rapid development and modification.
  - Deployment: The developers deploy the prototype to the customers and users for evaluation and feedback.
  - Refinement: The developers refine and improve the prototype based on the feedback and suggestions received from the customers and users.
  - Repeat: The developers repeat the previous phases until the prototype meets the user requirements and expectations or until the project budget or time is exhausted.
  - Final system: The developers finalize the system by incorporating the prototype features and fixing any errors or defects.
- The prototype model has the following advantages:
  - It improves the communication and collaboration between the developers and the customers and users.
  - It allows the customers and users to participate in the development process and provide their inputs and opinions.
  - It helps the developers to understand the user requirements and expectations better and avoid any misunderstandings or ambiguities.
  - It enables the developers to test and validate the system functionality and usability early and frequently.
  - It reduces the chances of failure and rework by identifying and resolving any issues or problems in the system.
  - It increases the customer and user satisfaction and confidence in the system.
- The prototype model has the following disadvantages:
  - It may increase the cost and time of the project by requiring multiple iterations and revisions of the prototype.
  - It may compromise the quality and reliability of the system by focusing more on the prototype features and less on the system standards and specifications.
  - It may create unrealistic expectations and dependencies on the prototype by the customers and users.
  - It may be difficult to manage and control the changes and modifications in the prototype and the system.
  - It may be challenging to integrate and transition from the prototype to the final system.



### Spiral Model

- The spiral model is a **risk-driven** software development process model that combines the **iterative** nature of prototyping with the **systematic** aspects of the linear sequential model .
- The spiral model is suitable for **large, complex, and high-risk** projects that require frequent feedback and changes .
- The spiral model consists of four phases in each iteration or loop:
  - **Planning**: This phase involves defining the objectives, alternatives, and constraints of the project. It also includes identifying and analyzing the risks involved in the project.
  - **Risk analysis**: This phase involves evaluating the alternatives and resolving the risks by prototyping, simulation, benchmarking, or other methods.
  - **Engineering**: This phase involves developing, testing, and verifying the product or system according to the specifications.
  - **Evaluation**: This phase involves reviewing and assessing the product or system by the customer or end-user and providing feedback for the next iteration.
- The number of iterations or loops in the spiral model depends on the project size and complexity and is determined by the project manager .
- The advantages of the spiral model are :
  - It can handle changing requirements and user feedback effectively.
  - It can reduce the risks and uncertainties in the project by early detection and resolution.
  - It can provide a realistic estimate of the cost, schedule, and quality of the project.
  - It can accommodate different types of projects and process models.
- The disadvantages of the spiral model are :
  - It can be complex and expensive to implement and manage.
  - It can require a high level of expertise and experience in risk analysis and management.
  - It can be difficult to define the objectives and scope of the project in the early stages.
  - It can be challenging to measure the progress and success of the project.



### Evolutionary Development Models

Evolutionary development models are software engineering models that aim to deliver the software system in an incremental and iterative manner. They are based on the idea that the requirements and the design of the system evolve over time, and that the system can be improved by feedback from the users and the developers. Some of the advantages of evolutionary development models are:

- They can cope with changing and unclear requirements by allowing the system to be modified and refined after each iteration.
- They can deliver the core features and functionalities of the system earlier, which can increase the customer satisfaction and confidence.
- They can reduce the risk of failure by testing and validating the system at each stage of development.
- They can facilitate the communication and collaboration between the stakeholders by involving them in the development process.

Some of the disadvantages of evolutionary development models are:

- They can be more expensive and time-consuming than other models, as they require more resources and effort to manage the changes and iterations.
- They can lead to lower quality and reliability of the system, as they may introduce errors and inconsistencies due to frequent modifications.
- They can be difficult to document and maintain, as they may lack a clear and stable structure and design of the system.
- They can be unsuitable for large and complex systems, as they may require too many iterations and changes to achieve the desired outcome.

There are different types of evolutionary development models, such as:

- Prototyping model: This model involves creating a simplified and incomplete version of the system, called a prototype, to demonstrate the main features and functionalities of the system to the users and the developers. The prototype is then evaluated and refined based on the feedback and suggestions, until it meets the requirements and expectations of the stakeholders. The prototyping model can be useful for exploring new ideas and concepts, validating the feasibility and usability of the system, and resolving the uncertainties and ambiguities in the requirements.
- Incremental model: This model involves developing and delivering the system in small and manageable units, called increments, each of which adds some functionality and value to the system. The increments are planned and prioritized based on the importance and urgency of the requirements, and are integrated and tested as they are completed. The incremental model can be useful for delivering the system faster and earlier, reducing the complexity and risk of the development process, and accommodating the changes and feedback in the subsequent increments.
- Spiral model: This model involves developing and delivering the system in a series of cycles, called spirals, each of which consists of four phases: planning, risk analysis, engineering, and evaluation. The planning phase involves defining the objectives and scope of the spiral, the risk analysis phase involves identifying and mitigating the potential risks and uncertainties of the spiral, the engineering phase involves designing, implementing, and testing the system, and the evaluation phase involves reviewing and assessing the system and the process. The spiral model can be useful for managing the risk and quality of the system, adapting to the changing and evolving requirements, and ensuring the alignment of the system and the stakeholders' needs.



### Iterative Enhancement Models

- Iterative enhancement models are a type of software development life cycle (SDLC) approach that combine elements of the linear sequential model with the iterative philosophy of prototyping  .
- In this model, the software is broken down into several modules which are incrementally developed and delivered  .
- Firstly, the development team develops the core module of the system, which provides the basic functionality and satisfies the essential requirements  .
- Then, the core module is tested and reviewed by the customer and feedback is obtained  .
- Based on the feedback, the next module is added to the core module, which enhances the functionality and quality of the system  .
- This process is repeated until all the modules are integrated and the final system is built and ready to be deployed   .
- The iterative enhancement model has some advantages, such as:
  - It allows early detection and correction of errors and defects  .
  - It provides a working piece of software very early in the lifecycle, which increases customer satisfaction and confidence  .
  - It accommodates changing requirements and feedback more easily than the linear sequential model  .
  - It reduces the risk of failure and improves the quality of the software  .
- The iterative enhancement model also has some disadvantages, such as:
  - It requires more management and coordination effort than the linear sequential model  .
  - It may result in scope creep and cost overrun if the iterations are not well-defined and controlled  .
  - It may introduce complexity and inconsistency in the system design and architecture if the modules are not well-integrated  .
- The iterative enhancement model is suitable for projects that have clear and stable requirements, but also need some flexibility and adaptability to accommodate changes and feedback  .
- The iterative enhancement model is not suitable for projects that have vague and volatile requirements, or that need a high degree of reliability and security  .



## Unit 2 - Software Requirement Specifications (SRS)

- Software Requirement Specifications (SRS) is a document that describes the features, functions, and constraints of a software system.
- SRS is also known as Software Requirements Document (SRD), Software Requirements Specification (SRS), or Functional Specification (FS).
- SRS is a communication tool between the stakeholders and the developers of the software system.
- SRS helps to ensure that the software system meets the needs and expectations of the stakeholders and the users.
- SRS also serves as a basis for software design, testing, validation, verification, maintenance, and evolution.

### Objectives of SRS

- The main objectives of SRS are:

  - To define the scope and boundaries of the software system.
  - To establish a common understanding of the software system among the stakeholders and the developers.
  - To specify the functional and non-functional requirements of the software system.
  - To provide a reference for software design, testing, validation, verification, maintenance, and evolution.
  - To reduce the risk of software failure, rework, and cost overrun.

### Characteristics of SRS

- A good SRS should have the following characteristics:

  - Correct: The SRS should accurately reflect the needs and expectations of the stakeholders and the users.
  - Complete: The SRS should cover all the requirements of the software system, without any ambiguity, inconsistency, or omission.
  - Consistent: The SRS should not have any conflicting or contradictory requirements.
  - Clear: The SRS should be written in a clear, concise, and understandable language, using appropriate terminology, notation, and format.
  - Verifiable: The SRS should be testable, i.e., each requirement should have a criterion for verification and validation.
  - Modifiable: The SRS should be structured and organized in a way that allows easy identification, modification, and traceability of the requirements.
  - Traceable: The SRS should be able to trace the origin, rationale, and dependencies of each requirement, as well as the impact of any change in the requirements.
  - Feasible: The SRS should be realistic and achievable, considering the available resources, technology, and constraints.
  - Unambiguous: The SRS should have only one possible interpretation, and avoid any vagueness, confusion, or misunderstanding.
  - Validated: The SRS should be reviewed and approved by the stakeholders and the users, to ensure that it meets their needs and expectations.

### Contents of SRS

- The contents of SRS may vary depending on the type, size, and complexity of the software system, as well as the standards, methodologies, and tools used for software development.
- However, a typical SRS may include the following sections:

  - Introduction: This section provides an overview of the software system, its purpose, scope, objectives, assumptions, dependencies, and constraints. It also defines the intended audience, the structure, and the organization of the SRS document.
  - System Overview: This section provides a high-level description of the software system, its context, environment, interfaces, and interactions with other systems. It also identifies the stakeholders and the users of the software system, and their roles and responsibilities.
  - Functional Requirements: This section specifies the functions and features that the software system should provide, in terms of inputs, outputs, processes, and behaviors. It also defines the use cases, scenarios, and user stories that illustrate how the software system should be used by the users and the stakeholders.
  - Non-Functional Requirements: This section specifies the quality attributes and the performance criteria that the software system should satisfy, such as reliability, availability, security, usability, maintainability, scalability, portability, etc. It also defines the standards, regulations, and policies that the software system should comply with, such as legal, ethical, social, environmental, etc.
  - System Models: This section provides graphical and textual representations of the software system, such as data models, process models, state models, object models, etc. It also describes the architecture, design, and implementation of the software system, using appropriate diagrams, notations, and methodologies.
  - System Testing: This section describes the testing strategy, plan, and methods for verifying and validating the software system, such as unit testing, integration testing, system testing, acceptance testing, etc. It also defines the test cases, test data, test procedures, test results, and test reports for the software system.
  - System Maintenance: This section describes the maintenance strategy, plan, and methods for evolving and improving the software system, such as corrective maintenance, adaptive maintenance, perfective maintenance, preventive maintenance, etc. It also defines the change management, configuration management, and quality management processes for the software



### Requirement Engineering Process

The requirement engineering process is a critical step in the software development life cycle as it helps to ensure that the software system being developed meets the needs and expectations of stakeholders, and that it is developed on time, within budget, and to the required quality.

The requirement engineering process is an iterative process that involves several steps, including :

- **Requirements inception or elicitation** – Developers and stakeholders meet; the latter are inquired about the objectives, expectations, constraints, and risks of the software system. Various techniques can be used to elicit requirements, such as interviews, questionnaires, workshops, observation, prototyping, etc.
- **Requirements analysis and negotiation** – Requirements are identified (including new ones if the development is incremental), classified, prioritized, and validated. Conflicts, inconsistencies, ambiguities, and gaps are resolved through negotiation and trade-offs among stakeholders.
- **System modeling** – Some engineering fields (or specific projects) require the use of formal or semi-formal models to specify and analyze the requirements. Models can be graphical, textual, or mathematical, and can represent different aspects of the system, such as structure, behavior, data, etc.
- **Requirements specification** – Requirements are documented in a clear, precise, and consistent way, using a standard format or notation. The requirements specification document (also known as software requirements specification or SRS) serves as a contract between the developers and the stakeholders, and as a basis for system design, testing, and maintenance.
- **Requirements validation** – Requirements are checked for quality, completeness, correctness, feasibility, and compliance with standards and regulations. Various techniques can be used to validate requirements, such as reviews, inspections, walkthroughs, simulations, testing, etc.
- **Requirements management** – Requirements are monitored and controlled throughout the software development life cycle. Changes to requirements are tracked, assessed, and approved, and their impact on the system and the project is evaluated. Requirements traceability is established and maintained, linking requirements to their sources, dependencies, and artifacts.

The requirement engineering process is a complex and challenging activity that requires the collaboration and communication of various stakeholders, such as customers, users, developers, testers, managers, etc. The quality of the requirement engineering process affects the quality of the software system and the success of the project. Therefore, it is essential to produce a requirements management plan that will aim to describe the organization, roles, responsibilities, tools, methods, standards, and metrics for the requirement engineering process.



### Elicitation for the notes of the Unit 2 - Software Requirement Specifications (SRS) in the subject of Software Engineering

- Elicitation is the process of gathering, analyzing, and validating the needs and requirements of the stakeholders for a software system.
- Elicitation involves various activities, such as identifying the stakeholders, defining the scope and objectives, collecting and documenting the requirements, verifying and validating the requirements, and managing changes and conflicts.
- Elicitation techniques are the methods and tools used to elicit the requirements from the stakeholders. Some of the common elicitation techniques are:
  - Interviews: A direct and interactive way of asking questions and obtaining answers from the stakeholders.
  - Questionnaires: A structured and standardized way of collecting information from a large number of stakeholders.

### Feasibility Study

- A feasibility study is an analysis of the viability of a project before it is undertaken.
- It evaluates the technical, economic, social, legal, and environmental aspects of the project to determine if it is worth pursuing.
- A feasibility study helps to identify the risks, benefits, costs, and resources required for the project, and to compare them with alternative solutions.
- A feasibility study also helps to define the scope, objectives, and constraints of the project, and to establish the feasibility criteria for its success.
- A feasibility study is usually conducted in the early stages of the software development life cycle (SDLC), before the software requirement specifications (SRS) are prepared.
- A feasibility study can be classified into four types: operational feasibility, technical feasibility, economic feasibility, and schedule feasibility.

#### Operational Feasibility

- Operational feasibility assesses the extent to which the proposed system can solve the existing problems and meet the user needs and expectations.
- It considers the operational aspects of the system, such as usability, compatibility, reliability, maintainability, security, and performance.
- It also considers the organizational aspects of the system, such as the impact on the existing processes, policies, culture, and structure, and the availability of the necessary skills, training, and support.
- Operational feasibility can be measured by conducting surveys, interviews, observations, and prototyping with the potential users and stakeholders of the system.

#### Technical Feasibility

- Technical feasibility assesses the extent to which the proposed system can be implemented using the available technology and resources.
- It considers the technical aspects of the system, such as the hardware, software, network, database, and integration requirements, and the compatibility with the existing systems and standards.
- It also considers the technical risks and challenges involved in the development, deployment, and operation of the system, and the availability of the necessary expertise, tools, and methods.
- Technical feasibility can be measured by conducting research, analysis, testing, and evaluation of the technical options and solutions.

#### Economic Feasibility

- Economic feasibility assesses the extent to which the proposed system can generate the expected benefits and returns on investment (ROI).
- It considers the economic aspects of the system, such as the costs, benefits, revenues, and savings associated with the development, operation, and maintenance of the system, and the comparison with the alternative solutions.
- It also considers the economic risks and uncertainties involved in the estimation, allocation, and management of the financial resources, and the sensitivity of the results to the changes in the assumptions and variables.
- Economic feasibility can be measured by conducting cost-benefit analysis, break-even analysis, net present value analysis, and payback period analysis.

#### Schedule Feasibility

- Schedule feasibility assesses the extent to which the proposed system can be completed within the given time frame and deadlines.
- It considers the schedule aspects of the system, such as the duration, milestones, deliverables, and dependencies of the project activities, and the availability and allocation of the human and material resources.
- It also considers the schedule risks and contingencies involved in the planning, execution, and control of the project, and the trade-offs between the time, cost, and quality of the system.
- Schedule feasibility can be measured by conducting work breakdown structure, Gantt chart, network diagram, and critical path analysis.

### Data Flow Diagrams

- A data flow diagram (DFD) is a graphical representation of the flow of data and information in a system or process.
- A DFD shows the sources and destinations of data, the processes that transform data, the data stores that hold data, and the data flows that connect them.
- A DFD can be used to model the logical or physical aspects of a system, or both.
- A DFD can be used for analysis or design of software systems, business processes, or any other system that involves data processing.
- A DFD can help software engineers to understand the operation and limitations of a system, to identify the requirements and specifications of a system, and to communicate and document the system design.

### Types of Data Flow Diagrams

- There are two main types of data flow diagrams: context diagrams and levelled diagrams.
- A context diagram is the highest-level DFD, which shows the system as a single process and its interaction with external entities (such as users, customers, or other systems).
- A levelled diagram is a DFD that decomposes the system into multiple levels of detail, showing the sub-processes and data flows within each process.
- A levelled diagram can use different notations, such as Yourdon and Coad, Gane and Sarson, or UML, to represent the processes, data stores, data flows, and external entities.
- A levelled diagram can use different numbering schemes, such as balanced, exploded, or partitioned, to indicate the hierarchy and relationship of the processes.

### Symbols and Notations of Data Flow Diagrams

- The common symbols and notations used in data flow diagrams are:

  - Process: A process is a transformation or manipulation of data, such as calculation, sorting, or filtering. A process is represented by a circle, a rectangle, or a rounded rectangle, with a name or a number inside.
  - Data store: A data store is a place where data is stored or retrieved, such as a database, a file, or a memory. A data store is represented by two parallel lines, with a name or a number above or between them.
  - Data flow: A data flow is a movement or transfer of data from one point to another, such as input, output, or feedback. A data flow is represented by an arrow, with a name or a label above or along it.
  - External entity: An external entity is a source or destination of data that is outside the system boundary, such as a user, a customer, or another system. An external entity is represented by a square, a rectangle, or an oval, with a name inside.

### Entity Relationship Diagrams

- Entity Relationship Diagrams (ERDs) are a data modeling method used in software engineering to produce a conceptual data model of an information system.
- ERDs help to identify different system elements and their relationships with each other. They are often used as the basis for data flow diagrams or DFDs.
- ERDs consist of different symbols and connectors that visualize two important information: the major entities within the system scope, and the inter-relationships among these entities.
- The main components of ERDs are:
  - Entity: An entity is a real-world object or concept that can be identified by a unique attribute or a set of attributes. For example, a student, a course, a book, etc. Entities are represented by rectangles in ERDs.
  - Attribute: An attribute is a property or characteristic of an entity that describes some aspect of it. For example, a student entity may have attributes such as name, ID, age, etc. Attributes are represented by ovals in ERDs.
  - Relationship: A relationship is an association or link between two or more entities that expresses some business rule or logic. For example, a student entity may have a relationship with a course entity that indicates the student is enrolled in the course. Relationships are represented by diamonds or lines in ERDs.
  - Cardinality: Cardinality is a constraint that specifies the number of instances of one entity that can be associated with instances of another entity in a relationship. For example, a student entity may have a one-to-many relationship with a course entity, meaning that one student can enroll in many courses, but one course can only have one student. Cardinality is represented by symbols or numbers on the relationship lines in ERDs.
- ERDs can be classified into three types based on the level of abstraction and detail they provide:
  - Conceptual ERD: A conceptual ERD is a high-level overview of the main entities and relationships in the system, without specifying any attributes or cardinalities. It is used to communicate the general idea of the system to stakeholders and users.
  - Logical ERD: A logical ERD is a more detailed and normalized version of the conceptual ERD, that specifies the attributes and cardinalities of each entity and relationship. It is used to design the logical structure of the database and to ensure data integrity and consistency.
  - Physical ERD: A physical ERD is a representation of how the logical ERD will be implemented in a specific database management system. It includes the physical characteristics of the database, such as data types, indexes, keys, constraints, etc.
- ERDs can be created using various software tools, such as Visual Paradigm, ConceptDraw, Creately, etc  . These tools allow users to draw and edit ERDs using graphical interfaces and generate SQL scripts or DDL statements to create the database tables  .
- ERDs are useful for software engineering because they provide a clear and concise way of modeling the data requirements and relationships of a system, which can help to avoid errors, ambiguities, and redundancies in the database design and development  .



### Decision Tables

- A decision table is a tabular representation of the conditions and actions of a system or a software module.
- A decision table consists of four quadrants: condition stub, condition entries, action stub, and action entries.
- The condition stub lists the possible conditions or inputs that affect the system or module behavior.
- The condition entries are the combinations of values (true/false, yes/no, etc.) that the conditions can take.
- The action stub lists the possible actions or outputs that the system or module can perform.
- The action entries are the indicators (X, check mark, etc.) that show which actions are executed for each combination of condition values.
- A decision table can be used to specify the functional requirements of a system or module in a clear and concise way.
- A decision table can also be used to test the system or module by checking if the actual behavior matches the expected behavior for each combination of condition values.
- A decision table can be constructed using the following steps:
  - Identify the conditions and actions that are relevant to the system or module.
  - Determine the number of columns needed for the condition entries. This is equal to the number of possible combinations of condition values, which is 2^n, where n is the number of conditions.
  - Assign a column number to each combination of condition values. A common method is to use binary notation, where each bit represents a condition value (0 for false, 1 for true).
  - Fill in the condition entries for each column by writing the corresponding condition values.
  - Fill in the action entries for each column by writing an indicator for each action that is executed for that column.
  - Simplify the decision table by eliminating duplicate or redundant columns or rows, or by using rules or expressions to represent complex conditions or actions.

Quality analysis measures and ensures the compliance of the system with the quality standards and criteria, such as reliability, usability, efficiency, maintainability, and portability. Trade-off analysis compares and balances the benefits and costs of different design choices and options.   - Appendices: It contains any additional or supplementary information that supports or complements the main content of the document, such as glossary, references, bibliography, or index.

### Coupling and Cohesion Measures

Coupling and cohesion are two key concepts in software engineering that are used to measure the quality of a software system's design. They are related to the degree of interdependence and modularity of the software components.

#### Coupling
- Coupling refers to the degree of interdependence between software modules .
- High coupling means that modules are closely connected and changes in one module may affect other modules .
- Low coupling means that modules are independent and changes in one module have minimal impact on other modules .
- Low coupling is desirable as it makes the system easier to maintain, test, and reuse  .
- Coupling can be measured by various metrics, such as efferent coupling, afferent coupling, instability, and abstractness.
- Efferent coupling is the number of outgoing dependencies from a module to other modules.
- Afferent coupling is the number of incoming dependencies to a module from other modules.
- Instability is the ratio of efferent coupling to total coupling (efferent + afferent).
- Abstractness is the ratio of abstract classes and interfaces to total classes and interfaces in a module.
- A module with high efferent coupling and low afferent coupling is unstable and difficult to change.
- A module with low efferent coupling and high afferent coupling is stable and easy to change.
- A module with high abstractness and low instability is abstract and stable.
- A module with low abstractness and high instability is concrete and unstable.

#### Cohesion
- Cohesion refers to the degree of relatedness and unity of the elements within a software module .
- High cohesion means that the elements within a module are strongly related and perform a single well-defined task .
- Low cohesion means that the elements within a module are weakly related and perform multiple unrelated tasks .
- High cohesion is desirable as it makes the system easier to understand, maintain, and reuse  .
- Cohesion can be measured by various metrics, such as functional cohesion, sequential cohesion, communicational cohesion, procedural cohesion, temporal cohesion, logical cohesion, and coincidental cohesion .
- Functional cohesion is the highest level of cohesion, where the elements within a module perform a single specific function .
- Sequential cohesion is where the elements within a module are related by the sequence of operations, such that the output of one element is the input of another element .
- Communicational cohesion is where the elements within a module are related by the data they operate on, such that they access the same data or data structure .
- Procedural cohesion is where the elements within a module are related by the order of execution, such that they follow a specific control flow .
- Temporal cohesion is where the elements within a module are related by the time of execution, such that they are executed together in a specific time period .
- Logical cohesion is where the elements within a module are related by the logic of the task, such that they perform different tasks based on some condition .
- Coincidental cohesion is the lowest level of cohesion, where the elements within a module are not related at all and are grouped arbitrarily .

### Design Strategies for the notes of the Unit 3 - Software Design in the subject of Software Engineering

- System design is a critical component of software engineering and involves making decisions about the architecture, components, modules, interfaces, and data for a software system.
- System design strategy refers to the approach that is taken to design a software system.
- There are several strategies that can be used to design software systems, including the following :
  - Top-Down Design: This strategy starts with a high-level view of the system and gradually breaks it down into smaller, more manageable components. The top-level component defines the overall functionality and behavior of the system, and the lower-level components implement the details and sub-functions. This strategy is useful for complex systems that require a clear and modular structure.
  - Bottom-Up Design: This strategy starts with the low-level components and builds them up into higher-level components that provide the desired functionality and behavior of the system. The low-level components are tested and integrated first, and then combined to form the higher-level components. This strategy is useful for systems that are based on existing or reusable components, or that have well-defined interfaces and data flows.
  - Structured Design: This strategy focuses on the data and control structures of the system, and organizes the components into a hierarchy of modules that communicate through well-defined interfaces. The modules are designed to have high cohesion and low coupling, meaning that they are self-contained and independent of each other. This strategy is useful for systems that have clear and stable requirements, and that need to be reliable and maintainable.
  - Function-Oriented Design: This strategy focuses on the functions and processes of the system, and decomposes the system into a set of functions that are performed by the components. The functions are designed to have high fan-in and low fan-out, meaning that they are invoked by many components and invoke few components. This strategy is useful for systems that have dynamic and changing requirements, and that need to be flexible and adaptable.
  - Object-Oriented Design: This strategy focuses on the objects and classes of the system, and models the system as a collection of interacting objects that have state and behavior. The objects are designed to have high encapsulation and polymorphism, meaning that they hide their internal details and can have different implementations. This strategy is useful for systems that have complex and diverse requirements, and that need to be reusable and extensible.

The layers are designed to have low dependency and high abstraction, meaning that they are loosely coupled and hide their implementation details. This pattern is useful for systems that need to separate concerns and responsibilities, and that need to be portable and interoperable.
  - Client-Server Pattern: This pattern divides the system into two types of components: clients and servers. The clients request services from the servers, and the servers provide services to the clients. The clients and servers are designed to have high distribution and scalability, meaning that they can be located on different machines and can handle multiple requests.   - Event-Driven Pattern: This pattern models the system as a set of event sources and event consumers that communicate through asynchronous messages. The event sources generate events that represent changes in the system state, and the event consumers react to the events that are relevant to them. The event sources and consumers are designed to have high decoupling and responsiveness, meaning that they are unaware of each other and can handle events quickly. This pattern is useful for systems that need to support complex and dynamic interactions, and that need to be reactive and scalable.



### Function Oriented Design

- Function Oriented Design is an approach to software design where the design is decomposed into a set of interacting units or modules where each unit or module has a clearly defined function .
- The main focus of Function Oriented Design is on the functions or operations that the software performs, rather than the data or information that the software manipulates.
- Function Oriented Design is based on the principle of top-down decomposition, where the software is divided into smaller and simpler sub-problems, and each sub-problem is further divided until it becomes a single function or module.
- Function Oriented Design follows a structured programming paradigm, where the control flow of the software is represented by using constructs such as sequence, selection, and iteration.
- Function Oriented Design uses various design notations and techniques to model the software, such as:

- Function Oriented Design has some advantages, such as:
  - It is easy to understand and implement, as it follows a natural way of problem solving.
  - It facilitates modularization and reusability of code, as each function or module can be tested and maintained independently.
  - It supports top-down testing and debugging, as each function or module can be verified before integrating with others.
- Function Oriented Design also has some disadvantages, such as:
  - It does not consider the data or information aspects of the software, which may lead to data redundancy and inconsistency.
  - It may result in poor performance and efficiency, as the software may have to pass large amounts of data between functions or modules.
  - It may not be suitable for complex and dynamic software systems, as it does not capture the interactions and behaviors of the software entities.

### Top-Down and Bottom-Up Design

- Top-down and bottom-up design are two strategies of information processing and knowledge ordering, used in a variety of fields including software engineering.
- Top-down design starts with a general overview of the system and then decomposes it into lower-level components that are easier to implement and test .
- Bottom-up design starts with the most specific and basic components and then composes them into higher-level components that provide more functionality and abstraction .
- Some advantages of top-down design are :
  - It helps to clarify the system objectives and scope.
  - It facilitates modularization and reuse of code.
  - It allows for parallel development of sub-systems.
  - It enables early detection of design errors and inconsistencies.
- Some disadvantages of top-down design are :
  - It may require extensive prototyping and stubs to test the system.
  - It may lead to poor integration of sub-systems if the interfaces are not well defined.
  - It may overlook some low-level details or constraints that affect the system performance or feasibility.
  - It may impose a rigid structure that is hard to modify or adapt to changing requirements.
- Some advantages of bottom-up design are :
  - It ensures that the basic components are functional and reliable before integrating them into higher-level components.
  - It allows for incremental testing and debugging of the system.
  - It can cope with complex or poorly defined problems by experimenting with different solutions.
  - It can accommodate changes or enhancements more easily by adding or modifying components.
- Some disadvantages of bottom-up design are :
  - It may result in redundant or unnecessary components that waste resources or complicate the system.
  - It may lack a clear vision or direction for the system as a whole.
  - It may produce a system that does not meet the user expectations or needs.
  - It may require extensive refactoring or restructuring of the system to improve its quality or maintainability.
- Modern software design approaches usually combine both top-down and bottom-up strategies to balance the benefits and drawbacks of each method .
- Object-oriented programming is an example of a hybrid approach that supports both top-down and bottom-up design by using classes, inheritance, polymorphism, and encapsulation .

### Various Size Oriented Measures

- Size oriented measures are software metrics that are derived by normalizing quality and/or productivity measures by considering the size of the software that has been produced .

### Halestead’s Software Science

- Halestead’s software science is a set of metrics that measure various aspects of software complexity and quality.
- The metrics are based on the analysis of the operators and operands in the source code of a program.
- Operators are the symbols that represent actions or functions, such as +, -, *, /, =, if, while, etc.
- Operands are the symbols that represent data or values, such as variables, constants, literals, etc.
- Halestead’s software science defines four basic measures:

  - n1: the number of distinct operators in the program
  - n2: the number of distinct operands in the program
  - N1: the total number of operators in the program
  - N2: the total number of operands in the program

- Based on these four measures, Halestead’s software science derives the following metrics:

  - Program length (N): the total number of operators and operands in the program, i.e., N = N1 + N2
  - Program vocabulary (n): the total number of distinct operators and operands in the program, i.e., n = n1 + n2
  - Volume (V): the amount of information contained in the program, i.e., V = N * log2(n)
  - Difficulty (D): the effort required to write or understand the program, i.e., D = (n1/2) * (N2/n2)
  - Effort (E): the amount of work or resources needed to develop the program, i.e., E = D * V
  - Time (T): the estimated time required to write the program, i.e., T = E / 18 seconds
  - Bugs (B): the estimated number of errors in the program, i.e., B = V / 3000

- Halestead’s software science can be used to compare the complexity and quality of different programs or different versions of the same program.
- The metrics can also be used to estimate the development time and cost of a program, as well as the maintenance effort and reliability of a program.
- However, Halestead’s software science has some limitations, such as:

  - It is language-dependent, as different languages have different sets of operators and operands.
  - It is sensitive to the coding style and formatting of the program, as different ways of writing the same logic can affect the counts of operators and operands.
  - It does not consider the logical structure or design of the program, such as modularity, cohesion, coupling, etc.
  - It does not account for the external factors that influence the development process, such as requirements, specifications, testing, documentation, etc.



### Function Point (FP) Based Measures

- Function points are a unit of measurement used to quantify the amount of business functionality being delivered by a software application.
- Function points measure the size of an application system based on the functional view of the system.
- Function points allow software engineers to better measure the size of a project, identify areas in need of optimization, and analyze development performance benchmarks over time.
- Function points are one of the most widely used measures of software size .
- The basis of function points is that the “functionality” of the system, that is, what the system performs, is the measure of the system size .
- Function points are independent of the technology, programming language, or development methodology used to build the software application.
- Function points are calculated by counting the number of inputs, outputs, queries, internal files and external files in the system and adjusting that total for the functional complexity of the system .
- The steps for counting function points are:
  - Identify the type of project (development, enhancement, or maintenance) and the type of count (application or project).
  - Identify the user requirements and the logical transactions of the system.
  - Classify the logical transactions into five types: external inputs (EI), external outputs (EO), external inquiries (EQ), internal logical files (ILF), and external interface files (EIF).
  - Assign a complexity level (low, average, or high) to each logical transaction based on the number of data elements and file types involved.
  - Use a complexity-weighting table to assign a numerical value to each logical transaction based on its type and complexity level.
  - Sum the numerical values of all the logical transactions to obtain the unadjusted function point (UFP) count.
  - Determine the value adjustment factor (VAF) by rating 14 general system characteristics (GSC) on a scale of 0 to 5 and summing the ratings.
  - Multiply the UFP by the VAF to obtain the adjusted function point (AFP) count.
- Function points can be used to estimate the effort, cost, and duration of a software project based on historical data and productivity factors.
- Function points can also be used to compare the productivity and quality of different software projects or teams.
- Function points are mainly used for measuring the size of management information system (MIS) software.



### Cyclomatic Complexity Measures

- Cyclomatic complexity is a software metric used to measure the complexity of a program   .
- It is a quantitative measure of the number of linearly independent paths through a program's source code  .
- It was developed by Thomas J. McCabe, Sr. in 1976 .
- McCabe interprets a computer program as a set of a strongly connected directed graph, where the nodes represent the basic blocks of the program and the edges represent the control flow between them .
- The cyclomatic complexity of a program can be calculated by using the following formula :

  - `V(G) = E - N + 2P`
  - where `V(G)` is the cyclomatic complexity, `E` is the number of edges, `N` is the number of nodes, and `P` is the number of connected components in the graph.

- Alternatively, the cyclomatic complexity can be calculated by using the following formula :

  - `V(G) = R + 1`
  - where `R` is the number of regions in the graph.

- The cyclomatic complexity can also be calculated by counting the number of decision points (such as `if`, `while`, `for`, `case`, etc.) in the program and adding one :

  - `V(G) = D + 1`
  - where `D` is the number of decision points.

- The cyclomatic complexity can be used to estimate the number of test cases required to cover all the possible paths in a program  .
- The cyclomatic complexity can also be used to indicate the maintainability, readability, and testability of a program  .
- The higher the cyclomatic complexity, the more complex the program is, and the more likely it is to contain errors or defects  .
- The lower the cyclomatic complexity, the simpler the program is, and the easier it is to understand, modify, and test  .
- There is no definitive threshold for the acceptable cyclomatic complexity, but some common guidelines are  :

  - A cyclomatic complexity of 1-10 is considered good.
  - A cyclomatic complexity of 11-20 is considered moderate.
  - A cyclomatic complexity of 21-50 is considered high.
  - A cyclomatic complexity of above 50 is considered very high and should be avoided or refactored.

- There are various tools available to measure the cyclomatic complexity of a program, such as Visual Studio, SonarQube, CodeClimate, etc. .



### Control Flow Graphs

- A control flow graph (CFG) is a graphical representation of the control flow or computation during the execution of a program or application .
- A CFG consists of nodes and edges, where nodes represent basic blocks and edges represent the possible transitions between them .
- A basic block is a maximal sequence of straight-line, or branch-free, code that always executes together, unless an exception occurs .
- A CFG can accurately represent the flow of control inside a program unit, such as a function, a method, or a module .
- A CFG can be used for various purposes, such as static analysis, compiler optimization, testing, debugging, and reverse engineering .

### Unit Testing

Unit testing is a process of testing individual units or components of a software application. A unit is the smallest testable part of the software's code, such as a function, method, module, object, or other entity. Unit testing has the following characteristics and benefits:

- Unit testing is a component of test-driven development (TDD), a methodology that takes a meticulous approach to building a product by means of continual testing and revision.
- Unit testing provides a strict, written contract that the piece of code must satisfy, and ensures that each unit of code works as intended.

- Unit testing improves the quality, reliability, and maintainability of the software product.
- Unit testing facilitates code refactoring, debugging, and documentation.

### Integration Testing

- Integration testing is a level of software testing where individual units or components are combined and tested as a group.
- The purpose of integration testing is to expose faults in the interaction between integrated units and to verify the compliance of a system or component with specified functional requirements .
- Integration testing is important because it ensures the successful integration of modules, the data integrity across different components, and the user-based functionality of the software application.
- There are different types of integration testing, such as:
  - Big-Bang Integration Testing: It is the simplest integration testing approach, where all the modules are combined and tested at once. It is suitable for small and simple projects, but it has the disadvantages of late defect detection, high debugging complexity, and low testability.
  - Bottom-Up Integration Testing: It is an incremental integration testing approach, where each module at lower levels is tested with higher modules using drivers (dummy modules that simulate the higher modules). It is suitable for projects with complex lower-level modules, but it has the disadvantages of requiring many drivers, delaying the testing of critical functionalities, and ignoring the system interface errors.
  - Top-Down Integration Testing: It is another incremental integration testing approach, where each module at higher levels is tested with lower modules using stubs (dummy modules that simulate the lower modules). It is suitable for projects with complex higher-level modules, but it has the disadvantages of requiring many stubs, delaying the testing of data processing functionalities, and ignoring the system integration errors.
  - Sandwich Integration Testing: It is a hybrid integration testing approach, where both bottom-up and top-down testing are performed simultaneously. It is suitable for projects with complex and interdependent modules, but it has the disadvantages of requiring both drivers and stubs, increasing the testing complexity, and requiring high coordination among testers.
- Some of the best practices or guidelines for integration testing are:
  - First, determine the integration test strategy that could be adopted and later prepare the test cases and test data accordingly.
  - Study the architecture design of the application and identify the critical modules. These need to be tested on priority.
  - Obtain the interface specifications and contracts for each module and verify the input and output parameters, data types, error handling, and exception handling.
  - Use appropriate tools and frameworks to automate the integration testing process and to generate test reports and coverage metrics.
  - Perform regression testing after each integration testing cycle to ensure that the previously integrated modules are still working as expected.

### Regression Testing

- Regression testing can be performed manually or using automated tools. Automated regression testing is preferred when the system has frequent changes, large test cases, or complex functionality.

This can help to execute the most important test cases first and increase the effectiveness of regression testing.
  - Test case minimization: This technique involves reducing the number of test cases by eliminating redundant or obsolete test cases. This can further optimize the cost and time of regression testing, but also require careful analysis and maintenance of the test cases.

### Top-Down and Bottom-Up Testing Strategies

- Top-down and bottom-up testing are two strategies for integration testing, which is a type of software testing that aims to verify the interactions and interfaces between different modules or components of a software system.
- Integration testing can be performed either after unit testing, which tests individual modules in isolation, or before unit testing, which tests the whole system as a single unit.
- Top-down testing and bottom-up testing differ in the order and direction of testing the modules or components, as well as the use of stubs and drivers, which are temporary substitutes for missing or incomplete modules or components.

#### Top-Down Testing

- Top-down testing is a strategy that starts with testing the highest-level or main module or component of the system, and then gradually moves down to the lower-level or subordinate modules or components.
- Top-down testing is driven by the principle that the main logic of an application needs more testing and verification than supporting logic. Top-down testing allows comparison of the application to functional requirements earlier than a bottom-up approach.
- Top-down testing requires the use of stubs, which are dummy modules or components that simulate the behavior of the lower-level or subordinate modules or components that are not yet developed or integrated . Stubs provide predefined inputs and outputs to the higher-level or main module or component, and can be replaced by the actual modules or components as they become available .

#### Bottom-Up Testing

- Bottom-up testing is a strategy that starts with testing the lowest-level or individual modules or components of the system, and then gradually moves up to the higher-level or integrated modules or components.
- Bottom-up testing is driven by the principle that the individual processes or functionalities of an application need more testing and verification than the overall logic or flow of the system. Bottom-up testing allows early detection of errors and defects in the individual modules or components, and reduces the need for debugging later in the development process .
- Bottom-up testing requires the use of drivers, which are dummy modules or components that simulate the behavior of the higher-level or main module or component that is not yet developed or integrated . Drivers provide predefined inputs and outputs to the lower-level or individual modules or components, and can be replaced by the actual modules or components as they become available .

#### Comparison of Top-Down and Bottom-Up Testing

- Both top-down and bottom-up testing have advantages and disadvantages, and the choice of strategy depends on various factors, such as the complexity and size of the system, the availability and dependency of the modules or components, the time and cost constraints, and the testing objectives and requirements.
- Some of the main differences between top-down and bottom-up testing are  :

| Top-Down Testing | Bottom-Up Testing |
| ---------------- | ----------------- |
| Starts with testing the main module or component and then moves down to the subordinate modules or components | Starts with testing the individual modules or components and then moves up to the integrated modules or components |
| Requires the use of stubs to simulate the lower-level or subordinate modules or components | Requires the use of drivers to simulate the higher-level or main module or component |
| Allows early comparison of the application to functional requirements and verification of the main logic or flow of the system | Allows early detection of errors and defects in the individual modules or components and verification of the individual processes or functionalities of the application |
| May miss some errors or defects in the lower-level or subordinate modules or components due to the use of stubs | May miss some errors or defects in the higher-level or integrated modules or components due to the use of drivers |
| May require more time and effort to create and maintain stubs | May require more time and effort to create and maintain drivers |
| May be more suitable for systems that have a clear hierarchical structure and a top-down development approach | May be more suitable for systems that have a complex or modular structure and a bottom-up development approach |



### Test Drivers and Test Stubs

- Test drivers and test stubs are two types of **test harness**, which is a collection of software and test data that is configured together in order to test a unit of a program by stimulating various conditions while constantly monitoring its outputs and behavior.
- Test drivers and test stubs are used in **integration testing**, which is a type of testing that aims to verify the functionality, performance, and reliability of different modules or components of a software system when they are combined together.
- Test drivers and test stubs are used to simulate the **missing or incomplete modules** or components that are required for integration testing, but are not yet available or ready for testing.
- Test drivers and test stubs are also used to **isolate** the module or component under test from the rest of the system, so that any errors or defects can be easily identified and traced to the source.

#### Test Drivers
- A test driver is a piece of code that **emulates a calling function** or module. It is also known as a **dummy main function** that calls other modules or components to form a complete application .
- Test drivers are created in integration testing following a **bottom-up approach**, which means that the testing starts from the lowest or most basic level of modules or components and moves up to the higher or more complex levels .
- Test drivers are used to **pass test cases** to the modules or components that are being tested, and to **receive and verify the outputs** from them .
- Test drivers are usually **written by the testers** or developers who are responsible for testing the modules or components.

#### Test Stubs
- A test stub is a piece of code that **emulates a called function** or module. It is also known as a **dummy subprogram** that returns predefined values or responses to the calling function or module .
- Test stubs are created in integration testing following a **top-down approach**, which means that the testing starts from the highest or most complex level of modules or components and moves down to the lower or more basic levels .
- Test stubs are used to **simulate the behavior** of the modules or components that are not yet available or ready for testing, and to **provide dummy inputs** to the calling function or module .
- Test stubs are usually **written by the developers** who are responsible for developing the modules or components.

#### Advantages of Test Drivers and Test Stubs
- Test drivers and test stubs **reduce the dependency** on the availability or readiness of the other modules or components for integration testing, and thus **avoid unnecessary delays** in the testing process .
- Test drivers and test stubs **isolate** the module or component under test from the rest of the system, and thus **facilitate the identification and localization** of any errors or defects in the module or component .
- Test drivers and test stubs **simulate various scenarios** and conditions that may not be possible or easy to create or reproduce in the real system, and thus **enhance the coverage and effectiveness** of the integration testing .



### Structural Testing (White Box Testing) for the notes of the Unit 4 - Software Testing in the subject of Software Engineering

- Structural testing, also known as white box testing, is a method of software testing that tests the internal structure, logic, and code of the software system  .

- The main objective of structural testing is to verify the quality, reliability, security, and performance of the software system by checking its code coverage, data flow, control flow, and error handling  .

  - Statement coverage: It measures the percentage of executable statements that are covered by the test cases.
  - Branch coverage: It measures the percentage of branches or decision points that are covered by the test cases.

  - Condition coverage: It measures the percentage of logical conditions or expressions that are evaluated to both true and false by the test cases.
  - Data flow testing: It analyzes the flow of data values and variables between the definitions and uses of the data in the code.
  - Control flow testing: It analyzes the flow of control or execution between the nodes and edges of the code graph.

### Functional Testing (Black Box Testing) for the notes of the Unit 4 - Software Testing in the subject of Software Engineering

- Functional testing is a quality assurance (QA) process and a type of black-box testing that bases its test cases on the specifications of the software component under test.
- Functional testing usually describes what the system does, not how it does it. The internal program structure is rarely considered (unlike white-box testing).
- Functional testing can be done at different levels of software development, such as unit testing, integration testing, system testing, and acceptance testing.
- Functional testing can be done manually or with the help of automated tools.
- Functional testing can be classified into two types: positive testing and negative testing. Positive testing verifies that the system works as expected for valid inputs and conditions. Negative testing checks that the system handles invalid inputs and errors gracefully.
- Functional testing can cover various aspects of the software functionality, such as:
  - Input and output validation
  - Data manipulation and processing
  - User interface and navigation
  - Security and access control
  - Business rules and logic
  - Compatibility and interoperability
  - Performance and reliability
- Functional testing can be done using various techniques, such as:
  - Equivalence partitioning: dividing the input domain into equivalent classes and selecting one representative value from each class for testing.
  - Boundary value analysis: testing the values at the boundaries of the input domain, such as minimum, maximum, and just inside and outside the boundaries.
  - Decision table testing: using a table to represent the combinations of inputs and outputs for different scenarios and rules.
  - State transition testing: testing the behavior of the system when it changes from one state to another based on inputs and events.
  - Use case testing: testing the system based on the user's perspective and actions.
  - Error guessing: using intuition and experience to guess the possible errors and defects in the system.
- Functional testing can be done in the following ways:
  - Syntax-driven testing: applied to systems that can be syntactically represented by some language, such as compilers and languages that can be represented by a context-free grammar.
  - Graph-based testing: applied to systems that can be modeled by a graph, such as finite state machines and control flow graphs.
  - Error-based testing: applied to systems that have known or predictable errors, such as boundary errors and overflow errors.
  - Domain testing: applied to systems that have a well-defined input domain, such as mathematical functions and algorithms.
  - Random testing: applied to systems that have a large or complex input domain, such as operating systems and networks.

- The objectives of FTR are :
  - To uncover errors in function, logic, or implementation for any representation of the software, such as requirements, design, code, test cases, etc.
  - To verify that the software meets the specified requirements and conforms to the standards and guidelines.
  - To improve the quality of the software product and the software process by identifying and eliminating defects early in the software development life cycle.
  - To provide feedback and suggestions for improvement to the software developers and managers.
  - To facilitate communication and collaboration among the software team members and stakeholders.
  - To serve as a training ground for junior engineers to learn from the different approaches and techniques of software engineering.
- The FTR process involves the following steps  :
  - Planning: The FTR leader selects the review team, assigns roles and responsibilities, schedules the review meeting, and distributes the review materials to the reviewers.
  - Preparation: The reviewers study the review materials and identify potential issues, questions, and comments. They also prepare a checklist of items to be verified during the review.
  - Review meeting: The review team meets to discuss the review materials and resolve the issues. The FTR leader moderates the meeting and ensures that the review objectives are met. The FTR scribe records the minutes of the meeting and the list of action items.
  - Rework: The software developers perform the necessary corrections and improvements based on the review feedback and action items.
  - Follow-up: The FTR leader verifies that the rework has been done satisfactorily and closes the review. The FTR leader also prepares a review report that summarizes the review results and recommendations.
- The FTR team consists of the following roles  :
  - FTR leader: The person who plans, organizes, and conducts the review. The FTR leader is usually a senior software engineer or a software quality assurance engineer.
  - FTR scribe: The person who records the review proceedings and the action items. The FTR scribe is usually a junior software engineer or a software quality assurance engineer.
  - Reviewers: The persons who examine the review materials and provide feedback and suggestions. The reviewers are usually software engineers or software quality assurance engineers who have expertise in the relevant domain or technology.
  - Presenter: The person who presents the review materials and answers the questions from the reviewers. The presenter is usually the software developer or the software manager who is responsible for the software product or the software process under review.
  - Observers: The persons who attend the review meeting but do not actively participate in the review. The observers are usually software engineers or software quality assurance engineers who are interested in learning from the review.
- The FTR guidelines are the following  :
  - The FTR should be conducted at regular intervals throughout the software development life cycle, preferably after each major milestone or deliverable.
  - The FTR should focus on the technical aspects of the software product or the software process, not on the personal performance or preferences of the software developers or managers.
  - The FTR should be constructive, objective, and respectful, not destructive, subjective, or hostile. The reviewers should provide positive feedback as well as negative feedback, and avoid personal attacks or criticisms.
  - The FTR should be efficient, effective, and timely, not wasteful, redundant, or delayed. The review meeting should be well-organized, well-prepared, and well-facilitated, and last no longer than two hours. The review materials should be relevant, complete, and accurate, and distributed to the reviewers at least one week before the review meeting. The review feedback and action items should be clear, concise, and actionable, and addressed as soon as possible after the review meeting.
  - The FTR should be documented, tracked, and reported, not ignored, forgotten, or hidden. The review proceedings and the action items should be recorded and stored in a repository. ### Reverse Engineering

Reverse engineering is a process or method of analyzing a software system or a product to understand its components, structure, functionality, and behavior. It is often done to extract the design, specifications, and requirements of the system or product, or to create a representation of it in another form or at a higher level of abstraction  .

Some of the objectives of reverse engineering are:

- To recover lost or unavailable source code from the executable code.
- To enhance the performance, quality, or functionality of the system or product.
- To fix bugs, errors, or vulnerabilities in the system or product.
- To understand the logic, algorithms, or techniques used by the system or product.
- To reuse or modify the system or product for a new purpose or application.
- To comply with legal or ethical standards, such as interoperability, compatibility, or security.

Some of the steps involved in reverse engineering are:

- Disassembly: The process of converting the executable code into assembly code, which is a low-level representation of the instructions executed by the processor.
- Decompilation: The process of converting the assembly code into a high-level programming language, such as C, C++, or Java, which is more readable and understandable by humans.
- Analysis: The process of examining the decompiled code to identify the components, structure, functionality, and behavior of the system or product. This may involve using tools such as debuggers, disassemblers, decompilers, or hex editors.
- Documentation: The process of creating a representation of the system or product in another form or at a higher level of abstraction, such as diagrams, models, or specifications. This may involve using tools such as UML, ERD, or DFD.



### Software Configuration Management Activities

Software configuration management (SCM) is a process that systematically manages, organizes, and controls the changes in the documents, codes, and other entities during the software development life cycle. The primary goal is to increase productivity with minimal mistakes.

The major activities of SCM are :

- **Configuration identification** – This is the process of identifying all of the components of a project and ensuring that these components can be found quickly throughout the project life cycle. Configuration identification also involves defining the configuration items (CIs), which are the units of configuration management, and the baselines, which are the reference points for configuration control.
- **Configuration control** – This is the process of implementing a controlled change process, which involves evaluating, approving, and implementing changes to the CIs and baselines. Configuration control also involves maintaining the traceability and integrity of the CIs and baselines throughout the project life cycle.
- **Configuration status accounting** – This is the process of recording and reporting all the necessary information on the status of the development process, such as the current version, location, and owner of each CI and baseline, the history of changes to each CI and baseline, and the dependencies and relationships among the CIs and baselines.
- **Configuration auditing** – This is the process of verifying that the CIs and baselines are consistent with the requirements, design, and implementation of the project, and that they comply with the standards and regulations. Configuration auditing also involves checking that the configuration management process is followed and documented properly.
- **Release management and delivery** – This is the process of preparing and distributing the CIs and baselines to the intended users, customers, or stakeholders. Release management and delivery also involves ensuring that the CIs and baselines are compatible, secure, and reliable, and that they meet the quality and performance expectations.



### Change Control Process

Change control is the process that a company uses to document, identify and authorize changes to an IT environment. It reduces the chances of unauthorized alterations, disruption and errors in the system. Change control is also known as change management or configuration management.

The change control process consists of the following steps :

- **Change request initiation**: In this step, a change is requested by a stakeholder, a user, a developer, or a manager. The change request should describe the reason, the scope, the impact, and the urgency of the change. The change request should also be logged in a change log or a change management tool for tracking and auditing purposes.
- **Change request assessment**: In this step, the change request is reviewed and assessed by a change control board (CCB) or a change manager. The CCB or the change manager is responsible for evaluating the feasibility, the benefits, the risks, and the costs of the change. The CCB or the change manager can approve, reject, or defer the change request based on the assessment criteria.
- **Change request analysis**: In this step, the change request is analyzed in detail by the change implementer or the change team. The change implementer or the change team is responsible for designing, developing, testing, and documenting the change. The change implementer or the change team should also communicate with the stakeholders, the users, and the CCB or the change manager throughout the analysis phase.
- **Change request implementation**: In this step, the change is implemented in the IT environment by the change implementer or the change team. The change implementation should follow the change plan, the change schedule, and the change procedures. The change implementation should also be monitored and controlled by the CCB or the change manager to ensure the quality and the compliance of the change.
- **Change request evaluation**: In this step, the change is evaluated by the CCB or the change manager, the stakeholders, the users, and the change implementer or the change team. The change evaluation should measure the outcomes, the benefits, the risks, and the costs of the change. The change evaluation should also identify the lessons learned, the best practices, and the improvement opportunities for the change control process.

The change control process is an essential part of software engineering, as it helps to manage the changes that occur during the software development life cycle. The change control process also helps to ensure the alignment of the software product with the business requirements, the user expectations, and the quality standards. The change control process can be adapted to different software engineering methodologies, such as agile, waterfall, or hybrid.



### Software Version Control

- Software version control (SVC) is a management strategy to track and store changes to a software development document or set of files that follow the development project from beginning to end-of-life .
- SVC is a component of software configuration management, which is the process of controlling the evolution of software products.
- SVC helps software teams to:
  - Manage changes to source code over time and avoid conflicts or errors .
  - Collaborate effectively and coordinate their work on shared files .
  - Recover previous versions of code in case of bugs, errors, or loss of data .
  - Trace the history of changes and identify who, when, and why made them .
  - Experiment with new features or ideas without affecting the main codebase .
- SVC systems are software tools that help implement SVC by taking snapshots of the files and saving them permanently in a repository .
- SVC systems can be classified into two main types: centralized and distributed .
  - Centralized SVC systems have a single server that stores all the files and their versions, and clients that access them through a network .
  - Distributed SVC systems have multiple repositories that can be synchronized with each other, and each client has a full copy of the files and their versions .
- Some examples of popular SVC systems are: Subversion (centralized), Git (distributed), Mercurial (distributed), and Team Foundation Version Control (centralized) .
- SVC systems use different terms and concepts to describe the changes and operations on the files, such as: revision, commit, branch, merge, tag, checkout, clone, pull, push, etc .
- SVC systems also provide various features and tools to support the software development process, such as: graphical user interfaces, command-line interfaces, web interfaces, integration with other tools, code review, code analysis, code quality, etc .

### Estimation of Various Parameters such as Cost for the notes of the Unit 5 - Software Maintenance and Software Project Management in the subject of Software Engineering

Estimation is the process of predicting the amount of time, effort, resources, and cost required to complete a software project. Estimation is essential for planning, budgeting, and controlling the software project. Estimation also helps to assess the feasibility, risk, and quality of the software project.

There are various techniques for estimating software projects, each with its own advantages and disadvantages. Some of the common techniques are:

- **Expert Judgment**: In this technique, a group of experts in the relevant field estimates the project size based on their experience and expertise. This technique is often used when there is limited information available about the project.
- **Work Breakdown Structure (WBS)**: A big project is made manageable by first breaking it down into individual components in a hierarchical structure, known as the Work breakdown structure, or the WBS. Each component is then estimated separately and the total estimate is obtained by aggregating the estimates of all the components.
- **Three Point Estimation**: Three-point estimation is a technique that makes use of three types of estimates for each component of the project: optimistic, pessimistic, and most likely. The optimistic estimate is the best-case scenario, the pessimistic estimate is the worst-case scenario, and the most likely estimate is the most realistic scenario. The three estimates are then combined using a weighted average formula to obtain the final estimate.
- **Functional Point Method**: Functional point method is a technique that measures the size of the software project based on the functionality it provides to the user. The functionality is divided into five types: external inputs, external outputs, external inquiries, internal logical files, and external interface files. Each type of functionality is assigned a complexity weight based on its characteristics. The total number of function points is obtained by multiplying the number of each type of functionality by its complexity weight. The function points are then converted into effort, time, and cost using productivity factors.
- **Story Point Method**: Story point method is a technique that measures the size of the software project based on the user stories that describe the features and requirements of the software. User stories are units of measure for expressing an estimate of the overall effort required to fully implement a product backlog item or any other piece of work. Teams assign story points relative to work complexity, the amount of work, and risk or uncertainty. The total number of story points is obtained by adding the story points of all the user stories. The story points are then converted into effort, time, and cost using velocity factors.

These are some of the software estimation techniques that can be used for estimating various parameters such as cost for the notes of the Unit 5 - Software Maintenance and Software Project Management in the subject of Software Engineering. Each technique has its own strengths and limitations, and the choice of the technique depends on the nature, scope, and complexity of the software project.

### Constructive Cost Models (COCOMO) for the notes of the Unit 5 - Software Maintenance and Software Project Management in the subject of Software Engineering

- COCOMO stands for **COnstructive COst MOdel**    .
- It is a **regression model** based on the **number of lines of code (LOC)**    .
- It is a **procedural cost estimate model** for software projects and is often used as a process of reliably predicting the various parameters associated with making a project such as **size, effort, cost, time, and quality**    .
- It was developed by **Barry W. Boehm** in **1981**  .
- The model parameters are derived from fitting a **regression formula** using data from **historical projects** (63 projects for COCOMO 81 and 163 projects for COCOMO II) .
- There are three types of COCOMO models: **Basic, Intermediate, and Detailed**    .
- The Basic COCOMO model is a **static, single-valued model** that computes the software development effort (and cost) as a function of program size expressed in estimated LOC    .
- The Intermediate COCOMO model computes software development effort as a function of program size and a set of **cost drivers** that include subjective assessment of product, hardware, personnel, and project attributes    .
- The Detailed COCOMO model incorporates all characteristics of the intermediate version with an assessment of the cost driver's impact on each step (analysis, design, etc.) of the software engineering process    .
- The COCOMO model has been revised and updated since 1981 and the latest version is **COCOMO II** .
- COCOMO II is designed to model the software development process for **new and emerging software project capabilities** such as object-oriented approaches, software reuse, prototyping, and application composition.
- COCOMO II consists of four submodels: **Application Composition, Early Design, Post-Architecture, and Reuse**.
- The Application Composition submodel is used for projects that are built with modern **graphical user interface builders** or with some form of **application generator**.
- The Early Design submodel is used for projects in the **early stages of system definition** when not much is known about the system.
- The Post-Architecture submodel is used for projects that have a good understanding of the **product architecture**.
- The Reuse submodel is used for projects that involve a significant amount of **software reuse**.
- COCOMO II uses **function points** as a measure of program size instead of LOC.
- COCOMO II also uses a different set of cost drivers and scaling factors than COCOMO 81.
- The advantages of COCOMO models are that they are **simple, easy to use, widely applicable, and based on empirical data** .
- The disadvantages of COCOMO models are that they are **based on outdated data, sensitive to LOC estimation errors, not suitable for agile methods, and do not account for non-functional requirements** .



### Resource Allocation Models

Resource allocation models are used to optimize the distribution of resources among different activities or tasks in a software project. Resource allocation models can help to improve the efficiency, quality, and profitability of software development and maintenance. Some of the objectives of resource allocation models are:

- To balance the workload and the available resources
- To minimize the cost and the duration of the project
- To maximize the customer satisfaction and the value of the software
- To reduce the risk and the uncertainty of the project
- To align the resource allocation with the project goals and priorities

There are different types of resource allocation models, depending on the nature and the scope of the project, the resources involved, and the criteria for optimization. Some of the common resource allocation models are:

- **Linear programming model**: This model uses mathematical equations to represent the constraints and the objective function of the resource allocation problem. The objective function can be to minimize the cost, the time, or the deviation from the desired quality level of the software. The constraints can be the availability of the resources, the dependencies among the tasks, the deadlines, the quality standards, etc. The model can be solved using various algorithms, such as the simplex method, to find the optimal solution.
- **Queueing theory model**: This model uses stochastic processes to model the arrival and the service of the tasks in a software project. The tasks can be the software requirements, the defects, the change requests, etc. The resources can be the software developers, the testers, the managers, etc. The model can be used to analyze the performance measures of the resource allocation, such as the average waiting time, the average service time, the utilization rate, the throughput, the probability of blocking, etc. The model can also be used to compare different resource allocation strategies, such as the first-come-first-served, the shortest-job-first, the priority-based, etc.
- **Putnam resource allocation model**: This model is based on the empirical observation that the software development effort is proportional to the size of the software raised to the power of a constant. The model can be used to estimate the effort, the time, and the productivity of the software project, given the size of the software and the constant. The model can also be used to determine the optimal allocation of the resources over the different phases of the software development life cycle, such as the planning, the design, the coding, the testing, etc. The model assumes that the resources are flexible and can be shifted from one phase to another as needed.
- **Resource-sharing model**: This model is used to allocate resources in a multitenant cloud environment, where multiple tenants may rent several virtual machines (VMs) to host their applications. The model considers the multi-resource demands of the VMs, such as the CPU, the memory, the disk, the network, etc. The model also considers the heterogeneity of the physical machines (PMs) that host the VMs, such as the capacity, the cost, the energy consumption, etc. The model can be used to optimize the resource allocation according to different objectives, such as the resource utilization, the revenue, the energy efficiency, the fairness, the quality of service, etc. The model can also be used to handle the dynamic changes in the resource demands and the availability of the VMs and the PMs.



### Software Risk Analysis and Management

- Software risk is the probability of occurrence for uncertain events and their potential for loss within an organization.
- Software risk analysis is the process of identifying, categorizing, and measuring software risks .
- Software risk management is the sequence of steps that help a software team to understand, analyze, and manage uncertainty.
- Software risk management consists of the following activities:
  - Risk identification: The process of finding out the possible risks that may affect the software project objectives. This can be done by using techniques such as brainstorming, checklists, interviews, etc.
  - Risk analysis: The process of assessing the level, likelihood, and impact of each risk. This can be done by using techniques such as risk matrices, probability distributions, decision trees, etc.
  - Risk prioritization: The process of ranking the risks according to their severity and urgency. This can be done by using techniques such as risk exposure, risk score, risk ranking, etc.
  - Risk mitigation: The process of reducing the probability and/or impact of the risks. This can be done by using techniques such as risk avoidance, risk transfer, risk reduction, risk acceptance, etc.
  - Risk monitoring: The process of tracking the status and progress of the risks and their mitigation actions. This can be done by using techniques such as risk reviews, risk audits, risk reports, etc.
- Software risk management is an important component of software development as it helps to ensure the quality, reliability, and security of the software products and services .
- Software risk management can be supported by using software risk management tools that provide features such as risk identification, analysis, prioritization, mitigation, and monitoring. Some examples of software risk management tools are MetricStream, RiskyProject, Active Risk Manager, etc.
