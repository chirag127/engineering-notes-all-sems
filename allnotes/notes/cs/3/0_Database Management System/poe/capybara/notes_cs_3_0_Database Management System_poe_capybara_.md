### Database System vs File System

In the field of database management, two main systems for storing and managing data are the database system and the file system. Here are some key differences between the two:

#### Database System

- A database system is a software system designed to manage and store large amounts of data.
- Data is stored in tables, which consist of rows and columns.
- The system allows for efficient querying, indexing, and retrieval of data.
- Multiple users can access and modify the data simultaneously, with the system managing concurrency control.
- The system typically includes features for backup and recovery, security, and data integrity.

#### File System

- A file system is a method for storing and organizing files on a computer.
- Data is stored in individual files, each with a unique name and location.
- The system is typically less efficient for querying and retrieval of data than a database system.
- Multiple users can access the files, but there is typically no built-in concurrency control.
- The system may not include features for backup and recovery, security, and data integrity, unless added separately.

In summary, while a file system is suitable for simple data storage and retrieval, a database system is necessary for managing large, complex data sets with multiple users and advanced features for data management and security.

### Data Independence and Database Language and Interfaces

Data independence is the separation of data from the application programs that use the data. It is the ability to modify the schema definition in one level without affecting the schema definition in the next higher level.

There are two types of data independence:

1. Physical data independence: It is the ability to modify the physical schema without affecting the conceptual schema. It means that changes in the storage structure or access methods used to store data do not affect the application programs that use the data.

2. Logical data independence: It is the ability to modify the conceptual schema without affecting the external schema or application programs. It means that changes in the way data is represented or organized do not affect the way application programs access the data.

Database Language and Interfaces are used to interact with the database system. There are three types of database languages:

1. Data Definition Language (DDL): It is used to define and modify the schema or structure of the database. Examples of DDL statements are CREATE, ALTER, and DROP.

2. Data Manipulation Language (DML): It is used to manipulate data in the database. Examples of DML statements are SELECT, INSERT, UPDATE, and DELETE.

3. Data Control Language (DCL): It is used to control access to the database. Examples of DCL statements are GRANT and REVOKE.

There are two types of interfaces:

1. Command-line Interface (CLI): It is a text-based interface where users enter commands to interact with the database system.

2. Graphical User Interface (GUI): It is a visual interface where users interact with the database system using graphical elements such as buttons and menus.

In summary, data independence and database language and interfaces are important concepts in database management systems. Understanding these concepts is essential for efficient and effective management of databases.

### Data Modeling Using the Entity Relationship Model

Data modeling is an essential part of the process of designing a database system. The Entity Relationship Model (ERM) is a widely used data modeling technique that helps to represent entities, attributes, and relationships between them in a clear and concise way. Here are some key points to understand about data modeling using the ERM:

- An entity is an object or concept that can be uniquely identified and represented in a database. Examples of entities include customers, products, and orders.

- Attributes are characteristics of an entity that describe its properties. Examples of attributes for a customer entity include name, address, and phone number.

- Relationships define the association between two or more entities. For example, an order entity might have a relationship with a customer entity, indicating that a customer has placed an order.

- The ERM uses symbols to represent entities, attributes, and relationships. A rectangle represents an entity, an oval represents an attribute, and a diamond represents a relationship.

- Cardinality is used to express the number of instances of one entity that can be related to another. For example, a customer might have zero or many orders, while an order must have exactly one customer.

- The ERM can be used to create a conceptual model of a database system, which is a high-level representation of the data and its relationships. This model can then be used to create a logical model, which defines the structure of the database, and a physical model, which specifies how the data will be stored and accessed.

- The ERM is a flexible and powerful tool for data modeling, but it does have some limitations. For example, it cannot capture all the complexities of a real-world system, and it may not be suitable for certain types of data, such as temporal or spatial data.

In summary, data modeling using the ERM is a fundamental aspect of database design. It allows us to represent entities, attributes, and relationships in a clear and concise way, and to create a conceptual, logical, and physical model of the database system. By understanding the key concepts and symbols of the ERM, you can create effective data models that meet the needs of your organization.



### ER Model Concepts

The Entity-Relationship (ER) model is a technique used to model the relationships between entities in a database. Following are the concepts that are important to understand in the ER model.

- **Entity:** An entity is a real-world object or concept that has its own unique identity. For example, a customer, a product, or an employee can be considered as entities.

- **Attribute:** An attribute is a characteristic of an entity. For example, a customer entity can have attributes such as customer name, address, and phone number.

- **Relationship:** A relationship is an association between two or more entities. It describes how entities are related to each other. For example, a customer can place an order, which creates a relationship between the customer and the order entities.

- **Cardinality:** Cardinality determines the number of instances of one entity that can be associated with the number of instances of another entity. The three types of cardinality are **one-to-one**, **one-to-many**, and **many-to-many**.

- **Weak Entity:** A weak entity is an entity that depends on another entity for its existence. For example, a line item entity depends on an order entity for its existence.

- **Identifying Relationship:** An identifying relationship is a type of relationship in which the existence of a weak entity depends on the existence of a strong entity. For example, a line item entity depends on an order entity for its existence.

- **Subtype and Supertype:** A subtype is a subset of an entity that has attributes that are specific to a particular subset. A supertype is a general entity that contains common attributes of all the subtypes. For example, a vehicle entity can have subtypes such as car, truck, and motorcycle, each with its own specific attributes.

- **Inheritance:** Inheritance is a mechanism that allows a subtype to inherit the attributes and relationships of a supertype. For example, a car entity can inherit the attributes and relationships of a vehicle supertype.

By understanding the above concepts, we can create an ER diagram to represent the relationships between entities in a database.



### Notation for ER Diagram

An Entity-Relationship (ER) diagram is a graphical representation of entities and their relationships to each other. It is an essential tool for designing and modeling databases. The notation used in ER diagrams is standardized and helps to create a clear, concise, and consistent representation of the data model.

The following are the symbols used in ER diagrams:

- Entities: Entities are represented by rectangles. Each entity represents a table in the database. The name of the entity is written inside the rectangle.

- Attributes: Attributes are represented by ovals. Each attribute represents a column in the table. The name of the attribute is written inside the oval.

- Relationships: Relationships are represented by diamonds. They connect two or more entities and show how they are related. The name of the relationship is written inside the diamond.

- Cardinality: Cardinality is the number of instances of one entity that can be associated with another entity. It is represented by lines between the entities. The most common cardinality notations are:

  - One-to-One (1:1): One instance of an entity is associated with only one instance of another entity.
  - One-to-Many (1:N): One instance of an entity is associated with many instances of another entity.
  - Many-to-One (N:1): Many instances of an entity are associated with only one instance of another entity.
  - Many-to-Many (N:N): Many instances of an entity are associated with many instances of another entity.

- Primary Key: A primary key is a unique identifier for each record in a table. It is represented by an underline beneath the attribute.

- Foreign Key: A foreign key is a reference to a primary key in another table. It is represented by an arrow pointing towards the referenced entity.

- Optional/mandatory relationship: The optional/mandatory relationship is represented by a circle at the end of the line. A filled circle represents a mandatory relationship, while an empty circle represents an optional relationship.

Using these symbols and notations, an ER diagram can be created to represent the data model of a database. It provides a visual representation of the relationships between the entities and their attributes, making it easier to understand and design the database schema.



### Mapping Constraints

In a database management system, constraints are defined as rules that restrict the values of attributes in a relation. Mapping constraints are used to relate the constraints in the conceptual schema to the constraints in the internal schema. The following are some of the mapping constraints that are used in a database management system:

- **Entity Integrity Constraints:** These constraints ensure that the primary key of a relation is not null and that there are no duplicate values in the primary key. The mapping constraint used for entity integrity constraints is mapping the primary key of the conceptual schema to the primary key of the internal schema.

- **Referential Integrity Constraints:** These constraints ensure that the values in a foreign key match the values in the corresponding primary key. The mapping constraint used for referential integrity constraints is mapping the foreign key of the conceptual schema to the foreign key of the internal schema.

- **Domain Constraints:** These constraints ensure that the values of attributes in a relation belong to a specified domain. The mapping constraint used for domain constraints is mapping the domain of the conceptual schema to the domain of the internal schema.

- **Assertion Constraints:** These constraints ensure that certain conditions are satisfied in a relation. The mapping constraint used for assertion constraints is mapping the assertion of the conceptual schema to the assertion of the internal schema.

- **User-Defined Constraints:** These constraints are defined by the user and are used to enforce business rules. The mapping constraint used for user-defined constraints is mapping the user-defined constraint of the conceptual schema to the user-defined constraint of the internal schema.

In summary, mapping constraints are used to map the constraints in the conceptual schema to the constraints in the internal schema. This helps to ensure data integrity and consistency in a database management system.

### Reduction of an ER Diagrams to Tables

In database management system, an Entity-Relationship (ER) diagram is a graphical representation of entities and their relationships to each other. ER diagrams are used to design and model relational databases. However, ER diagrams alone cannot be used to create physical tables in a database. Therefore, reduction of ER diagrams to tables is necessary for creating a database.

Here are the steps for reducing an ER diagram to tables:

1. Identify entities: Identify all the entities in the ER diagram. Entities are objects, things, or concepts that are represented in the database. Each entity will be represented as a table in the database.

2. Identify attributes: Identify the attributes of each entity. Attributes are characteristics or properties of an entity. Each attribute will become a column in the table corresponding to the entity.

### Normal Forms for the Notes of Unit 3 - Database Design & Normalization

Database normalization is the process of organizing data in a database so that it is consistent, accurate, and easy to maintain. Normalization is achieved by applying a set of rules called normal forms. In this unit, we will learn about the different normal forms and how they are applied.

Here are the different normal forms:

#### First Normal Form (1NF)
- A relation is in first normal form if and only if all attributes contain atomic values (i.e., indivisible).
- Each column of a table should contain only one value, and each row should be unique.
- Example: A table with columns for "First Name" and "Last Name" would be in 1NF.

#### Second Normal Form (2NF)
- A relation is in second normal form if it is in 1NF and all non-key attributes are fully dependent on the primary key.
- Each non-key attribute should depend on the entire primary key, not just a part of it.
- Example: A table with columns for "Order ID", "Product ID", "Quantity", and "Price" would be in 2NF if "Quantity" and "Price" depend on both "Order ID" and "Product ID".

#### Third Normal Form (3NF)
- A relation is in third normal form if it is in 2NF and all non-key attributes are independent of each other.
- Each non-key attribute should depend only on the primary key, not on any other non-key attributes.
- Example: A table with columns for "Customer ID", "Product ID", "Product Name", and "Product Description" would not be in 3NF if "Product Description" depends on "Product Name".

#### Fourth Normal Form (4NF)
- A relation is in fourth normal form if it is in 3NF and has no multi-valued dependencies.
- Each attribute should depend on the primary key, not on any other attributes.
- Example: A table with columns for "Customer ID", "Order ID", "Product ID", and "Product Description" would not be in 4NF if there are multiple "Product Descriptions" for a single "Order ID".

#### Fifth Normal Form (5NF)
- A relation is in fifth normal form if it is in 4NF and has no join dependencies.
- Each attribute should be uniquely determined by the primary key, not by any other attributes.
- Example: A table with columns for "Customer ID", "Order ID", "Product ID", and "Product Description" would not be in 5NF if "Product Description" can be determined by both "Customer ID" and "Order ID".

In conclusion, normalization is an essential process in database design that ensures data consistency, accuracy, and maintainability. By applying the different normal forms, we can organize data in a way that is efficient and effective for data retrieval and manipulation.
