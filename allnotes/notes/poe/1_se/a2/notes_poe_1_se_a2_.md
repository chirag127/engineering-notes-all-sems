# Software Engineering

Software Engineering is the systematic approach to the development, operation, maintenance, and retirement of computer software. It involves analyzing user needs, designing the software, implementing the design, testing, and maintaining the finished product.

4. Testing: Rigorously testing the software to identify and fix any bugs or defects.
5. Deployment: Deploying the software for customer use.
6. Maintenance: Making changes to fix bugs or add new features as required.

### Software Crisis

The software crisis refers to the range of problems and difficulties associated with developing and maintaining complex software systems. Some of the major issues associated with the software crisis are:

1. Requirements: The requirements of software applications are often not well-defined, complete or consistent. This leads to software that does not satisfy the actual needs or that contains unnecessary features.
2. Complexity: Software systems have become increasingly complex with time. This makes software difficult and time-consuming to develop and test. It also makes software more prone to defects and harder to maintain.
3. Tight schedules: Software projects often have tight schedules and budgets leading to missed requirements, defects and rushed coding and testing. This decreases software quality.
4. Bugs: Software applications often end up containing numerous bugs or defects. This can make software unusable, unreliable or vulnerable to security risks. Debugging and fixing bugs is difficult, time-consuming and expensive.
5. Lack of documentation: Software system documentation is often poor or lacking. This makes it difficult for others to understand the system, modify or maintain it.
6. Upgrade issues: Evolving software and system requirements force software systems to be continually upgraded or replaced. This can be challenging, risky and resource-intensive. The latest upgrades may also introduce new bugs or incompatibilities.

Some solutions to the software crisis include:
- Improving requirements engineering to get complete, consistent and feasible requirements
- Adopting design and architectural styles that reduce complexity
- Providing more time and resources for software development and testing
- Using effective programming languages, tools, and testing techniques
- Applying documentation standards and creating good system documentation
- Planning upgrades carefully and testing upgrades thoroughly before deployment

### Similarity and Differences from Conventional Engineering Processes

Conventional engineering processes like waterfall model follow a sequential approach where each phase must be completed before moving on to the next one. Some key similarities and differences between conventional engineering processes and agile methodology are:

**Similarities:**
- Clearly defined requirements and goals. Agile also starts with a vision or roadmap of the final product.
- Team formation and project planning. As with conventional methods, agile also involves identification and assignment of team members and planning the schedule, budget, etc.

**Differences:**
- Static vs dynamic requirements. Conventional methods assume requirements are well-defined upfront whereas agile methods acknowledge that requirements evolve over time and embrace change.
- Sequential vs iterative approach. Conventional methods follow a sequential lifecycle (analyze, design, develop, test, deploy) while agile methods take an iterative approach, rapidly cycling through phases to adapt to changes.
- Heavy documentation vs working software. Conventional methods rely heavily on documentation while agile prioritizes delivering working software over comprehensive documentation. Documentation is produced as needed.

Some key advantages of the agile approach are faster delivery, higher quality, and increased customer satisfaction. However, it may not be suitable for smaller projects or those with strict constraints on budget, resources, or timelines. The choice between conventional and agile methods depends on various factors specific to a project and organization.

### Software Development Life Cycle (SDLC) Models

The Software Development Life Cycle (SDLC) is a process used by the software industry to design, develop and test high quality softwares. The SDLC aims to produce a high-quality software that meets or exceeds customer expectations, reaches completion within times and cost estimates.

There are several Software Development Life Cycle models:

1. Waterfall Model: The waterfall Model is a sequential design process, often used in software development projects. It consists of the following stages:

- Requirements Analysis: Identifying the requirements of the software to be developed.
- Design: Defining the architecture/design of the software.
- Implementation: Coding/Programming.
- Testing: Checking the software for defects/bugs.
- Deployment: Making the software available to the users.
- Maintenance: Updating/Fixing the software.

Advantage: Simple and easy to understand.
Disadvantage: Difficult to accommodate changes later in the process.

2. Agile Model: Agile methods break the product into small incremental builds. These builds are provided in iterations. Each iteration involves cross-functional teams working through the entire process. Some popular agile methods are:

- Scrum: Iterations are called sprints, typically 2 weeks long. Includes daily stand-up meetings.
- Extreme Programming (XP): Focuses on coding best practices, includes practices like test-driven development and pair programming.

Advantage: Accommodates changes easily.
Disadvantage: Can be less predictable due to adapting to changes.

### Water Fall Model in SDLC

The Waterfall model is a sequential design process, often used in software development processes, in which progress is seen as flowing steadily downwards (like a waterfall) through the phases of conception, initiation, analysis, design, construction, testing, production/implementation and maintenance.

The waterfall model:

-   Is a sequential model. Each phase must be completed before the next phase can begin.
-   Emphasizes that distinct stages occur in sequence and that outputs of one stage become inputs to the next stage.
-   Requirements are fully collected before design begins.
-   No iterations between development phases are expected.

Advantages:

-   Simple and easy to understand.
-   Stages and workflows are well defined and easy to manage due to rigidity.
-   Works well for smaller projects where requirements are very well understood.

Disadvantages:

-   Rigid model and difficult to accommodate changes later in the process.
-   In practice, requirements change and there can be a need for iteration. The waterfall model does not support iteration well.
-   Risks and uncertainties are not accounted for. Problems may emerge after a stage is completed.
-   Can lead to products/systems that do not meet customer requirements well.

Mnemonics:

-   Imagine a 'falling' waterfall to remember the sequential phases of the model - Conception, Initiation, Analysis, Design, Construction, Testing, Implementation, Maintenance.
-   'Can't Integrate? Try Again!' - to emphasize that each phase must be completed before the next phase. Iteration is difficult in this model.

Applications:

-   Projects where requirements are well understood and stable.
-   Projects following a structured approach with milestone stages.
-   Simple, small projects with fixed timelines and budgets.

Examples of use: Early software development processes, construction/engineering projects with well-defined requirements.

### Prototype Model in SDLC

The Prototype Model is a software development model in which a prototype (an early incomplete version of the software) is first built, then it is refined to get the final complete software.

The key steps in the Prototype Model are:

1. Requirements Analysis - Requirements of the software product are gathered from the customer.
2. Quick Design - A quick design of the prototype is made.
3. Building Prototype - The prototype is built quickly using some tools and techniques.
4. Customer Evaluation - The prototype is evaluated by the customer and user and their feedback is gathered.
5. Refining Prototype - The prototype is refined and enhanced based on the customer feedback. More prototype revisions may be developed.
6. Development of Complete Software - The complete software is developed based on the refined prototype.

Advantages:

- Customer involvement is high. The customer can see the prototype and provide feedback early in the process. This avoids misunderstandings and reduces risks.
- Problems can be detected earlier as the prototype provides an early vision of the software.
- Flexibility is high. Changes can be incorporated at the prototype stage, so less rework is required later.

Disadvantages:

- Extra time and cost may be required to build prototypes.
- The prototype and the final software may differ considerably, leading to extra work.
- The customer may expect the prototype to be the final software and may not be willing to accept a product that is different from the prototype.

Applications: When requirements are not clear, for new technology areas, for user interfaces, and for high risk projects.

Mnemonics:
Quick and dirty,
Evaluate and refine.

### Spiral Model in SDLC

The spiral model is a software development process combining elements of both design and prototyping-in-stages, in an effort to combine advantages of top-down and bottom-up concepts.

* Points:

1. The spiral model consists of four phases: Planning, Risk Analysis, Engineering and Evaluation.

2. Software is developed in a series of incremental releases. Each release is a spiral through the phases.

3. The spiral model is an iterative model. Each iteration involves an increment of product release.

4. Risk handling is one of the key points of this model. Risks are identified and resolved throughout each phase of each iteration.

5. The spiral model allows for incremental releases of the product, which can be very useful in getting customer feedback along the way.

* Mnemonics/Learning Tricks:

PLRE Model - Planning, Risk analysis, Engineering and Evaluation.
Taking risks inloops.
Releasing in chunks.

* Advantages:

- High amount of risk analysis hence, avoidance of risks.
- Software is released in increments so can get customer feedback.
- Good for large and expensive projects.
- Can accommodate changes to requirements.

* Disadvantages:

- Can be a costly model to follow.
- Needs very precise initial requirements.
- Needs high level of risk management.

1. Incremental Model: In this model, the software is developed in increments or parts. Each increment adds some functionality to the software. The key features are adapting to changes, early delivery, continuous testing and integration. The advantages are that it is flexible and delivers working software early. The disadvantages are that it could be difficult to estimate costs and timelines and it may not be suitable for large, mission-critical projects.
Mnemonic: Flexible, iterative approach delivering working software early through self-organizing teams.

### Iterative Enhancement Models in SDLC

Iterative enhancement models involve gradually building software prototypes and evolving them into the complete system. This process is repeated in a series of cycles where each cycle involves adding or modifying a set of functionality to each prototype. Some popular iterative models are:

- Rapid Application Development (RAD): Focuses on building prototypes and then incrementally enhancing them. The entire process is people-centric and emphasizes user involvement. Usually consists of 4 stages: Business modeling, Data modeling, Process modeling, and Construction. Advantages include fast development and user satisfaction. Disadvantages include lack of scalability and documentation.
- Incremental Model: Involves breaking down the entire software into increments or subsets. Each increment is thoroughly tested before the next increment is built. This model combines the elements of the waterfall model with the iterative philosophy of prototyping. It has advantages of early user feedback and risk mitigation but can be more time-consuming.
- Spiral Model: Combines the idea of iterative development with the systematic, controlled aspects of the waterfall model. It comprises of 4 quadrants: Planning, Risk Analysis, Engineering and Evaluation. Each quadrant feeds into the next, representing increasing levels of detail. This model is ideal for large, expensive, and complicated projects. However, it can be a costly model to implement.

Some mnemonics or learning tricks for these models could be:

- RAD: Rapidly build prototypes, users involved
- Incremental: Break into increments, test then build
- Spiral: Plan -> Risk analyze -> Engineer -> Evaluate in cycles

### Requirement Engineering Process in SRS

The requirement engineering process for Software Requirements Specification (SRS) involves the following steps:

1.  **Elicitation**: This is the first step where requirements are gathered from the client, users, stakeholders, etc. Techniques used are interviews, questionnaires, observation, etc. **Mnemonic:** ELIcit REquirements.
2.  **Analysis**: The elicited requirements are then analysed for consistency, completeness, unambiguousness, verifiability, modifiability, etc. Ambiguities and conflicts are resolved.
3.  **Specification**: The analysed requirements are then specified in a standard format with necessary details which can be used by designers and developers. **Mnemonic:** AnaLYSE then SPECIFY.
4.  **Validation**: The specified SRS is validated by checking if it meets the user needs and expectations. Techniques used are prototypes, reviews, etc.
5.  **Management**: The requirements are then managed by tracing and tracking them and controlling changes.

**Advantages:** Provides a structured approach, increases understanding, decreases ambiguity, forms the base for testing, etc.
**Disadvantages:** Time-consuming, expensive, complex process, people-dependent, etc.
**Applications:** Requirements engineering is done in all software/system development life cycle stages.

### Elicitation in Requirement Engineering Process in SRS

The elicitation process in Requirement Engineering extracts requirements from stakeholders. Some key points about elicitation in RE process for SRS are:

1. Identify stakeholders - First step is to identify all stakeholders like users, customers, developers, testers, etc. who can provide requirements.
2. Conduct interviews - Interview stakeholders individually or in groups to understand their needs and gather requirements. Prepare interview questions in advance. Note down requirements.
3. Host brainstorming sessions - Bring stakeholders together for brainstorming sessions to generate new ideas and elicit requirements. Reduce inhibitions and encourage participation.
4. Use questionnaires - Prepare questionnaires or surveys for stakeholders to fill out requirements. Provides anonymity and collects standard data but may miss follow up questions.
5. Refer to similar systems - Analyze existing similar systems to identify their functional and non-functional requirements and get inspiration for the new system. But do not copy requirements blindly.
6. Observe users - Directly observe users in their environment and note down points where they face problems or requirements for a new system. But may miss non-observable requirements.

- `CATWOE` - Customers, Actors, Transformation process, Weltanschauung, Owner, Environmental constraints

**Advantages:** Captures hidden/implicit requirements, Considers users' perspectives, Generates new ideas
**Disadvantages:** Time consuming, Requires skilled facilitators, May be inconsistent/incomplete

### Review and Management of User Needs in Requirement Engineering Process in SRS

- User needs are the core aspects of software requirement specification (SRS) document. Hence, it is important to review and manage user needs effectively in the requirement engineering process.

- Some key steps to review and manage user needs are:

## Unit 3 - Software Design

- Software design refers to the process of planning a software solution to a problem. It includes low-level component and algorithm implementation issues as well as high-level architectural issues.

### Architectural Design in Software Design

Architectural design is the process of defining a collection of hardware and software components and their interfaces to establish the framework for the development of a computer system. The key steps in architectural design are:

1. Identify major system components - This involves identifying major system modules needed to satisfy the functional requirements. E.g. For an e-commerce application, the major components could be: product catalog, shopping cart, order management, inventory management, etc.

- Modularity - The system is divided into modules with well-defined interfaces. This enhances understandability, maintainability and reusability.
- Loose coupling - Components interact through well-defined interfaces and have minimal dependencies on the internal details of other components. This increases flexibility and robustness to changes.
- Separation of concerns - The system is separated into distinct features or responsibilities. This makes the system easier to understand and manage.
- Scalability - The architecture allows for growth in scope and size. It should be possible to add new features and extra load capacity with minimal impact on existing system structure.

#### Coupling in Software Design

Coupling refers to the degree of dependence between software modules. Lower coupling is desirable as it implies lesser dependency between modules and makes the system more maintainable and extensible. Following are the types of coupling:

- **Content Coupling:** Modules are coupled by sharing data. Changes in one module may affect the other. Example: Global variables.
- **Common Coupling:** Modules are coupled by using the same global data or resources. Example: Accessing same global variables.
- **External Coupling:** Modules are coupled by depending on some external interface, device, etc. Example: Reading input from keyboard.
- **Control Coupling:** The control flow of one module depends on another. Changes in one module affect the sequence of execution of the other. Example: Using goto statements to transfer control.
- **Data Coupling:** Modules are coupled by passing data to each other. Lesser dependency as the structure of data is well-defined and changes in one module won't affect the other if data structure is unchanged. Example: Passing parameters to functions.

- Increased reusability
- Reduced ripple effects of changes
- Flexibility to introduce changes

**Disadvantages of Tight Coupling:**
- Lesser cohesion
- Reduced maintainability due to ripple effects of changes

#### Cohesion Measures in Software Design

Cohesion refers to the degree to which the elements inside a module are functionally related. High cohesion is desirable as it leads to several benefits such as increased reusability, reduced module complexity, enhanced maintainability, and increased reliability. The following are some popular cohesion measures:

- **Functional Cohesion**: This is the strongest form of cohesion where all elements of a module work together to achieve a single well-defined task. For example, a module to calculate the square root of a number exhibits functional cohesion.
- **Sequential Cohesion**: The elements of a module are cohesive if they are executed in a sequential order. For example, a module that opens a file, reads some data, processes the data, and then closes the file exhibits sequential cohesion.
- **Communication Cohesion**: The elements of a module exhibit communication cohesion if they operate on the same data. For example, a module that receives a message and then notifies multiple recipients exhibits communication cohesion.
- **Temporal Cohesion**: The elements of a module are cohesive if they are related based on time. For example, a module that backs up files at the end of every day exhibits temporal cohesion.

Some mnemonics to remember the cohesion measures:

- **F**unctional cohesion is the **F**irst and strongest type
- **S**equential and **C**ommunication come in **S**econd
- **T**emporal cohesion is the **T**hird type

The advantages of high cohesion are:

- Increased reusability: Highly cohesive modules have a single well-defined purpose which makes them more reusable.
- Reduced module complexity: As modules are focused on a single task, they are less complex and easier to understand.
- Enhanced maintainability: It is easier to identify the modules to change on introduction of new requirements as they are highly focused.
- Increased reliability: As modules are self-contained and focused, faults are more easily detected and corrected leading to increased reliability.

#### Top-Down and Bottom-Up Design in Software Design

Top-Down Design:
- The system is viewed as a whole and it is divided into successive decomposition until the primitive components are reached.
- The design starts with the highest level of abstraction and moves downwards towards more detailed components.
- The main advantage is that it provides an overview of the system and its components right from the beginning.
- However, the higher-level modules may be difficult to design without details of lower-level modules.

Bottom-Up Design:
- The design starts with the smallest components and these components are integrated to form higher-level structures.
- The main advantage is that lower-level components can be designed in detail as the designer has a clear understanding of the lower levels.
- However, this approach may lead to over-designing the lower-level components and it is difficult to identify the interfaces between components.

*Mnemonics*:
- "Waterfall down" - Top-down, like a waterfall flowing down
- "Built from ground up" - Bottom-up, built from the ground up

*When to use?*:
- Use Top-Down design for complex systems to have an overview and divide into modules.
- Use Bottom-Up design for components/modules where lower-levels are clear to design in detail.
- Often a combination of both is used: Top-Down to define the overall structure and Bottom-Up to define lower-level components.

*Advantages and Disadvantages*:
Top-Down:
Advantage: Overview of system and division into modules
Disadvantage: Lower-levels unclear, difficult to design higher-levels without lower-level details

Bottom-Up:
Advantage: Lower-levels designed in detail
Disadvantage: May lead to over-designing lower-levels, difficult to identify interfaces between components

*Examples and Applications*:
- Software architectures and frameworks use Top-Down design
- Device drivers and protocol stacks use Bottom-Up design
- Operating systems use a combination of both

##### Halestead’s Software Science in software design

- Halstead's software science is a quantitative method for measuring software complexity. It was proposed by Maurice Halstead in the 1970s.
- It uses two measures - vocabulary (n) and length (N) to calculate software complexity.

Vocabulary (n) - Number of distinct operators and operands in a program.
Length (N) - Total number of operators and operands in a program.

Based on these two measures, the following software metrics can be calculated:

- Program volume (V) = N log2 n
- Difficulty (D) = n (log2 n)/2
- Effort (E) = D × V
- Time required to program (T) = E/18

Advantages:
- Provides quantitative measures for software complexity.
- Gives an estimate of effort and time required to develop software.

Disadvantages:
- Does not consider structured programming concepts like modules, information hiding, etc.
- The empirical constants used in the formulae were determined based on a small sample and may not be accurate.
- The measures are language dependent and hard to calculate for larger programs.

In summary, Halstead's software science provides some basic quantitative measures of software complexity. However, due to the disadvantages mentioned above, it should not be used alone to predict effort and time required for software development. It can be used along with other qualitative techniques to get a better estimate.

##### Cyclomatic Complexity Measures in software design

Cyclomatic complexity is a software metric (measurement) used to indicate the complexity of a program. It measures the number of independent paths through a program's source code.

- It was developed by Thomas J. McCabe, Sr. in 1976.
- It is calculated as: V(G) = E - N + 2 where E is the number of edges of the graph and N is the number of nodes.
- A lower Cyclomatic Complexity indicates less complex and easier to understand and test code. A higher value indicates more complex code that is harder to understand, test and maintain.
- V(G) value of 10 or less is desired as it indicates the code is not very complex.

**Mnemonics to remember:**

- "Edges - Nodes + 2"
- "Voluminous (V) code is Complex (high Cyclomatic Complexity)"

**Advantages:**

- Gives a quantitative measure of code complexity.
- Helps identify code segments that need simplification.
- Guides testing efforts - higher complexity needs more testing.

**Disadvantages:**

- Does not consider data flow complexity or other types of complexity.
- Does not indicate what makes the code complex. Only gives a measure of complexity.

**Examples:**

- A single sequence of statements has a complexity of 1.
- An 'if' statement leads to 2 possible paths so increases complexity by 1.
- A 'switch' statement can lead to many paths and increases complexity significantly.
- 'for' or 'while' loops also add to complexity depending on the complexity within the loop.

**Applications:**

- Estimating testing efforts.
- Identifying code segments to simplify to reduce defects.
- Estimating costs of maintenance and onboarding new team members.
- Tracking complexity trends in code to take suitable actions.

###### Control Flow Graphs in software design

Control flow graphs (CFGs) are a representation of all paths that might be traversed through a program during its execution. They are a formalism for describing and analyzing control flow in programs.

** Nodes represent basic blocks of code (straight-line code segments with only one entry and exit point)
** Edges represent control flow between basic blocks (the flow of control from one block to another)
* The start node has no incoming edges and the end node has no outgoing edges
* Useful for:
** Visualizing control flow
** Analyzing control flow (detecting loops, finding all possible execution paths, etc.)
** Optimizing code (reducing branches, common subexpression elimination, etc.)

Mnemonics for remembering parts of a CFG:
* Nodes are blocks - basic blocks of code
* Edges are control flow - flow of control between blocks
* Start is where we begin - no incoming edges
* End is where we're done - no outgoing edges

Advantages:
* Provides a clear, visual representation of control flow
* Enables formal analysis of control flow
* Useful intermediate representation for optimization

Disadvantages:
* May be more complex than source code for humans to understand
* Constructing CFGs can be challenging for complex control flow

### Top-Down and Bottom-Up Testing Strategies in Software Testing

Top-down testing strategy:
- In top-down strategy, testing starts from the high-level modules and moves downwards to the low-level modules.
- The main advantage is that it begins with the verification of the most crucial functionality of the system.
- If a fault is detected in a high-level module, the lower-level modules are not tested, thus saving time.
- However, a major disadvantage is that low-level modules are not tested thoroughly.

Bottom-up testing strategy:
- In bottom-up strategy, testing starts with the low-level modules and moves upwards to the high-level modules.
- The main advantage is that the low-level modules are tested thoroughly.
- However, a major disadvantage is that the faults in low-level modules are detected late leading to wastage of time in testing the higher-level modules.

When to use which strategy:
- Top-down strategy should be used when:
-- Requirements are well understood
-- Low-level modules are not ready and high-level modules can be tested
-- Testing critical functionality is important
- Bottom-up strategy should be used when:
-- Low-level modules are ready but high-level modules are not ready
-- Thorough testing of components is required
-- Design is complex with many low-level modules

A combination of both top-down and bottom-up strategies can also be used based on the situations. The strategy to be used depends on multiple factors like requirements, schedule, availability of modules, etc.

Mnemonics:
- For top-down: Think high-level first
- For bottom-up: Think low-level building blocks first

Learning tricks:
- Visualize a tall building for top-down: Start from top floor and go downwards
- Visualize a foundation for bottom-up: Start from foundation and go upwards

- "Relative fitness" depends on context
- "Communities enable evolution" through feedback
- "Design guides" evolution toward better architectures

The evolutionary perspective highlights the fact that software is always evolving and provides a useful lens for understanding how and why software changes over its lifetime. By steering evolutionary forces, we can cultivate software that is more adaptable and resilient to requirements changes.

The following are the major categories of software maintenance:

### Estimation of Various Parameters such as Cost and Time in software project management

-   **Estimation techniques:** There are various estimation techniques used to estimate cost and time parameters for software projects such as:
    -   **Expert judgment:** Experts estimate the parameters based on their experience. Useful for small projects but prone to bias.
    -   **Analogous estimation:** Estimates are based on historical data from similar past projects. Adjustments are made for differences in scale or complexity. Prone to errors if projects are not truly similar.
    -   **Parametric estimation:** Estimates are calculated using statistical techniques and project metrics like lines of code. Requires historical data and is more quantitative but can be inaccurate if metrics are miscalculated.
-   **Three-point estimation:** A weighted average of three estimates is calculated:
    -   **Optimistic (o):** Best case scenario.
    -   **Most likely (m):** Realistic scenario.
    -   **Pessimistic (p):** Worst case scenario.
    -   Estimates are calculated as (o + 4m + p) / 6. Useful as it considers variability and risk but still depends on the accuracy of individual estimates.
-   **Estimation checklists:** Lists of standard tasks and estimates of time/cost required for each. Useful as a starting point but individual project details must be considered for accurate estimates.
-   **Learning curve considerations:** As team gains experience, estimates may decrease. The law of diminishing returns applies - efficiency gains decrease over time. Historical data must account for learning curves to produce accurate estimates for new projects.
-   **Risks and uncertainty:** Software project estimates are uncertain and prone to risks/unknowns. Sensitivity analysis determines impact of variables on estimates. Risk management techniques like risk mitigation and contingency allowance can handle uncertainty. Buffer/contingency time/cost is added to estimates to account for risks.

**Mnemonics:**

-   **PERT:** Program Evaluation and Review Technique. Uses three-point estimation.
-   **COCOMO:** Constructive Cost Model. Uses parametric estimation based on lines of code.

**Advantages:** Quantitative, considers risks, uses expert knowledge.
**Disadvantages:** Prone to bias/inaccuracy, requires historical data which may not exist for new types of projects.
**Applications:** Producing project schedules/budgets, resource allocation, monitoring/control.
