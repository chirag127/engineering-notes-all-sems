### Transactions with replicated data for the notes of the Unit 10 - Replication in the subject of DISTRIBUTED SYSTEM

- Transactions are a sequence of operations that are executed atomically, consistently, isolatedly, and durably (ACID properties) on a database system.
- Replication is the process of creating and maintaining multiple copies of data on different servers in a distributed system, to enhance availability, reliability, and performance.
- Transactions with replicated data are transactions that involve accessing or updating data that is replicated on multiple servers in a distributed system.
- Transactions with replicated data pose some challenges and trade-offs, such as:
  - How to ensure that the replicated data is consistent across all servers, i.e., that all copies of the same data item have the same value at any given time.
  - How to handle concurrent transactions that may access or update the same data item on different servers, i.e., how to ensure serializability and isolation of transactions.
  - How to handle failures or network partitions that may affect the availability or communication of some servers, i.e., how to ensure atomicity and durability of transactions.
  - How to balance the performance and scalability benefits of replication with the overhead and complexity of maintaining consistency and coordination among servers, i.e., how to achieve a desirable trade-off between consistency and availability (CAP theorem).

- There are different models, methods, and protocols for implementing transactions with replicated data, such as:
  - Primary-backup model: In this model, one server is designated as the primary server for each data item, and the other servers are backups. The primary server is responsible for processing all transactions that access or update the data item, and propagating the updates to the backups. The backups can serve read-only transactions or queries. This model ensures strong consistency, but has a single point of failure and a bottleneck for writes.
  - Quorum-based model: In this model, each server has a vote for each data item, and a transaction needs to obtain a quorum (a majority or a threshold) of votes from the servers to access or update the data item. The quorum size and composition can vary depending on the type of operation (read or write) and the desired level of consistency and availability. This model allows for more flexibility and fault-tolerance, but has a higher communication and coordination cost.
  - Two-phase commit protocol: In this protocol, a transaction coordinator is responsible for initiating and committing transactions that span multiple servers. The protocol consists of two phases: a prepare phase, where the coordinator asks each server to vote on whether it is ready to commit the transaction, and a commit phase, where the coordinator decides whether to commit or abort the transaction based on the votes, and informs each server of the decision. This protocol ensures atomicity and consistency, but has a high latency and a blocking behavior in case of failures or network partitions.
  - Paxos protocol: In this protocol, a set of servers use a consensus algorithm to agree on a single value for each data item, and execute transactions that access or update the data item accordingly. The protocol consists of multiple rounds of messages, where each server proposes a value and accepts or rejects the values proposed by others, until a majority of servers agree on the same value. This protocol ensures consistency and availability, but has a high message complexity and a low throughput.
