#### Zookeeper concepts

- Zookeeper is a distributed coordination service that provides a consistent, reliable and scalable way of managing configuration information, naming, synchronization, group membership and leader election among distributed systems.
- Zookeeper consists of a set of servers, called **ZooKeeper servers**, and a set of clients, called **ZooKeeper clients**, that communicate with each other using a TCP-based protocol.
- Zookeeper maintains a hierarchical namespace of **znodes**, which are data nodes that store configuration data or other metadata. Each znode has a path, such as `/app/config`, that uniquely identifies it in the namespace. Znodes can also have children znodes, forming a tree structure.
- Zookeeper provides four types of znodes: **persistent**, **ephemeral**, **sequential** and **container**. Persistent znodes are permanent and remain in the namespace until explicitly deleted. Ephemeral znodes are temporary and are automatically deleted when the client that created them disconnects. Sequential znodes are persistent znodes that have a unique sequence number appended to their names. Container znodes are persistent znodes that are automatically deleted when they have no children.
- Zookeeper allows clients to perform various operations on znodes, such as **create**, **delete**, **read**, **write**, **setACL**, **getACL**, **getChildren**, **exists** and **sync**. These operations are atomic and linearizable, meaning that they are executed as a single unit and in the same order on all servers.
- Zookeeper also allows clients to set **watches** on znodes, which are callbacks that are triggered when a znode changes. Watches can be set for data changes, children changes or existence changes. Watches are one-time triggers and need to be re-registered after each notification.
- Zookeeper guarantees three consistency properties: **sequential consistency**, **atomicity** and **single system image**. Sequential consistency means that updates from a client will be applied in the order that they were sent. Atomicity means that updates either succeed or fail, and no partial results are visible. Single system image means that clients will see the same view of the system regardless of the server they connect to.
- Zookeeper uses a consensus protocol called **Zab** (ZooKeeper Atomic Broadcast) to ensure that all servers have the same state of the namespace. Zab works by electing a leader server that proposes updates to the namespace and broadcasts them to the follower servers. The followers acknowledge the updates and apply them to their local copies. The leader commits the updates once a majority of followers have acknowledged them.
- Zookeeper can tolerate failures of some servers as long as a majority of servers are available. This is called a **quorum**. For example, if there are five servers, then at least three servers need to be up for Zookeeper to function. If the leader server fails, then a new leader is elected from the remaining servers using a protocol called **Fast Leader Election**.
- Zookeeper can be used for various distributed system scenarios, such as **configuration management**, **service discovery**, **distributed locking**, **barrier synchronization**, **leader election** and **queue management**. For example, Zookeeper can store the configuration data of an application in a znode and notify the clients of any changes using watches. Zookeeper can also register the available services in ephemeral znodes and allow the clients to discover them using getChildren. Zookeeper can also implement a distributed lock by creating an ephemeral sequential znode and checking if it is the lowest in the order.
