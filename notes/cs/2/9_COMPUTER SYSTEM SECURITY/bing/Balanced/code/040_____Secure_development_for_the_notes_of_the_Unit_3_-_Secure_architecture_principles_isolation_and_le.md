### Secure development for the notes of the Unit 3 - Secure architecture principles isolation and least privilege in the subject of COMPUTER SYSTEM SECURITY

Secure development refers to the set of tools, practices, and approaches that the SEI has created to identify and prevent security flaws during early development of software systems, when it is most cost effective to do so. Some of the secure development principles are:

- **Minimize attack surface area**: Every time a programmer adds a feature to their application, they are increasing the risk of a security vulnerability. Therefore, it is important to keep the application as simple and modular as possible, and to limit the exposure of sensitive data and functionality to the minimum necessary.
- **Establish secure defaults**: The default configuration of the application should be secure by default, meaning that it should not allow any unauthorized access or actions unless explicitly granted by the user or administrator. For example, the default settings of the application should require strong passwords, encryption, and logging.
- **The principle of least privilege**: The principle of least privilege means that you ensure people only have enough access that they need to do their job. For instance: if you design a system which holds sensitive customer financial information, it’s good practice to limit who can access that information. This principle applies to both users and processes, and it can help reduce the impact of a security breach or a malicious insider.
- **The principle of defense in depth**: The principle of defense in depth means that you apply multiple layers of security controls to protect the application from different types of threats. For example, you can use firewalls, encryption, authentication, authorization, auditing, and monitoring to create a comprehensive security strategy. This way, even if one layer is compromised, the other layers can still provide some protection.
- **Fail securely**: The application should handle errors and exceptions in a secure manner, meaning that it should not leak any sensitive information or allow any unauthorized actions in case of a failure. For example, the application should not display detailed error messages to the user, but rather log them internally and show a generic message. The application should also revert to a secure state after a failure, and not leave any temporary files or data behind.
- **Don’t trust services**: The application should not blindly trust any external services or components that it interacts with, such as third-party libraries, APIs, or cloud providers. The application should validate the input and output of these services, and use secure protocols and encryption to communicate with them. The application should also monitor the performance and behavior of these services, and have a contingency plan in case they fail or are compromised.
- **Separation of duties**: The application should enforce the separation of duties among different roles and responsibilities, such as developers, testers, administrators, and users. This can help prevent conflicts of interest, collusion, and fraud. For example, the application should not allow the same person to create, approve, and execute a transaction, or to access both production and test environments.
- **Avoid security by obscurity**: The application should not rely on hiding or obscuring the details of its design, implementation, or configuration as a security measure. Instead, the application should follow the principle of open design, meaning that it should be secure even if the attacker knows everything about it. The application should also follow the principle of least astonishment, meaning that it should behave in a predictable and consistent way, and not surprise the user or the developer with unexpected behavior.
