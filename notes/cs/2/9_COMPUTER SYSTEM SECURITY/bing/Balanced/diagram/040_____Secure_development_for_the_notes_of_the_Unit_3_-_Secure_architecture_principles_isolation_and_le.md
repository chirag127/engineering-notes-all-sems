### Secure development for the notes of the Unit 3 - Secure architecture principles isolation and least privilege

Secure development is the process of creating software systems that are resilient to security threats and vulnerabilities. Secure development requires following a set of principles, practices, and tools that help identify and prevent security flaws during early stages of software development, when it is most cost effective to do so.

Some of the secure development principles are:

- **Minimize attack surface area**: This principle states that every feature or functionality added to a software system increases the risk of a security vulnerability. Therefore, developers should only implement the essential features and functionalities that are required by the system, and avoid unnecessary or unused code that could expose the system to attacks.
- **Establish secure defaults**: This principle states that the default configuration and settings of a software system should be secure and not expose the system to unnecessary risks. For example, the default permissions for files and directories should be restrictive, the default passwords should be strong and unique, and the default network ports should be closed or filtered.
- **The principle of least privilege**: This principle states that every user, process, or component of a software system should only have the minimum level of access or privilege that is necessary to perform its function. This principle reduces the impact of a security breach, as an attacker would have limited access to the system resources and data .
- **The principle of defense in depth**: This principle states that a software system should have multiple layers of security controls and mechanisms that protect it from different types of attacks. For example, a web application should have security measures at the network, application, and data layers, such as firewalls, encryption, authentication, and authorization.
- **Fail securely**: This principle states that a software system should handle errors and exceptions in a secure manner, and not reveal sensitive information or compromise the system security. For example, a software system should not display detailed error messages that could help an attacker exploit the system, but rather log the errors and display generic messages to the user.
- **Don't trust services**: This principle states that a software system should not blindly trust the inputs, outputs, or communications from other services or components, as they could be malicious or compromised. For example, a software system should validate and sanitize the inputs from the user or other sources, and encrypt and authenticate the communications with other services or components.
- **Separation of duties**: This principle states that a software system should have different roles and responsibilities for different users, processes, or components, and enforce the separation of those roles and responsibilities. For example, a software system should have separate roles for developers, testers, and administrators, and restrict the access and actions of each role.
- **Avoid security by obscurity**: This principle states that a software system should not rely on hiding or obscuring its security mechanisms or vulnerabilities, as they could be discovered or exposed by an attacker. For example, a software system should not use weak or hard-coded encryption keys, or hide sensitive information in comments or hidden files.

These are some of the secure development principles that can help create software systems that are more secure and robust. However, these principles are not exhaustive or definitive, and they should be applied with care and context. Developers should also use secure development tools and practices, such as security testing, code reviews, threat modeling, and security training, to enhance the security of their software systems   .
