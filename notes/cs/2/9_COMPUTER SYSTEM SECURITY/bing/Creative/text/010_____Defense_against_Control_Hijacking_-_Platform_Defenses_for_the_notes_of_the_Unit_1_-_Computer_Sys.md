### Defense against Control Hijacking - Platform Defenses

Control hijacking is a type of attack that exploits a vulnerability in a program to alter its execution flow and execute malicious code. Control hijacking can be performed by overwriting code pointers, such as return addresses, function pointers, or exception handlers, with the address of the attacker's payload. To defend against control hijacking, various platform defenses have been proposed, such as:

- **Stack canaries**: A stack canary is a random value that is placed on the stack before the return address. The canary is checked before returning from a function, and if it is corrupted, the program aborts. Stack canaries can prevent overwriting the return address, but they can be bypassed by brute force, information leakage, or indirect overwrites.
- **Non-executable memory**: Non-executable memory is a feature that marks certain memory regions as non-executable, meaning that the processor will not execute any code stored in those regions. This can prevent the execution of injected code or data, but it does not prevent overwriting existing code or code pointers.
- **Address space layout randomization (ASLR)**: ASLR is a technique that randomizes the base addresses of the code, data, stack, and heap segments of a program. This makes it harder for the attacker to guess the location of the payload or the code pointers, but it can be defeated by information leakage, brute force, or return-oriented programming (ROP).
- **Control flow integrity (CFI)**: CFI is a technique that enforces that the control flow of a program follows a predefined control flow graph (CFG), which is derived from the program's source code or binary. CFI can prevent arbitrary jumps or calls to unintended locations, but it requires a precise and sound CFG, which is hard to obtain in practice. Moreover, CFI can be circumvented by exploiting existing code gadgets or indirect branches.
- **Code pointer integrity (CPI)**: CPI is a technique that protects all code pointers from being overwritten by separating them into a safe memory region that is inaccessible to the attacker. CPI can prevent any control hijacking attack that relies on corrupting code pointers, but it requires a precise and sound analysis of the code pointers, which is also hard to obtain in practice. Furthermore, CPI can incur a significant performance overhead due to the frequent memory accesses to the safe region.
- **Complete memory safety**: Complete memory safety is a property that guarantees that a program does not perform any illegal memory accesses, such as buffer overflows, use-after-free, or dangling pointers. Complete memory safety can prevent any control hijacking attack that relies on exploiting a memory error, but it is very difficult to achieve in practice, especially for low-level languages like C or C++. Some techniques that aim to provide complete memory safety are static analysis, dynamic analysis, memory-safe languages, or hardware support.
