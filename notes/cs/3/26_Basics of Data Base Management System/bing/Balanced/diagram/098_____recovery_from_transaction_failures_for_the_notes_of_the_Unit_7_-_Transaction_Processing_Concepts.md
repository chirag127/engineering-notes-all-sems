### Recovery from transaction failures

- Transaction failures are situations where a transaction cannot complete its execution due to various reasons, such as network failures, deadlock, or errors in application logic.
- Transaction failures can compromise the consistency and integrity of the database, as they may leave the database in an intermediate or inconsistent state.
- Recovery mechanisms are techniques that can help restore the database to a consistent state after transaction failures, by undoing or redoing the effects of the failed transactions .
- There are two major techniques for recovery from non-catastrophic transaction failures: deferred updates and immediate updates.
  - Deferred update: This technique does not physically update the database on disk until a transaction has reached its commit point. It maintains a log of all the operations performed by the transaction in the main memory. If a transaction fails before reaching its commit point, no recovery action is needed, as the database on disk is not affected. If a transaction reaches its commit point, the log is written to disk and the database is updated accordingly.
  - Immediate update: This technique allows the database to be updated on disk before a transaction reaches its commit point. It also maintains a log of all the operations performed by the transaction in the main memory. If a transaction fails before reaching its commit point, the recovery manager may undo the transactions, i.e., reverse the operations of the failed transaction using the log. If a transaction reaches its commit point, the recovery manager may redo the transactions, i.e., reapply the operations of the committed transaction using the log, in case of a system crash or power failure.
- There are also techniques for recovery from catastrophic transaction failures, which are caused by events that damage the database on disk, such as fire, flood, or disk failure. These techniques involve restoring a previous copy of the database from archival backup, and applying the transaction log to the copy to reconstruct a more current state by redoing the committed transaction operations up to the failure point .
- In a partitioned database environment, where the database is distributed across multiple servers, transaction failures may require database recovery on both the failed server and any other server that was participating in the transaction. This can be achieved by using a distributed commit protocol, such as the two-phase commit protocol, which ensures that either all the servers commit the transaction or none of them do.
