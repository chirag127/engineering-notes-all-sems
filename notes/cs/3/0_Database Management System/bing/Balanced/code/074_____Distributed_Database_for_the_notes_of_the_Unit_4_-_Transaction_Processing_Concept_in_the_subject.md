### Distributed Database for the notes of the Unit 4 - Transaction Processing Concept in the subject of Database Management System

- A distributed database is a collection of databases that are physically stored on different network hosts and logically appear as a single database to the users.
- A distributed transaction is a database transaction that involves two or more network hosts . A transaction is a logical unit of work that consists of one or more SQL statements executed by a single user.
- A distributed transaction must satisfy the ACID properties: atomicity, consistency, isolation, and durability . Atomicity means that either all or none of the changes made by a transaction are reflected in the database. Consistency means that the database remains in a valid state after a transaction. Isolation means that the concurrent transactions do not interfere with each other. Durability means that the committed changes are permanent and survive failures.
- A distributed transaction is managed by a transaction manager, which is responsible for creating and coordinating a global transaction that encompasses all the operations against the distributed resources . The transaction manager uses a two-phase commit protocol to ensure the atomicity and durability of the distributed transaction .
- The two-phase commit protocol consists of two phases: the prepare phase and the commit phase . In the prepare phase, the transaction manager asks each host involved in the transaction to vote on whether to commit or abort the transaction. In the commit phase, the transaction manager decides to commit or abort the transaction based on the votes and informs each host of the decision. If all hosts vote to commit, the transaction manager commits the transaction. If any host votes to abort, the transaction manager aborts the transaction.
- A distributed transaction may become in-doubt if the two-phase commit protocol fails due to network or system failures . An in-doubt transaction is a transaction whose outcome is unknown or uncertain. The transaction manager must resolve the in-doubt transactions by either committing or aborting them, depending on the state of the hosts and the data involved .
