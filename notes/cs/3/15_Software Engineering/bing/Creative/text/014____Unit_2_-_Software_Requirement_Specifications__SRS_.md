## Unit 2 - Software Requirement Specifications (SRS)

- Software Requirement Specifications (SRS) is a document that describes the features, functions, and constraints of a software system.
- SRS is also known as Software Requirements Document (SRD), Software Requirements Specification (SRS), or Functional Specification (FS).
- SRS is a communication tool between the stakeholders and the developers of the software system.
- SRS helps to ensure that the software system meets the needs and expectations of the stakeholders and the users.
- SRS also serves as a basis for software design, testing, validation, verification, maintenance, and evolution.

### Objectives of SRS

- The main objectives of SRS are:

  - To define the scope and boundaries of the software system.
  - To establish a common understanding of the software system among the stakeholders and the developers.
  - To specify the functional and non-functional requirements of the software system.
  - To provide a reference for software design, testing, validation, verification, maintenance, and evolution.
  - To reduce the risk of software failure, rework, and cost overrun.

### Characteristics of SRS

- A good SRS should have the following characteristics:

  - Correct: The SRS should accurately reflect the needs and expectations of the stakeholders and the users.
  - Complete: The SRS should cover all the requirements of the software system, without any ambiguity, inconsistency, or omission.
  - Consistent: The SRS should not have any conflicting or contradictory requirements.
  - Clear: The SRS should be written in a clear, concise, and understandable language, using appropriate terminology, notation, and format.
  - Verifiable: The SRS should be testable, i.e., each requirement should have a criterion for verification and validation.
  - Modifiable: The SRS should be structured and organized in a way that allows easy identification, modification, and traceability of the requirements.
  - Traceable: The SRS should be able to trace the origin, rationale, and dependencies of each requirement, as well as the impact of any change in the requirements.
  - Feasible: The SRS should be realistic and achievable, considering the available resources, technology, and constraints.
  - Unambiguous: The SRS should have only one possible interpretation, and avoid any vagueness, confusion, or misunderstanding.
  - Validated: The SRS should be reviewed and approved by the stakeholders and the users, to ensure that it meets their needs and expectations.

### Contents of SRS

- The contents of SRS may vary depending on the type, size, and complexity of the software system, as well as the standards, methodologies, and tools used for software development.
- However, a typical SRS may include the following sections:

  - Introduction: This section provides an overview of the software system, its purpose, scope, objectives, assumptions, dependencies, and constraints. It also defines the intended audience, the structure, and the organization of the SRS document.
  - System Overview: This section provides a high-level description of the software system, its context, environment, interfaces, and interactions with other systems. It also identifies the stakeholders and the users of the software system, and their roles and responsibilities.
  - Functional Requirements: This section specifies the functions and features that the software system should provide, in terms of inputs, outputs, processes, and behaviors. It also defines the use cases, scenarios, and user stories that illustrate how the software system should be used by the users and the stakeholders.
  - Non-Functional Requirements: This section specifies the quality attributes and the performance criteria that the software system should satisfy, such as reliability, availability, security, usability, maintainability, scalability, portability, etc. It also defines the standards, regulations, and policies that the software system should comply with, such as legal, ethical, social, environmental, etc.
  - System Models: This section provides graphical and textual representations of the software system, such as data models, process models, state models, object models, etc. It also describes the architecture, design, and implementation of the software system, using appropriate diagrams, notations, and methodologies.
  - System Testing: This section describes the testing strategy, plan, and methods for verifying and validating the software system, such as unit testing, integration testing, system testing, acceptance testing, etc. It also defines the test cases, test data, test procedures, test results, and test reports for the software system.
  - System Maintenance: This section describes the maintenance strategy, plan, and methods for evolving and improving the software system, such as corrective maintenance, adaptive maintenance, perfective maintenance, preventive maintenance, etc. It also defines the change management, configuration management, and quality management processes for the software
