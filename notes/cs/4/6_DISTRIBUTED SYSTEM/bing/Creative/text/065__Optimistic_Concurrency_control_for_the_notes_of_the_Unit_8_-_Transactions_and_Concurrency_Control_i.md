### Optimistic Concurrency Control

- Optimistic concurrency control (OCC) is a method of managing concurrent access to shared data in a transactional system, such as a database or a software application. 
- OCC assumes that conflicts between concurrent transactions are rare, and therefore does not use locks to prevent them. Instead, OCC allows transactions to read and write data without acquiring locks, and checks for conflicts before committing. 
- If a conflict is detected, OCC typically aborts and restarts the transaction, although other resolution schemes are possible. OCC avoids the overhead of locking and the possibility of deadlocks, but may incur the cost of aborting and retrying transactions. 
- OCC is suitable for environments with low data contention, where conflicts are unlikely to occur frequently. In environments with high data contention, OCC may perform poorly due to frequent aborts and retries. 
- OCC transactions involve three phases: 
  - Begin: Record a timestamp or a version number marking the transaction's start time.
  - Modify: Read and write data without acquiring locks. Keep track of the data items read and written by the transaction.
  - Validate: Check whether any other transaction has modified the data items that this transaction has read or written since its start time. If there is no conflict, commit the transaction. If there is a conflict, abort and restart the transaction, or use another resolution scheme.
- OCC can be implemented in different ways, depending on how conflicts are detected and resolved. Some common techniques are: 
  - Timestamp ordering: Assign a timestamp to each transaction and each data item. A transaction can read or write a data item only if its timestamp is greater than the data item's timestamp. Otherwise, the transaction is aborted. This ensures that transactions are executed in a serializable order based on their timestamps.
  - Validation-based: Use a validation function to check whether a transaction's read set and write set overlap with any other transaction's write set that has committed since the transaction's start time. If there is an overlap, the transaction is aborted. Otherwise, the transaction is committed.
  - Multi-version: Maintain multiple versions of each data item, each with a timestamp or a version number. A transaction can read the latest version of a data item that is older than its start time, and can write a new version of a data item with its own timestamp. A transaction is aborted if it tries to write a data item that has a newer version than its start time. This allows read-only transactions to execute without validation or aborts.
- OCC can be used in various transactional systems, such as relational databases, NoSQL databases, and software transactional memory. Some examples of systems that support OCC are:   
  - Azure Cosmos DB: A NoSQL database that supports multi-item transactions with OCC using stored procedures, triggers, and merge procedures written in JavaScript. Azure Cosmos DB also provides an ETag mechanism for implementing OCC in web applications using HTTP requests.
  - SQL Server: A relational database that supports OCC using row versioning and snapshot isolation. SQL Server also provides an @@rowversion data type and a rowversion column property for implementing OCC in applications using timestamps.
  - Entity Framework: An object-relational mapping framework that supports OCC using concurrency tokens, such as timestamps or version numbers, that are stored as properties of entity classes. Entity Framework also provides an OptimisticConcurrencyException class for handling concurrency conflicts in applications.
