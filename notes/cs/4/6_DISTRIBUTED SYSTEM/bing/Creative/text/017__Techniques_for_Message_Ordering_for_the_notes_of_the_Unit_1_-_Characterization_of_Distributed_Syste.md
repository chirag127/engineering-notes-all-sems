### Techniques for Message Ordering

- Message ordering is the problem of ensuring that messages sent by different processes in a distributed system are received in a consistent and predictable order.
- Message ordering is important for achieving correctness, consistency, and coordination in distributed applications that rely on message-passing for communication.
- There are different types of message ordering guarantees that can be provided by a distributed system, depending on the application requirements and the system assumptions.
- Some of the common types of message ordering are:

  - **Non-FIFO ordering**: This is the weakest form of message ordering, where messages can be received in any order, regardless of their send order. This can happen due to network delays, message losses, or message retransmissions. Non-FIFO ordering does not provide any guarantee about the order of messages, and can lead to confusion and inconsistency in distributed applications.
  - **FIFO ordering**: This is the basic form of message ordering, where messages sent by the same process are received in the same order as they were sent. FIFO ordering ensures that messages from the same source are not reordered, but does not prevent messages from different sources from being interleaved. FIFO ordering can be achieved by attaching sequence numbers to messages, and buffering out-of-order messages at the receiver until the next expected message arrives.
  - **Causal ordering**: This is a stronger form of message ordering, where messages that are causally related are received in the same order as they were sent. Causal ordering captures the notion of potential causality, where a message m1 can potentially cause another message m2 if m1 is sent before m2, or if m1 is received by a process that sends m2, or if there is a chain of such messages between m1 and m2. Causal ordering ensures that messages that are causally dependent are not reordered, but does not prevent messages that are causally independent from being reordered. Causal ordering can be achieved by using vector clocks, which are arrays of logical clocks that track the causal history of each message.
  - **Total ordering**: This is the strongest form of message ordering, where all messages are received in the same order by all processes. Total ordering ensures that messages are globally ordered, and that there is no ambiguity or inconsistency in the order of messages. Total ordering can be achieved by using a consensus protocol, such as Paxos or Raft, which elects a leader process that assigns a global sequence number to each message, and broadcasts the messages in that order to all processes. Alternatively, total ordering can be achieved by using a multicast protocol, such as Totem or Spread, which uses a ring or a tree topology to deliver messages to all processes in the same order.

- Message ordering can be specified using different methods, such as:

  - **Forbidden predicates**: This is a method proposed by Kshemkalyani and Singhal, which uses logical expressions to specify the order of messages that are not allowed in a distributed system. For example, the forbidden predicate for FIFO ordering is (s(m1) < s(m2)) ∧ (r(m2) < r(m1)), which means that it is not allowed for a process to send message m1 before message m2, and receive message m2 before message m1. Forbidden predicates can be used to specify any type of message ordering, and can be checked by using a distributed algorithm that monitors the send and receive events of each message.
  - **Virtual synchrony**: This is a method proposed by Birman, which uses the concept of a view to specify the order of messages in a distributed system. A view is a set of processes that are currently connected and can communicate with each other. A view change occurs when a process joins or leaves the system, or when a network partition or a failure occurs. Virtual synchrony ensures that all processes in the same view observe the same events in the same order, and that all messages sent in a view are delivered before the view changes. Virtual synchrony can be implemented by using a group communication protocol, such as Isis or Horus, which maintains a consistent view of the system and delivers messages according to a predefined message ordering guarantee.
