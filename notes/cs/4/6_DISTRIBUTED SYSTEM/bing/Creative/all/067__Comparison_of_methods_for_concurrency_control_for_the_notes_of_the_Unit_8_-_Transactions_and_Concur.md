### Comparison of methods for concurrency control for the notes of the Unit 8 - Transactions and Concurrency Control in the subject of DISTRIBUTED SYSTEM

Concurrency control is the process of managing concurrent access to shared data in a distributed system. Concurrency control ensures that transactions are executed in a consistent and correct manner, and that the integrity of the data is maintained. There are various methods for concurrency control, each with its own advantages and disadvantages. Some of the common methods are:

- **Two-phase locking (2PL)**: This method uses locks to prevent conflicting operations on the same data item. A transaction must acquire a lock on a data item before reading or writing it, and release the lock after finishing the operation. There are two phases in this method: the growing phase, where a transaction can only acquire locks but not release any, and the shrinking phase, where a transaction can only release locks but not acquire any. 2PL ensures serializability, which means that the concurrent execution of transactions is equivalent to some serial execution of the same transactions. However, 2PL may cause deadlock, where two or more transactions are waiting for each other to release locks, and thus cannot proceed. 2PL also reduces concurrency, as transactions may have to wait for locks held by other transactions. 2PL can be implemented in a centralized or distributed manner, where a single or multiple lock managers are responsible for granting and releasing locks .

- **Timestamp ordering (TO)**: This method assigns a unique timestamp to each transaction, and uses the timestamps to order the execution of conflicting operations. A transaction can read or write a data item only if its timestamp is greater than the read-timestamp and write-timestamp of the data item, which record the latest time when the data item was read or written, respectively. If a transaction's timestamp is smaller than the read-timestamp or write-timestamp of the data item, the transaction is aborted and restarted with a new timestamp. TO ensures serializability, as the concurrent execution of transactions is equivalent to the execution of the transactions in the order of their timestamps. TO also avoids deadlock, as transactions do not wait for each other. However, TO may cause starvation, where a transaction is repeatedly aborted and restarted due to conflicts with other transactions. TO also requires synchronization of clocks or counters to generate timestamps. TO can be implemented in a centralized or distributed manner, where a single or multiple timestamp managers are responsible for assigning and comparing timestamps .

- **Multiversion concurrency control (MVCC)**: This method maintains multiple versions of each data item, and allows transactions to access different versions based on their timestamps. Each successful write operation creates a new version of the data item, and each version is labeled with the timestamp of the transaction that created it. When a transaction reads a data item, it selects the latest version that is not newer than its timestamp. When a transaction writes a data item, it creates a new version with its timestamp, and checks if there is any conflicting version that is newer than its timestamp. If there is, the transaction is aborted and restarted with a new timestamp. MVCC ensures serializability, as the concurrent execution of transactions is equivalent to the execution of the transactions in the order of their timestamps. MVCC also avoids deadlock and starvation, as transactions do not wait for each other or abort due to conflicts with older transactions. However, MVCC requires extra storage space and overhead to maintain and access multiple versions of data items. MVCC also requires synchronization of clocks or counters to generate timestamps. MVCC can be implemented in a centralized or distributed manner, where a single or multiple version managers are responsible for creating and selecting versions .

- **Validation (or optimistic) concurrency control (VCC)**: This method allows transactions to execute without any locking or timestamping, and validates their correctness at the end of their execution. A transaction is divided into three phases: the read phase, where the transaction reads data items from the database, the validation phase, where the transaction checks if its execution is serializable, and the write phase, where the transaction writes data items to the database. The validation phase uses a validation test to determine if the transaction conflicts with any other concurrent transaction. If the validation test fails, the transaction is aborted and restarted. Otherwise, the transaction commits and writes its updates to the database.
