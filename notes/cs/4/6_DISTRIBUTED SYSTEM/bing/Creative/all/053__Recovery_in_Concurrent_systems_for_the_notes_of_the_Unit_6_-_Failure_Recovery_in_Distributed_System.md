### Recovery in Concurrent systems for the notes of the Unit 6 - Failure Recovery in Distributed Systems in the subject of DISTRIBUTED SYSTEM

- Recovery in concurrent systems is the process of restoring the system to a consistent and correct state after a failure, while preserving the concurrency and parallelism of multiple transactions.
- Recovery in concurrent systems can be classified into two categories: backward recovery and forward recovery.
  - Backward recovery: Moving the system from its current state back to a previously correct state by undoing the effects of erroneous transactions. It requires periodically saving the system's state to a stable storage and restoring it when a failure occurs. A checkpoint is a point in time when the system's state is saved. Backward recovery can be done using the log, which records the updates and actions of each transaction. The log can be scanned backward to undo the updates of failed transactions and restore the data items to their previous values.
  - Forward recovery: Moving the system from its current state to a new correct state by correcting the errors or compensating for their effects. It requires anticipating the possible errors and designing the system to handle them. Forward recovery can be done using redundancy, replication, error correction codes, or exception handling mechanisms.
- Recovery in concurrent systems interacts with concurrency control, which is the process of ensuring the correctness and consistency of concurrent transactions. Concurrency control can be done using locking, timestamping, or optimistic methods. Concurrency control affects the recovery process in the following ways:
  - Concurrency control can prevent some errors from occurring, such as lost updates, uncommitted dependencies, or inconsistent reads, by enforcing serializability or isolation levels of transactions.
  - Concurrency control can generate additional log records, such as lock requests, lock releases, or timestamps, which can be used for recovery purposes.
  - Concurrency control can impose some constraints on the recovery process, such as preserving the order of commit or abort operations, or maintaining the atomicity and durability of transactions.
- Recovery in concurrent systems can be done using the following techniques:
  - Transaction rollback: A failed transaction is rolled back by using the log to undo its updates and release its locks. The system scans the log backward from the point of failure, and for every log record of the transaction, it restores the data item to its previous value and writes a compensation log record (CLR) to indicate the undo operation. The transaction is then marked as aborted and its locks are released.
  - Checkpointing: A checkpoint is a point in time when the system saves its state to a stable storage, such as a disk or a tape. Checkpointing reduces the amount of log records that the system has to scan during recovery, and also the number of transactions that have to be rolled back or redone. Checkpointing can be done in different ways, such as:
    - Blocking checkpoint: The system suspends all transactions, flushes all buffers to the stable storage, writes a checkpoint record to the log, and then resumes the transactions. This ensures that the checkpoint is consistent and no transaction is active at the checkpoint time.
    - Non-blocking checkpoint: The system writes a checkpoint record to the log with a list of active transactions at the checkpoint time, and then flushes the buffers to the stable storage in the background. This allows the transactions to continue without interruption, but the checkpoint may not be consistent and some transactions may have to be redone after the checkpoint.
    - Fuzzy checkpoint: The system writes a checkpoint record to the log and then flushes the buffers to the stable storage in batches, allowing some transactions to perform updates while the checkpoint is in progress. This reduces the blocking time of transactions, but the checkpoint may be fuzzy and some transactions may have to be undone or redone after the checkpoint.
