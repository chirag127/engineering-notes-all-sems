## Unit 3 - Structural Testing

Structural testing is a type of software testing that focuses on the internal structure, design, and implementation of the software. It is also known as white-box testing, glass-box testing, or logic-driven testing. The main objective of structural testing is to verify that the software conforms to its specified design and that all the possible paths, branches, statements, and conditions are executed and tested.

Some of the topics covered in this unit are:

- **Code coverage**: Code coverage is a measure of how much of the source code is executed during testing. It can be expressed as a percentage or a ratio of the number of covered elements (such as statements, branches, paths, etc.) to the total number of elements. Code coverage helps to identify the untested or dead code and to assess the quality and completeness of the test cases.
- **Statement coverage**: Statement coverage is a type of code coverage that measures how many statements in the source code are executed at least once during testing. It is calculated as the ratio of the number of executed statements to the total number of statements. Statement coverage can be improved by adding more test cases that cover different scenarios and inputs.
- **Branch coverage**: Branch coverage is a type of code coverage that measures how many branches or decision points in the source code are executed at least once during testing. It is calculated as the ratio of the number of executed branches to the total number of branches. Branch coverage can be improved by adding more test cases that cover different outcomes of the branches, such as true and false conditions.
- **Path coverage**: Path coverage is a type of code coverage that measures how many paths or sequences of statements and branches in the source code are executed at least once during testing. It is calculated as the ratio of the number of executed paths to the total number of paths. Path coverage can be improved by adding more test cases that cover different combinations of branches and statements.
- **Control flow graph**: A control flow graph is a graphical representation of the structure and logic of the source code. It consists of nodes and edges, where nodes represent statements or blocks of code and edges represent the flow of control or the transitions between nodes. A control flow graph can be used to analyze the complexity, coverage, and dependencies of the code.
- **Cyclomatic complexity**: Cyclomatic complexity is a metric that measures the complexity of the source code based on the number of linearly independent paths in the control flow graph. It is calculated as the number of edges minus the number of nodes plus two, or alternatively, as the number of decision points plus one. Cyclomatic complexity can be used to estimate the number of test cases required to achieve full path coverage, as well as to identify the high-risk or error-prone areas of the code.
- **Data flow testing**: Data flow testing is a type of structural testing that focuses on the data dependencies and interactions between the variables and statements in the source code. It is based on the concept of defining and using variables, where a variable is defined when it is assigned a value and used when it is referenced or modified. Data flow testing aims to verify that the data flows correctly and consistently throughout the code and that there are no anomalies or errors such as uninitialized, unused, or overwritten variables.
- **Data flow graph**: A data flow graph is a graphical representation of the data dependencies and interactions between the variables and statements in the source code. It consists of nodes and edges, where nodes represent statements or blocks of code and edges represent the data flows or the transitions between nodes. A data flow graph can be used to identify the data flow anomalies and to design the test cases based on the data flow criteria.
- **Data flow criteria**: Data flow criteria are the rules or conditions that define the coverage and adequacy of the data flow testing. Some of the common data flow criteria are:

  - **All-Defs**: All-Defs criterion requires that every definition of every variable in the code is covered by at least one test case.
  - **All-Uses**: All-Uses criterion requires that every use of every variable in the code is covered by at least one test case.
  - **All-DU-Paths**: All-DU-Paths criterion requires that every definition-use pair of every variable in the code is covered by at least one test case that follows the path from the definition to the use.
  - **All-P-Uses**: All-P-Uses criterion requires that every predicate use of every variable in the code is covered by at least one test case that evaluates the predicate to both true and false values.
  - **All-C-Uses**: All-C-Uses criterion requires that every computational use of every variable in the code is covered by at least one test case.
