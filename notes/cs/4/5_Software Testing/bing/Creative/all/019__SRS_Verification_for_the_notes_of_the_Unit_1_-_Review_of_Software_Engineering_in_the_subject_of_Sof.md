### SRS Verification for the notes of the Unit 1 - Review of Software Engineering in the subject of Software Testing

- SRS stands for Software Requirement Specification, which is a document that describes the functional and non-functional requirements of a software system.
- SRS verification is the process of manually examining or reviewing the SRS document to ensure that it is correct, complete, consistent, unambiguous, and verifiable  .
- SRS verification is important because it can help to improve the quality of the software, reduce the cost and time of development, and avoid errors and misunderstandings in the later phases of software engineering  .
- SRS verification can be done by using various methods, such as peer reviews, walkthroughs, inspections, checklists, etc  .
- Peer reviews are informal reviews where a group of peers or colleagues examine the SRS document and provide feedback and suggestions for improvement.
- Walkthroughs are semi-formal reviews where the author of the SRS document presents it to a group of reviewers and explains the rationale and assumptions behind the requirements.
- Inspections are formal reviews where a group of reviewers follow a predefined process and use a checklist to identify and report defects in the SRS document .
- Checklists are verification tools that consist of a list of critical information content that the SRS document should contain or avoid. For example, a checklist may look for duplicate, missing, unclear, wrong, or conflicting information in the SRS document.
- A good SRS document should have the following quality characteristics:
  - Correctness: Every requirement should correctly represent the expectation from the software and the inputs and outputs should be sufficient for the specified processing.
  - Completeness: The SRS document should cover all the functional and non-functional requirements needed for the software and address all the possible scenarios and exceptions.
  - Consistency: The SRS document should not have any conflicting or contradictory requirements and every object should be referred to with a unique name and defined by one set of characteristics.
  - Unambiguity: The SRS document should have a single and clear meaning for every requirement and avoid ambiguous words or phrases.
  - Verifiability: The SRS document should state the requirements in a way that they can be verified by using test cases or other methods.
- A mnemonic to remember the quality characteristics of a good SRS document is **C3UV** (Correct, Complete, Consistent, Unambiguous, Verifiable).
- An example of a checklist for SRS verification is given below:

| S.No. | Checklist Item | Yes/No |
| ----- | -------------- | ------ |
| 1 | Does the SRS document have a clear and concise title? | |
| 2 | Does the SRS document have a table of contents and a list of figures and tables? | |
| 3 | Does the SRS document have an introduction section that describes the purpose, scope, definitions, acronyms, abbreviations, references, and overview of the document? | |
| 4 | Does the SRS document have a general description section that describes the product perspective, product functions, user characteristics, general constraints, assumptions and dependencies, and apportioning of requirements? | |
| 5 | Does the SRS document have a specific requirements section that describes the functional requirements, performance requirements, design constraints, software system attributes, and external interface requirements? | |
| 6 | Does the SRS document have an appendix section that provides any additional or supplementary information? | |
| 7 | Are all the requirements stated in the SRS document correct, complete, consistent, unambiguous, and verifiable? | |
| 8 | Are all the requirements stated in the SRS document traceable to the source of the requirement? | |
| 9 | Are all the requirements stated in the SRS document prioritized according to their importance and urgency? | |
| 10 | Are all the requirements stated in the SRS document testable by using test cases or other methods? | |
