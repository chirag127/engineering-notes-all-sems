### Extreme Programming in spm

- Extreme Programming (XP) is an agile software development framework that aims to produce higher quality software, and higher quality of life for the development team. 
- XP is the most specific of the agile frameworks regarding appropriate engineering practices for software development. 
- XP advocates frequent releases in short development cycles, intended to improve productivity and introduce checkpoints at which new customer requirements can be adopted. 
- XP takes the beneficial elements of traditional software engineering practices to "extreme" levels. For example, code reviews are considered a beneficial practice; taken to the extreme, code can be reviewed continuously (i.e. the practice of pair programming). 
- XP is based on five values: communication, simplicity, feedback, courage, and respect. These values guide the team to adopt the five rules and 12 practices of XP.  
- The five rules of XP are: 
  - Planning: The team and the customer collaborate to define the scope and priorities of the project, and to plan the releases and iterations. 
  - Managing: The team monitors and adjusts its progress and velocity based on feedback and metrics. 
  - Designing: The team keeps the design of the system as simple and clean as possible, and refactors the code whenever necessary. 
  - Coding: The team writes the code following the test-driven development (TDD) approach, and pairs up to review and improve the code quality. 
  - Testing: The team writes automated unit and acceptance tests for all the code, and runs them frequently to ensure the system works as expected. 
- The 12 practices of XP are:  
  - The Planning Game: The team and the customer meet regularly to define, estimate, and prioritize user stories (features) for the system. 
  - Small Releases: The team delivers working software to the customer frequently, usually every one or two weeks. 
  - Metaphor: The team uses a common vocabulary and a simple analogy to describe the system and its architecture. 
  - Simple Design: The team follows the principle of "You Aren't Gonna Need It" (YAGNI), and designs the system to meet the current requirements, not the future ones. 
  - Testing: The team writes automated tests before writing the code (TDD), and ensures that all tests pass at all times. 
  - Refactoring: The team improves the design of the system by changing its internal structure without altering its external behavior. 
  - Pair Programming: The team works in pairs, with one person writing the code and the other person reviewing it and providing feedback. 
  - Collective Ownership: The team shares the responsibility and the ownership of the code, and anyone can change any part of the code. 
  - Continuous Integration: The team integrates and tests the code several times a day, using a shared repository and a build server. 
  - 40-Hour Week: The team avoids working overtime and maintains a sustainable pace of work. 
  - On-Site Customer: The team has constant access to a real customer or a customer representative, who provides feedback and clarifies the requirements. 
  - Coding Standards: The team follows a consistent set of coding rules and conventions, such as naming, formatting, and documentation.
