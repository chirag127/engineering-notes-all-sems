### Documentation in Requirement Engineering Process in SRS

Documentation is an essential part of the requirement engineering process in software development. It involves creating, organizing, and communicating the requirements of the software system to various stakeholders, such as customers, developers, testers, and managers. Documentation helps to:

- Define the scope, purpose, and functionality of the software system.
- Establish a common understanding and agreement among the stakeholders.
- Provide a basis for planning, designing, testing, and maintaining the software system.
- Reduce the risk of errors, ambiguities, and inconsistencies in the software system.
- Facilitate the verification and validation of the software system.

There are different types of documentation in the requirement engineering process, such as:

- Software Requirement Specification (SRS): A document that describes what the software system should do and how it should perform, including both functional and non-functional requirements. It is the main output of the requirement analysis phase and serves as a contract between the customer and the developer. It also guides the subsequent phases of software development, such as design, implementation, and testing. An SRS should be clear, concise, consistent, complete, verifiable, and traceable.  
- Software Design Specification (SDS): A document that describes how the software system will be structured and implemented to meet the requirements specified in the SRS. It includes the architectural, component, interface, and data design of the software system. It is the main output of the software design phase and serves as a blueprint for the software construction and integration. An SDS should be coherent, modular, abstract, and maintainable. 
- Software Test Plan (STP): A document that describes the objectives, scope, strategy, and methods of testing the software system to ensure that it meets the requirements specified in the SRS. It includes the test cases, test procedures, test data, test environment, test tools, and test schedule. It is the main output of the software testing phase and serves as a guideline for the software verification and validation. An STP should be realistic, comprehensive, systematic, and traceable. 
- Software User Manual (SUM): A document that describes how to use the software system and its features, functions, and interfaces. It includes the installation, configuration, operation, and troubleshooting instructions for the software system. It is the main output of the software deployment phase and serves as a reference for the software users and maintainers. An SUM should be accurate, understandable, user-friendly, and consistent. 

Documentation in the requirement engineering process should follow some general principles, such as:

- Use a standard format and structure for each type of document, such as IEEE, ISO, or CMMI standards. 
- Use a consistent terminology and notation for each type of document, such as UML, ERD, or DFD diagrams. 
- Use a proper language and style for each type of document, such as formal, informal, technical, or non-technical. 
- Use a suitable tool and medium for each type of document, such as word processors, spreadsheets, databases, or web pages. 
- Use a version control and change management system for each type of document, such as SVN, Git, or Jira. 
- Use a review and approval process for each type of document, such as peer review, inspection, or walkthrough. 

Documentation in the requirement engineering process is not a one-time activity, but a continuous and iterative process that evolves along with the software system. Therefore, it is important to keep the documentation updated, accurate, and consistent throughout the software development lifecycle.
