### Review and Management of User Needs in Requirement Engineering Process in SRS

- User needs are the expectations and requirements of the end-users and other stakeholders of a software system. They describe what the system should do, how it should perform, and what qualities it should have.
- User needs are essential for defining the scope and purpose of the software project, and for ensuring that the system meets the needs of its intended users and the business goals of the client.
- User needs are typically elicited through various techniques, such as interviews, surveys, observations, brainstorming, prototyping, and use cases. User needs should be documented in a clear, concise, and consistent way, using natural language and avoiding technical jargon.
- User needs should be validated and verified to ensure that they are correct, complete, consistent, feasible, and testable. Validation techniques include user reviews, inspections, walkthroughs, and prototyping. Verification techniques include testing, analysis, and traceability.
- User needs should be managed throughout the software development life cycle, as they may change or evolve due to new requirements, feedback, or changing business environment. User needs management involves prioritizing, negotiating, resolving conflicts, and updating the user needs documentation.
- User needs are the basis for deriving the system requirements, which are more detailed and precise specifications of the system functionality, performance, quality, and constraints. System requirements are usually written in a formal or semi-formal notation, such as UML or Z.
- System requirements are also documented in a Software Requirements Specification (SRS) document, which is a comprehensive and structured description of the system to be developed. An SRS document should include the following sections:

  - Introduction: This section provides an overview of the SRS document, its purpose, scope, definitions, acronyms, abbreviations, references, and overview.
  - Overall Description: This section provides a general description of the system, its context, functions, user characteristics, constraints, assumptions, and dependencies.
  - Specific Requirements: This section provides a detailed description of the system requirements, such as functional requirements, non-functional requirements, external interface requirements, and design constraints.
  - Appendices: This section provides any additional information that may be relevant to the SRS document, such as data models, glossary, user interface mockups, or use case diagrams.
  - Index: This section provides an alphabetical list of terms and topics covered in the SRS document, along with their page numbers.

- An SRS document should follow some general principles, such as:

  - Completeness: An SRS document should cover all the user needs and system requirements, and should not omit any relevant information.
  - Consistency: An SRS document should not contain any contradictory or conflicting requirements, and should use consistent terminology and notation throughout.
  - Clarity: An SRS document should be easy to understand by the intended audience, and should avoid ambiguity, vagueness, or confusion.
  - Correctness: An SRS document should be accurate and valid, and should reflect the true user needs and system requirements.
  - Feasibility: An SRS document should be realistic and achievable, and should not specify any requirements that are impossible or impractical to implement.
  - Modifiability: An SRS document should be easy to modify and update, and should support changes and revisions as needed.
  - Traceability: An SRS document should be traceable to the user needs and the system design, and should support tracking and verification of the requirements.
  - Verifiability: An SRS document should be testable and measurable, and should specify the criteria and methods for verifying the requirements.
