### Bringing Microbatch and One-Record-at a- Time Closer Together

- Spark's distributed processing model is based on the concept of **resilient distributed datasets (RDDs)**, which are immutable collections of data that can be partitioned and processed in parallel across multiple nodes in a cluster.
- Spark supports two types of RDDs: **batch RDDs** and **streaming RDDs**. Batch RDDs are created from static sources, such as files or databases, and can be transformed and cached in memory for fast access. Streaming RDDs are created from dynamic sources, such as sockets or Kafka, and can be processed in real time using **Spark Streaming**.
- Spark Streaming is a framework that allows users to write streaming applications using the same APIs and abstractions as batch applications. Spark Streaming divides the input data stream into small batches, called **microbatches**, and processes them using batch RDDs. This approach is also known as **microbatching**.
- Microbatching has several advantages over the traditional one-record-at-a-time model, such as:
  - Higher throughput and lower latency, as microbatches can be processed in parallel and leverage Spark's in-memory caching and fault tolerance mechanisms.
  - Easier integration with batch processing, as microbatches can be joined with batch RDDs or written to the same output sinks as batch RDDs.
  - Simpler semantics and guarantees, as microbatches can be treated as atomic units of processing and provide exactly-once delivery and end-to-end fault tolerance.
- However, microbatching also has some limitations, such as:
  - Higher end-to-end latency, as microbatches introduce a delay between the arrival of data and its processing. The delay depends on the size and frequency of the microbatches, which are determined by the user or the system.
  - Lower flexibility and expressiveness, as microbatches impose a fixed window of processing and do not allow for stateful or event-driven computations that depend on the order or timing of the records.
  - Higher resource consumption, as microbatches require more memory and network bandwidth than one-record-at-a-time processing.
- To overcome these limitations, Spark has introduced several features and enhancements that bring microbatch and one-record-at-a-time closer together, such as:
  - **Structured Streaming**, which is a high-level API that allows users to write streaming applications using declarative SQL queries or DataFrame/Dataset operations. Structured Streaming handles the microbatching logic internally and provides a unified view of the data as an unbounded table that is continuously updated with new records. Structured Streaming also supports **event-time processing**, which allows users to define windows and watermarks based on the logical timestamps of the records, rather than the arrival time of the microbatches.
  - **Continuous Processing**, which is an experimental mode of Structured Streaming that allows users to process data with sub-millisecond latency using one-record-at-a-time processing. Continuous Processing uses a different execution engine than microbatching, which is based on **continuous operators** that run asynchronously and independently on each partition of the input stream. Continuous Processing also supports **exactly-once semantics** and **checkpointing**, which ensure the correctness and durability of the streaming computations.
  - **Adaptive Query Execution (AQE)**, which is a feature that allows Spark to optimize the execution plan of a query at runtime based on the characteristics of the data and the available resources. AQE can improve the performance and efficiency of both batch and streaming queries by dynamically adjusting the **shuffle partitions**, **join strategies**, and **skew handling**. AQE can also reduce the latency of microbatching by **coalescing** small microbatches into larger ones, or by **splitting** large microbatches into smaller ones, depending on the load and the capacity of the cluster.
