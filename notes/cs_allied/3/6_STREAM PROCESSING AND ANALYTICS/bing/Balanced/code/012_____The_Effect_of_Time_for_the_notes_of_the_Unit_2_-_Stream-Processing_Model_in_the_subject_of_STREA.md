### The Effect of Time

- Time is an essential dimension of stream processing, as streams are inherently temporal data sources that produce events continuously and in order.
- Time affects both the semantics and the performance of stream processing applications, as different notions of time can influence how events are processed, aggregated, joined, and delivered to the output.
- There are two main types of time that are relevant for stream processing: event time and processing time.
- Event time is the logical timestamp of an event, which usually reflects when the event occurred in the real world. For example, a sensor reading may have an event time that indicates when the measurement was taken, or a web click may have an event time that indicates when the user clicked on a link.
- Processing time is the physical timestamp of an event, which reflects when the event was processed by the stream processing system. For example, a sensor reading may have a processing time that indicates when the reading was received by the system, or a web click may have a processing time that indicates when the click was processed by the system.
- Event time and processing time may differ due to various factors, such as network delays, system failures, out-of-order events, or late events. For example, a sensor reading may arrive late due to network congestion, or a web click may be processed out of order due to load balancing.
- The difference between event time and processing time is called event-time skew or event-time lag, and it can affect the correctness and consistency of stream processing results. For example, if a stream processing application aggregates events by event time windows, then late or out-of-order events may cause incorrect or incomplete window results, or duplicate or inconsistent results across different windows.
- To deal with the effect of time, stream processing systems provide various mechanisms, such as:
  - Time semantics: the ability to specify how events are assigned to time windows, how windows are triggered, and how late or out-of-order events are handled. For example, a system may support event-time windows, processing-time windows, or hybrid windows that combine both types of time; a system may also support different types of triggers, such as count-based, time-based, or data-driven triggers; and a system may also support different types of handling strategies, such as discarding, updating, or appending late or out-of-order events.
  - Time synchronization: the ability to align the event time and the processing time across different sources, operators, and sinks in a stream processing application. For example, a system may use watermarking, which is a technique that estimates the progress of event time in a stream, and signals when all events with a certain event time have been processed; or a system may use checkpointing, which is a technique that periodically saves the state of a stream processing application, and allows for recovery in case of failures or reprocessing.
  - Time management: the ability to control the trade-off between latency and completeness in stream processing results. For example, a system may allow the user to specify a maximum allowed event-time lag, which determines how long the system will wait for late or out-of-order events before emitting a window result; or a system may allow the user to specify a minimum required completeness, which determines how many events must be processed before emitting a window result.
