#### Schema design in HBase

- HBase is a distributed, column-oriented database that is built on top of Hadoop and modeled after Google Bigtable. It provides fast and random access to large amounts of data.
- HBase schema design is different from relational database schema design. It requires careful consideration of the data access patterns, the row key design, the number and structure of column families, and the use of filters and compression.
- HBase organizes data into tables, which consist of rows and columns. Each row is identified by a unique row key, which is a byte array. Each column belongs to a column family, which is a logical grouping of columns that share some common properties. A column is identified by a column family name and a column qualifier, which is also a byte array. A cell is the intersection of a row and a column, which stores a value and a timestamp. A cell can have multiple versions, which are sorted by the timestamp in descending order.
- HBase supports denormalization and nested entities. Denormalization means storing redundant data in multiple tables or columns to avoid joins and improve performance. Nested entities are columns whose names are unique identifiers for the nested records and whose values are the entire records mashed together. HBase allows dynamic column definition, so there is no problem in creating nested entities.
- HBase schema design should follow some general principles, such as:

  - Choose a row key that is unique, short, and sortable. The row key determines the physical location of the data and the scan performance. A good row key should avoid hotspots, which are regions that receive more requests than others. A bad row key example is a sequential number or a timestamp, which can cause write skew and read latency. A good row key example is a hash or a composite key, which can distribute the data evenly and support range queries.
  - Choose a column family that is stable, coherent, and compact. The column family determines the storage and I/O characteristics of the data. A good column family should have a fixed and small number of columns, which are frequently accessed together and have similar data types and sizes. A bad column family example is a column family that has many columns, which are rarely accessed together and have different data types and sizes. A good column family example is a column family that has a few columns, which are often accessed together and have similar data types and sizes.
  - Choose a column qualifier that is descriptive, concise, and consistent. The column qualifier determines the logical structure and meaning of the data. A good column qualifier should be easy to understand and query, and should not change frequently. A bad column qualifier example is a column qualifier that is ambiguous, verbose, or variable. A good column qualifier example is a column qualifier that is clear, succinct, or fixed.
  - Choose a cell value that is atomic, simple, and compressed. The cell value determines the content and size of the data. A good cell value should be self-contained and easy to process, and should not exceed the maximum size limit of 10 MB. A bad cell value example is a cell value that is complex, large, or uncompressed. A good cell value example is a cell value that is primitive, small, or compressed.
  - Choose a filter that is selective, efficient, and relevant. The filter determines the filtering and sorting criteria of the data. A good filter should reduce the amount of data returned and processed, and should match the query needs. A bad filter example is a filter that is broad, costly, or unnecessary. A good filter example is a filter that is narrow, cheap, or essential.

- HBase schema design should also consider some advanced parameters, such as:

  - Compression: Compression can reduce the disk space and network bandwidth required for storing and transferring data. HBase supports different compression algorithms, such as GZIP, LZO, LZ4, and Snappy. The choice of compression algorithm depends on the trade-off between compression ratio and CPU overhead. Generally, GZIP has the highest compression ratio but the highest CPU overhead, while Snappy has the lowest compression ratio but the lowest CPU overhead. LZO and LZ4 are somewhere in between. Compression can be applied at the column family level or the table level.
  - Bloom filter: Bloom filter can reduce the disk I/O required for reading data. HBase supports different bloom filter types, such as ROW, ROWCOL, and NONE. The choice of bloom filter type depends on the trade-off between memory usage and false positive rate.
