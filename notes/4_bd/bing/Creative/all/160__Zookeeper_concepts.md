#### Zookeeper concepts

- Zookeeper is a distributed coordination service that provides a consistent and reliable way to manage configuration, synchronization, naming, and leader election among a cluster of nodes.
- Zookeeper is based on the concept of a **znode**, which is a data structure that represents a file or a directory in a hierarchical namespace. A znode can store data, metadata, and have children znodes.
- Zookeeper maintains a **zookeeper quorum**, which is a set of servers that communicate with each other and agree on the state of the znodes. A quorum requires a majority of servers to be available and consistent, which ensures fault tolerance and high availability.
- Zookeeper clients can connect to any server in the quorum and perform operations on the znodes, such as create, delete, read, write, watch, and set ACLs. Zookeeper guarantees that the operations are **atomic**, **consistent**, **isolated**, and **durable** (ACID).
- Zookeeper also provides a **watch** mechanism, which allows clients to register for notifications when a znode or its children change. This enables clients to react to changes in the cluster state and implement synchronization primitives, such as locks, barriers, queues, etc.
- Zookeeper uses a **leader-follower** model, where one server is elected as the leader and the rest are followers. The leader is responsible for coordinating the updates to the znodes and broadcasting them to the followers. The followers replicate the updates and serve read requests from the clients. The leader election is done using a **Zab** protocol, which is a variant of Paxos.
- Zookeeper has a **version number** associated with each znode, which is incremented every time the znode is modified. This helps to implement **conditional updates** and **optimistic concurrency control**, where clients can specify the expected version of the znode before performing an operation. If the version does not match, the operation fails and the client can retry with the latest version.
- Zookeeper supports two types of znodes: **persistent** and **ephemeral**. Persistent znodes are permanent and remain in the namespace until explicitly deleted. Ephemeral znodes are temporary and are automatically deleted when the client that created them disconnects. Ephemeral znodes are useful for implementing dynamic membership and leader election, where clients can create ephemeral znodes under a common parent znode and watch for changes in the children list.
- Zookeeper also supports **sequential** znodes, which are znodes that have a unique suffix appended to their name. The suffix is a monotonically increasing sequence number that is maintained by the server. Sequential znodes are useful for implementing distributed counters, queues, and unique identifiers.
