### Documentation in Requirement Engineering Process in SRS

The Requirement Engineering Process results in various documents which serve as documentation. Proper documentation is essential for -

1. Communicating the requirements to the stakeholders
2. Providing a reference for designing and developing the software
3. Facilitating maintenance and evolution of the software

The major documentation components in the Requirement Engineering Process for Software Requirements Specification (SRS) are -

1. **Use Case Diagrams** - Graphically represent the interaction between the system and external actors/entities. Help in envisioning the functionalities and scope of the system.

2. **Use Cases** - Describe interactions between the system and actors in a sequential manner. Cover the functional requirements and main scenarios/flows. Can include extensions and exceptions.

3. **Activity Diagrams** - Depict the flow of activities/actions in the system. Help in elaborating the scenarios and flows in the Use Cases in a graphical manner.

4. **Domain Model** - Represent the key concepts/entities and their relationships in the problem domain. Aid in understanding the scope and knowledge of the domain for which the software is being developed.

5. **Sequence Diagrams** - Show the sequence/ ORDER OF MESSAGES in the interactions between objects for a particular scenario. Supplement the Use Cases by covering the dynamic aspects.

**Mnemonics** -
- "ucid" - Use Case Diagrams, Use Cases, Activity Diagrams, Domain Model, Sequence Diagrams
- "comms" - Communication (among stakeholders), Construct (models/diagrams), Memo (documentation)

**Advantages** -
- Common understanding between stakeholders
- Basis for further software engineering activities
- Facilitates maintenance by providing a reference

**Disadvantages** -
- Documentation can get outdated if not properly maintained
- Can be time-consuming to create and update
- If incomplete/inconsistent, can lead to misunderstandings
